<objective>
Create the schema every tenant-managed HR list needs, once, in one changeset.

`employees.department` and `employees.designation` are TEXT columns today. There is no table behind
them, so the Employees screen offers a free-text box, and the user's complaint — three spellings of
one department and no report that can group them — follows directly from the schema. There is also no
salary-component table at all, which is why `PayrollRunService.calculate` sets gross equal to basic and
writes an empty allowances map.

Three of hr-service's sibling services (pos, kitchen, purchasing) carry an `RlsForcedInvariantIT`.
hr-service does not, despite `hr_db` being FORCE RLS and despite this plan adding four more tenant
tables. That gap closes here, with the behavioural canary as well as the schema query, because the
schema query alone cannot observe the defect it is guarding against.

Purpose: plans 29-05, 29-08, 29-09 and 29-11 all need these tables, and putting them in one changeset
means one Liquibase ordering to reason about instead of three that can be applied out of order.
Output: one changelog, one master include, one invariant test with two independent proofs.
</objective>

  <action>
    Create 014-hr-config-tables.xml with one changeset creating all four tables, and a second changeset
    applying RLS in the same file so the two can never be applied apart.

    `departments`: id, tenant_id, name, an optional code, an active flag, and the audit columns the
    other hr tables carry. Unique on (tenant_id, lower(trim(name))) via a functional unique index —
    a plain UNIQUE(tenant_id, name) is the thing that lets "Waiter" and "waiter" coexist, and this
    phase exists partly because that happened. Do not add a branch_id: a department list is a property
    of the tenant, and scoping it per branch would force an owner to retype it once per location.

    `designations`: the same shape, plus a nullable department_id foreign key, so a tenant that wants
    designations grouped under departments can have that and a tenant that does not can leave it null.
    Same case-insensitive uniqueness, scoped (tenant_id, lower(trim(name))).

    `salary_components`: id, tenant_id, code, name, a kind discriminator distinguishing an earning from
    a deduction, a calculation discriminator distinguishing a fixed paisa amount from a percentage of
    basic, a fixed amount as BIGINT paisa, a rate as NUMERIC — never a float, per the phase constraint —
    a taxable flag, an active flag, audit columns. Exactly one of the amount and the rate is populated,
    enforced by a CHECK constraint keyed off the calculation discriminator; a component that is
    ambiguous about how it is computed is a payroll defect waiting for a month-end. Unique on
    (tenant_id, lower(trim(code))). The code column must not collide with the deduction map keys
    PayrollRunService already writes into payslips; read those first and add a CHECK or a comment
    recording the reserved set.

    `employee_salary_components`: id, tenant_id, employee_id and salary_component_id foreign keys, an
    effective_from date, a nullable effective_to, and an optional override amount or rate for the
    employee-specific case. Unique on (tenant_id, employee_id, salary_component_id, effective_from).

    Money stays BIGINT paisa and rates stay NUMERIC with an explicit scale. The phase constraint is
    absolute here: `tax_config` mapping NUMERIC as a Java double is what stopped hr-service booting,
    and a float column would reproduce that class of defect one table over.

    In the second changeset, for each of the four tables: ENABLE ROW LEVEL SECURITY, FORCE ROW LEVEL
    SECURITY, and a tenant_isolation policy matching the idiom in 011 exactly. Then extend the GRANT
    to hr_user with the four new tables. Write a rollback block dropping the four tables.

    Seed nothing. Not a default department, not a standard designation, not a conventional allowance.
    The user was explicit that nothing may require a developer to seed, and a migration-seeded row is a
    developer seeding it. An empty list with a clear empty state on the screen is the correct first
    experience; plan 29-11 owns that empty state.

    Append the include to db.changelog-master.xml after 013 and before 020, keeping the numeric ordering
    the file already reads by.
  </action>
