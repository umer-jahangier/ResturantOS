<objective>
Make the blocker fixable by the person it blocks.

The financial wiring audit's finding is the reason this phase exists in the form it does: `tax_config`
holds one row, for a placeholder tenant, for a fiscal year that has already ended, with no screen. Plan
29-06 built the API. This plan builds the screen, and fixes the surface that reports its absence.

The Payroll screen today takes the period as two `<Input type="number">` boxes and reports every mutation
failure with `onError: () => toast.error("Action failed")`. So the single most likely outcome of pressing
Calculate on a fresh tenant — a refusal because nobody has configured this fiscal year — arrives as two
words that name neither the cause nor the cure. That is the class of message D-35-03 targets, and it sits
directly on top of the phase's hard blocker.

Purpose: definition-of-done items 4 and 5. After this plan an owner can go from a fresh tenant to a
calculated payroll run without a database client.
Output: a tax configuration screen with a slab editor, a salary-component area, and a payroll screen that
explains itself.
</objective>

    Build the screen on the standard, with the slab table as a field array whose field names match the
    indexed path format plan 29-06 emits, so a server-side structural violation lands on its row. The
    existing resolver already walks indexed paths — that support was added for purchase-order lines — so
    this is a matter of naming the fields correctly, not of new machinery.

    Implement the four structural rules client-side as well as relying on the server's. This is one of the
    few places where duplicating a rule is right, and the reason is specific: a slab table is edited as a
    whole and a structural error is a property of the set, so telling the user after a round trip means
    they have already left the screen mentally. Derive both from one shared predicate if the schema can
    express it; where it cannot, put the client copy immediately beside a comment naming the server's copy.

    from plan 29-09 exactly: if the rate travels as a string it stays a string through the input, and the
    input is a text field with a numeric pattern rather than `type="number"`, whose value a browser may
    normalise. A rate that reads back as 11.5 when the accountant typed 11.500 is cosmetic; one that reads
    back as 11.499999 is a wrong payslip.

    Copy-forward is a convenience with a real hazard: last year's slabs are the ones a Finance Act just
    changed. Make the draft state obvious, require confirmation, and put the caution in the copy — the
    seeded changelog's own comment already says these figures are verify-with-accountant, and the screen
    should say the same thing to the person who can actually verify them.

    Keep previous years readable. Nothing else in the product can explain an old payslip.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-29-12-A | Tampering | Decimal precision lost on a tax rate between input and request | critical | mitigate | The serialisation decision from plan 29-09 is honoured end to end; rates use a pattern-validated text input rather than a numeric one; a byte-identical round trip is asserted |
| T-29-12-B | Tampering | Copy-forward carrying a superseded statutory rate into a new year | high | mitigate | Copy-forward produces a visibly-marked draft requiring explicit confirmation, with caution copy naming the Finance Act |
