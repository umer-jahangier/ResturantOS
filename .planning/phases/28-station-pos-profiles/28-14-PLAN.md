<objective>
Prove the phase. D-28-05's last line is the standard: *"If a step needs SQL, the phase is not done."*
And the definition of done's sixth item requires all of it to be reachable from the UI and proven in a
browser.

This phase has repeatedly leaned on the observation that this project ships components that look wired
and are not — a table picker that worked perfectly against a catalogue nothing could write to, a POS
WebSocket that refused every browser client, a station CRUD that has never had a caller. Every plan
before this one asserted its own piece at the service or the component level. This plan is the one that
puts the pieces in a browser in the order a restaurant owner would actually use them and reads what
comes out.

Two assertions carry the phase.

**The spanning order.** One order with a dish and a drink, placed through the real POS, must produce two
tickets whose contents are disjoint. The assertion is on which items appear on which ticket, by name.
Counting tickets passes when both tickets list both items, which is exactly the wrong outcome D-28-04
describes.

**The unassigned user.** A user with no station assignment must still see everything. Every user in
every tenant is in that state today, so this is not an edge case, it is the installed base. It gets its
own named scenario so that a failure names itself rather than being buried in a larger journey.

A live gateway script sits beside the browser spec asserting the same facts over HTTP. When something
breaks later, the two together say whether the regression is in a screen or in a service, which is the
difference between an afternoon and a week.

Purpose: this is the phase's evidence, not its documentation.
Output: a browser journey, a live script, and screenshots of the states a reviewer should be able to see.
</objective>
