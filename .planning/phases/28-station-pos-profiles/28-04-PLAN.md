<objective>
Model the thing the user asked for by name: *"a dedicated POS which should be selecting respective
menu"* (D-28-03). A terminal is a profile — a name, a code, a branch, the stations it fires to, and the
menu categories it offers. There is no such entity in this codebase today; a grep for a terminal class
in pos-service returns nothing, and `orders` has a cashier and a till session and no notion of which
physical POS took the order.

Two rules carry most of the weight here.

**An empty category set means the terminal offers everything.** A tenant who never opens this screen
must keep today's behaviour exactly, and today's behaviour is one POS showing the whole menu. An empty
join table is the only encoding where doing nothing is the compatible thing; a `serves_all` boolean
would be a second source of truth that can disagree with the rows it summarises.

**The category scope is a menu filter, not an authorization boundary.** The server does not refuse an
add-item for a category the terminal does not list. Saying that out loud matters: an ambiguous
half-enforcement is exactly the shape of the guard phase 13-16 found in `createOrder`, which only fired
when a user id happened to be present and therefore established nothing it claimed. If a hard boundary
is ever wanted it belongs in the policy engine with its own rules and its own tests.

This plan is the backend only. Order attribution lands in 28-12, the admin UI in 28-09, and the runtime
menu scoping in 28-13.

Purpose: 28-09, 28-12 and 28-13 all have nothing to talk to until a terminal exists.
Output: a terminal entity, its scope tables, and an admin API behind its own permission.
</objective>

    - A terminal with category rows reads back offering exactly those.
    - A terminal with no station rows reads back as firing to every station.

  <action>
    Write V14 creating three tables: `pos_terminals`, `pos_terminal_categories` and
    `pos_terminal_stations`.

    `pos_terminals` carries tenant and branch ids, a short operator-facing code, a name, a service model,
    an optional default order type, an optional opaque receipt-printer reference, an is_active flag and
    the standard audit columns. Unique on tenant, branch and code, mirroring the station constraint.
    Money, if any is ever added here, is BIGINT paisa — none is added by this plan.

    Keep the printer reference an opaque nullable string. Thermal printing is owned by phase 26 and it
    decides the identifier scheme; modelling an address or a model name here would either duplicate or
    contradict that decision. One nullable handle is the correct amount of coupling.

    `pos_terminal_categories` is a join of terminal to menu category, tenant-scoped, keyed on the pair.
    `pos_terminal_stations` is a join of terminal to station, same shape. Both empty-means-all. Put that
    rule in a comment in the DDL as well as in the entity, because it is the kind of default a later
    reader "fixes" by adding a flag.

    Every one of the three tables gets a tenant_isolation policy, then ENABLE, then FORCE. Not one of
    them may ship ENABLE-only: `RlsForcedInvariantIT` will fail the build, and the reason it exists is
    that thirty-three tables shipped with inert isolation and a green suite proved nothing. Add the
    tables to the same posture V11 established rather than inventing a variant.

    Create the entities and the two repositories. Every finder carries an explicit tenantId predicate in
    addition to the policy — under FORCE an unscoped query returns zero rows rather than erroring, so a
    wiring break presents as "this branch has no terminals" and reads like a configuration question. The
    predicate is also what keeps the query correct if the tenant GUC is ever not set on a connection.

    Create `ServiceModel` as an enum with the counter, table-service and self-serve values. It drives
    which defaults a terminal offers and whether the table picker is shown; it is not a security control
    and its javadoc should say so.

    Add the three tables to the RLS canary's world by simply following V11's posture; do not modify
    `RlsForcedInvariantIT` to accommodate them. If it fails, the migration is wrong, not the test.
  </action>
