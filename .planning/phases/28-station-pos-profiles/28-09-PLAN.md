<objective>
Build the screen where an owner says *"this one is the bar till, it sells drinks, and it fires to the
bar."* This is the configuration half of D-28-03, and it is what makes D-28-05 true for terminals: no
developer, no seed, no support ticket.

The one piece of interaction design that carries real weight is how an empty menu scope is shown. In the
data model it is an empty set and it means "everything" — that encoding exists because a tenant who
never opens this screen must keep today's behaviour, and an empty join table is the only shape where the
do-nothing path is the compatible path. But an admin looking at a screen with nothing ticked will read
it as "this till sells nothing". So the screen states the meaning in words: with no categories selected,
it says the terminal offers the whole menu. The encoding is for the database; the sentence is for the
person.

The second is honesty about what the scope is. It decides what the terminal displays. It is not an
access control, the server does not refuse an item outside it, and the copy must not suggest otherwise —
a screen that implies a boundary the server does not enforce is worse than no screen, because it gets
relied on.

Purpose: this is the configuration surface plan 28-13 reads at runtime.
Output: the terminal frontend layers and the Terminals screen the navigation already points at.
</objective>
