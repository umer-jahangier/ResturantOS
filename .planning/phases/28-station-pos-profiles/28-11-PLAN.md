<objective>
This is the screen the user was describing. Their words: *"don't have the exact capacity to select the
specific screen/station for that account he is creating."* The account creation form has a branch and a
role and nothing else, and D-28-02 puts the station beside them, at creation and at edit.

Two things have to be got right or the feature does harm.

**Selecting nothing means everything.** Every user in every tenant is currently unassigned, and that is
the safe default for a small restaurant with one screen. A form that renders an empty selection as
"none" will read as a broken or restrictive state, and an admin will start ticking boxes to fix a
problem that does not exist — turning a working single-screen kitchen into a set of narrow ones. The
field says, in words, that no selection means the user sees every station in the branch.

**The station picker follows the branch.** A station code is unique within a branch, not within a
tenant. Offering stations before a branch is chosen would let an admin assign something that cannot be
resolved. The form already pairs branch and role and refuses one without the other; the station field
extends that pairing rather than competing with it.

**And the change is not instant for a signed-in user.** The scope rides the access token, so an
assignment edited mid-shift takes effect when that user's token next refreshes. Plan 28-07 records the
bound. The form states it rather than leaving an admin to conclude the setting did not save.

Purpose: this closes the user's stated gap in the place they said it was missing.
Output: a station field in the user form, the assignment on the detail view, and honest copy about both
the default and the delay.
</objective>
