<objective>
Record where an order came from. Without this, a terminal is a configuration object with no evidence
that anything ever used it — the definition of decorative.

`Order` carries a cashier and a till session and has no notion of which physical POS took it. Adding one
is small and additive, and it is what makes "which till is busiest" answerable later and what lets plan
28-14 prove in a browser that the bar terminal is the thing that took the drinks order.

Three boundaries are drawn deliberately and none of them may be crossed.

**The terminal id is an attribution hint, never an authorization input.** It arrives from a client, so
it is validated to belong to the caller's own branch before it is stored — the same treatment phase 19b
gave `tableId` after finding that `createOrder` bound it with no validation at all and would happily
accept a sibling branch's table or one that never existed. That defect was unreachable only because no
tenant had any tables. Terminals are about to have the same property, and the same fix is applied
before the same bug becomes reachable.

**The origin terminal is not the settlement terminal.** A waiter takes an order on a handheld with no
till; a cashier settles it at the counter. Those are two different true facts and overwriting one with
the other loses both. This plan records origin only. Settlement attribution would require binding a till
to a terminal, which is a money change with a breaking index swap behind it, and it is not in this phase.

**The till rule does not move.** Phase 13-16 established that no cash is taken without an open drawer for
the paying user, and D-28-06 says not to weaken what is proven. This plan adds a nullable column to
`orders` and touches nothing in `till_sessions`, `PaymentServiceImpl`, or the open-till index.

Purpose: plan 28-13 sends the terminal from the browser and plan 28-14 reads it back.
Output: order attribution, validated, additive, and bounded.
</objective>
