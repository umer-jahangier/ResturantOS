<objective>
D-28-04 says split tickets are required, not optional, and says how to prove it: *"Assert this with an
order that spans both."* This plan does exactly that, and fixes the one thing that multi-station service
makes visible.

**The split already works.** `TicketRoutingService.groupByStation` emits one ticket per order and
station code, and `route` appends-or-creates per group. A burger routed to a grill and a mojito routed to
a bar produce two tickets on the first fire. That is not a claim this plan is making on the strength of
the class existing — this project has repeatedly shipped code that looks wired and is not, so this plan's
entire job is to fire a real spanning order and read what comes out the other end. A unit test over the
grouping function would prove the grouping function and nothing about whether an order can reach it.

**What multi-station makes visible is the ready aggregate.**
`TicketServiceImpl.checkAndPublishOrderReady` fires `ORDER_READY` only when no ticket for the order is
still pending or cooking, which is correct. But the payload carries the station code of whichever ticket
happened to finish last, and on the POS side `OrderReadyConsumer` then advances only the lines whose
station key equals that one code. So on a two-station order, the aggregate advances one station's lines
and silently ignores the other's. It is not a visible bug today because a per-item status event is
published on every transition and applied with an ordinal guard, so the per-item path does the real
work and the aggregate is a redundant backstop that happens to be wrong. Multi-station is exactly the
configuration where a regression in the per-item path would stop being masked by the aggregate — which
is the situation this phase creates.

Purpose: this is the plan that turns D-28-04 from a property of the code into a fact about the product.
Output: two spanning-order integration tests on both sides of the boundary, and a correct ready
aggregate.
</objective>
