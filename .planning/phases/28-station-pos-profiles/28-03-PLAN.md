<objective>
Close a live cross-tenant read on a running socket, before this phase multiplies the number of boards
that socket serves.

`KdsWebSocketHandler.validateJwtAndPermission` takes `branchId` as a parameter and never reads it. Its
body checks one thing: that the token's permission list contains `pos.kds.view`. So any holder of that
permission — including one belonging to a different tenant, since the tenant is likewise never compared
— can subscribe to another branch's live ticket stream and watch it in real time. The correct version of
this check is already written next door in `PosOrderWebSocketHandler.validateJwt`, which compares the
token's branch claim against the path variable.

This is deliberately its own plan and its own wave. It depends on nothing in this phase, it is two files,
and it is the single most shippable thing here: it can be merged and deployed on its own the day it is
written, ahead of every other plan. Phase 28 adds station-typed boards and staff-scoped boards, both of
which increase the number of live subscriptions — closing this first means that growth happens on a
socket that checks who is asking.

Constraint, stated because it is easy to conflate: `WS_UPGRADE_PATHS` is the gateway's list of paths
eligible for a WebSocket upgrade. It is not this defect and it is not touched. The fix is entirely
inside kitchen-service's own handler.

Purpose: plan 28-07 adds a station filter to this same handler and must land on a handler that already
validates identity.
Output: a KDS socket with POS-socket parity, and a test that fails if the parity is lost again.
</objective>

  <action>
    Run GitNexus impact analysis on `KdsWebSocketHandler` before editing. It is the delivery path for
    every live board in the product.

    Read the token's tenant and branch claims and compare both against the values parsed from the
    subscription path, in addition to the existing permission check. Mirror `PosOrderWebSocketHandler`'s
    comparison rather than inventing a second style — the codebase should end up with one shape for this,
    not two. A missing or unparseable claim is a refusal, never a pass: a check that admits when it
    cannot decide is the same class of guard as the one phase 13-16 documented, which only fired when a
    user id happened to be present and therefore established nothing.

    Widen the parameter list so the handler passes the tenant through to the validator, or resolve the
    tenant inside it — whichever keeps the call site honest. Do not leave a parameter that is accepted
    and ignored; that is precisely the defect being fixed, and a second one would be worse for having
    been introduced deliberately.

    tenant or the permission was the problem hands an attacker a discriminator; the current generic text
    is correct and should be left alone. Add a debug-level log line that DOES record which check failed,
    because the operator debugging a legitimately mis-configured board needs that and the client must not
