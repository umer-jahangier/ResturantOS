<objective>
This is where D-28-02 gets teeth. Plan 28-01 put a user's stations into their token; this plan makes the
kitchen actually honour them.

Today a kitchen user sees every ticket for the branch. `KdsController.getTickets` with no station code
returns the branch-wide board; `getStations` returns every active station; the station picker lets one
screen hop freely between all of them; and the socket pushes whatever the subscription asks for. Nothing
in that chain knows who is looking.

The single most dangerous line in this plan is the default. **An absent station set means unrestricted.**
Every user in the product today has no assignment, so if an empty set is read as an empty allow-list,
every kitchen screen in every tenant goes blank the moment this deploys. D-28-02 states the default
explicitly for that reason and the definition of done asserts it explicitly. This plan treats "no
assignment sees everything" as a first-class behaviour with its own tests, not as a fallback branch.

The scope is decided once, in `KdsAuthorizationService` — which already owns tenant and branch authority
for this service — and applied to all three surfaces. Three copies of one rule is how a bar screen ends
up correctly filtered on the list and unfiltered on the socket.

Purpose: without this, station assignment is a stored preference nobody reads.
Output: a scoped board, a scoped station list, and a scoped socket.
</objective>

  <behavior>
    - A caller whose token carries no station attribute at all produces an unrestricted scope.
    - A caller whose token carries two station codes produces a scope naming exactly those two.
    - A caller whose token carries an attribute value that is present but empty ALSO produces an unrestricted scope, so a malformed token degrades open rather than blacking out a kitchen.
    - A caller whose token carries a value of an unexpected shape produces an unrestricted scope and logs a warning, rather than throwing.
    - An unrestricted scope reports itself as unrestricted through a single predicate the callers use, rather than as an empty collection the callers have to interpret.
    - Asking a restricted scope whether it permits a station it names returns true; asking about one it does not name returns false.
    - Asking an unrestricted scope about any station returns true.
  </behavior>
  <action>
    Create `StationScope` as a small value type in the authz package with two states: unrestricted, and
    restricted to a named set. Give it one predicate that answers "may this caller see this station
    code" and one that answers "is this scope unrestricted". Callers must never inspect a raw collection
    — the whole failure mode this plan is defending against is a caller looking at an empty list and
    concluding "no stations permitted". Make that reading impossible by not exposing the list in a shape
    that invites it.

    Every degenerate input maps to unrestricted: absent attribute, present-but-empty value, wrong type,
    unparseable entry. Write that decision as a comment naming the consequence of the alternative —
    every existing kitchen screen in the product goes blank — because a later reader tightening this
    into fail-closed would be making a locally reasonable change with a product-wide outage attached.
    Log a warning on the malformed cases so an operator can see that something is wrong even though the
    board kept working.

    Add a resolve operation to `KdsAuthorizationService` that returns the scope for the current
    authenticated caller. Put it beside the existing view and update authorization methods so this
    service has one authority object, not two. The scope resolution runs AFTER the existing tenant and
    branch checks, never instead of them: identity is verified first, scope is applied second, and the
    order matters because a scope check that runs first would be deciding what a caller may see before
    establishing who the caller is.

    Write `StationScopeIT` covering the seven behaviours. The three degenerate-input cases are the ones
    that matter; write them first and make sure each fails before the implementation exists.
  </action>
