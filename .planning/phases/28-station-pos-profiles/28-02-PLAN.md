<objective>
Make a station say what kind of destination it is (D-28-01), and carry that answer all the way to the
screen that has to decide whether to show the ticket. A bar ticket landing on the kitchen board is the
failure this closes.

The type is a closed enum in the domain — `KITCHEN`, `BAR`, `PANTRY`, `EXPO`, `DESSERT` per D-28-01 —
with a database CHECK constraint behind it and a migration path for new values. Free text is
explicitly refused: the whole point of a type is that two people spelling the same concept differently
get the same station.

This plan touches two services because the type is worthless in pos_db alone. `kds_stations` is an
event-fed projection of pos stations — `Station`'s own javadoc says so — and the board reads the
projection. The two payload records must therefore be edited together, in one commit, because field-name
parity between them is the only contract check that exists and a mismatch drops every kitchen message
without an error.

Purpose: plans 28-06, 28-07 and 28-09 all need a station to have a type before they have anything to
filter on.
Output: a typed station, end to end, with today's behaviour unchanged for every existing row.
</objective>
