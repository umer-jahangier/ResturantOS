<objective>
Give a user a set of stations, and make that set travel with the user's identity (D-28-02). This is the
half of the user's stated gap that lives in the account system: *"don't have the exact capacity to
select the specific screen/station for that account he is creating."*

The carrier is the access token's `attributes` map. That is not a new mechanism —
`PermissionResolver.buildForAssignment` already puts `approval_limit_paisa` there, and shared-lib's
`JwtAuthenticationFilter` reads `attributes` directly out of the JWT in every downstream service
rather than from a gateway header. So kitchen-service can read a user's stations with no cross-service
call, no projection table, and no consumer that can silently drop a message. Plan 28-07 does the
reading; this plan does the writing and the minting.

This plan also lands `pos.terminals.admin`, because `PermissionCatalogClosureTest` scans
`@PreAuthorize` across every service and fails the build on a permission that no changelog defines —
so the permission must exist before plan 28-04's controller references it. Both changelogs land here
so that exactly one plan owns `db.changelog-master.xml`.

Purpose: nothing else in D-28-02 is testable until a user can carry a station.
Output: an auth_db assignment table, an admin API, a JWT attribute, and the terminal permission.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tenant admin to user-service | One user's station scope is being set by another user |
| user-service to auth-service | The internal hop that carries the assignment |
| auth-service to auth_db | Assignment rows written under forced row-level security |
| auth-service to every downstream service | The signed token that carries the resulting attribute |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-28-01-A | Elevation of Privilege | Station assignment target selection | high | mitigate | The target user is resolved inside the caller's tenant and a foreign target answers exactly as a nonexistent one, so the endpoint is not a cross-tenant probe |
| T-28-01-B | Tampering | Client-asserted station scope | high | mitigate | The station list is only ever read from a signature-verified token minted by auth-service; no endpoint accepts it as a request input |
| T-28-01-C | Information Disclosure | Cross-tenant assignment rows | critical | mitigate | `user_station_assignments` is ENABLEd and FORCEd with a tenant_isolation policy, and the repository carries an explicit tenant predicate as the second line |
| T-28-01-D | Denial of Service | An empty-list encoding read as an empty allow-list | high | mitigate | Absent-key is the only encoding of "unrestricted"; an explicit test asserts the key is absent, not empty |
| T-28-01-E | Spoofing | Permission granted to no role | medium | mitigate | Changelog 085 carries the 083-style verification changeSet that fails the migration if `pos.terminals.admin` has zero holders |
| T-28-01-F | Repudiation | Silent removal of a station assignment | low | accept | Rows are deactivated rather than deleted, so the prior state is readable; a dedicated audit event is not warranted for a view-scope setting |
| T-28-01-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages. If one becomes necessary, halt and require the package-legitimacy audit plus a blocking human checkpoint |
</threat_model>
