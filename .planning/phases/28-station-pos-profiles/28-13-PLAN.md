<objective>
This is the sentence in the user's request that has had no implementation anywhere: *"a dedicated POS
which should be selecting respective menu."* A bar till should open showing drinks.

`MenuGrid` builds its category list from every active category the tenant has. There is no notion of
which POS is asking. Plan 28-04 gave a terminal a category scope and plan 28-09 gave an admin a way to
set it; this plan is where the scope changes what a cashier sees.

The compatibility rule is the same one that governs the rest of the phase, applied at the last mile: a
POS screen that has never been told which terminal it is shows the whole menu. So does a terminal whose
scope is empty. Every installation of this product is in the first state right now, and a version of
this plan that greets an existing tenant with an empty menu grid is a worse product than the one before
the phase. Both defaults are behaviours with their own tests, not fallback branches.

The terminal identity is stored in the IndexedDB meta store, which already exists in the offline module
and currently has no writer. It is a device preference — which till this iPad is — and it is not
authentication. The server independently validates that any terminal id it receives belongs to the
caller's branch, so a tampered local value produces a refused order rather than a misattributed one.

Purpose: this makes the fourth item of the definition of done true.
Output: a terminal picker, a scoped menu grid, and terminal-attributed orders.
</objective>
