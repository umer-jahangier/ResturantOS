<amendments date="2026-08-12" authorized-by="coordinator">
**Add roster reconciliation.** A periodic comparison of the cloud's roster for a device against the
roster the device actually holds, via `DATA QUERY USERINFO` through 25-07's command queue.

Why it belongs here rather than in 25-07: this plan already owns the sweep, and reconciliation is the
same failure family as silence. A terminal that is factory-reset, swapped under warranty, or replaced
after a failure **silently knows nobody** — it handshakes, it reports healthy, its last-seen advances,
and every punch it sends quarantines. The first signal anyone gets today is a month-end pile of
unattributed punches, which is the D-25-02 failure with a different symptom.

In a cloud deployment this is the only way it is detectable at all: the platform never sees the device
except through the device's own polls, so "what do you actually have" has to be asked.

Required behaviour:
- A device whose roster is missing employees the cloud expects is surfaced with the count and the
  names, not merely flagged.
- A device holding references the cloud does not know about is surfaced too — that is a leaver who was
  never removed, or a terminal that was moved between branches without being re-provisioned.
- Reconciliation queues its own repair commands rather than requiring a human to re-enrol by hand, and
  a repair that is a REMOVAL follows 25-07's amended revocation rules (retry until acknowledged, never
  expire).
</amendments>

<objective>
Make silence loud.

`last_seen_at` is written on every authenticated device request and read by nothing. A terminal that
stops pushing is invisible until somebody notices missing attendance — and on a payroll cycle that
means month-end, by which point the missing days are a dispute with an employee rather than a
maintenance ticket. D-25-02 names the failure family precisely: this is the audit log sitting at zero
rows for four days while everything looked healthy. The column existed then too.

There is a second, quieter version of the same problem. The device stamps the punch and its clock is
the only clock the protocol has; a terminal drifting by twenty minutes puts punches in the wrong shift
window and corrupts every late-arrival calculation downstream. The schema already stores both what
the device said and when the server received it, precisely so drift is measurable — and nothing
measures it.

Both are the same shape: the data to notice is already being written, and nothing reads it. This plan
is the reader.

Purpose: D-25-02, and the half of the clock-skew problem that is solvable without touching a device.
Output: a health computation, a cross-tenant sweep that announces transitions once and escalates a
bounded number of times, and drift visible per device.
</objective>

<hardware_signoff>
**Requires U5 for one number, not for the mechanism.** Everything here — detection, escalation,
recovery, replica safety, drift computation — is proven with an injected clock and the simulator.

week, which sets a sensible default for the skew threshold, and the real contact cadence a firmware
keeps, which sets a sensible default for the expected interval. Both are defaults on a column, so a
wrong guess is a row update rather than a code change. That distinction goes on 30-13's list.
