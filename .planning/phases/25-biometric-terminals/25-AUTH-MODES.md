# D-25-06 — How a physical ZKTeco terminal authenticates

**Decided 2026-08-11. Chosen: `both` — build the credential-policy seam and both alternative modes,
selectable per device, with one constraint added beyond what the plan proposed.**

---

## The problem, stated once

The ADMS/iClock ingest in hr-service authenticates a device by a token in the query string:
`/iclock/cdata?SN=...&token=...`. That works, it is constant-time compared, and it is the posture
D-25-06 says not to weaken.

A stock ZKTeco terminal cannot use it. Its configuration menu (COMM → Cloud Server) offers exactly
Enable, Domain Name, Server Address, Server Port and proxy settings. **The request path and its
entire query string are generated by firmware.** There is no field for a token, no documented ADMS
parameter carrying a per-device secret, and no header. The one authentication-adjacent concept in
the ZKTeco ecosystem — the communication key — belongs to the separate binary pull protocol, not to
this one.

So the accurate description of the state before this phase is not "the protocol is done, the
management is missing". It is: **the protocol is done for a client we write ourselves, and no stock
terminal can walk it.** The USB bridge agent can hold a token because it is our code. A terminal
cannot.

Verified live on 2026-08-11, the exact boot request a terminal sends:

```
GET /iclock/cdata?SN=UNKNOWN-DEVICE-999&options=all&pushver=2.4.0  ->  401 DEVICE_AUTH_FAILED
```

(That request returned **500 INTERNAL_ERROR** until commit `174f24f` earlier the same day — a
separate defect, fixed, and worth noting here because it is why this was not caught sooner: a
terminal that gets a 500 looks like a server problem, and a terminal that gets a 401 looks like an
enrolment problem. Only the second one sends anyone to read this document.)

## What was chosen

**`both`** — the policy seam plus `host-mapped` and `serial-only-bounded`, chosen per device, with
`token` remaining the default and remaining untouched.

### Why not pick one

The two alternatives fail in opposite deployments, and both deployments are real customers:

- `host-mapped` needs a DNS name and a certificate per branch. It is the strongest option and it is
  unavailable to exactly the customer most likely to own a biometric terminal — a single restaurant
  on a domestic connection, which is what Floating Terrace F-7 is.
- `serial-only-bounded` works with any firmware and needs nothing but an address and a port. It is
  what most commercial ADMS servers do, including the products this integration is compared against.
  It is also the weaker of the two, and it degrades badly on a dynamic address.

A chain with a static IP per branch and an ops team should get `host-mapped`. A single restaurant
should get `serial-only-bounded`. Choosing one for a customer nobody has met is choosing wrong for
half of them, and the marginal cost of the second mode, once the policy seam exists at all, is small
— the seam is the work; the modes are a switch on it.

### Why not `bridge-only`

The bridge agent binary does not exist in this repository — only its wire contract does. Requiring
it means an on-premise process per branch, which is the largest operational commitment of the three,
and it forfeits the network terminal's chief advantage: it dials out, needs no inbound firewall
rule, and needs nothing installed. Rejecting a whole hardware integration to avoid writing down a
trade-off is not a security decision, it is a deferral.

## The added constraint (beyond the plan's four)

**A device refused for a source-address mismatch MUST record the observed source address on its own
row, and the device screen MUST show it with a one-click "allow this address".**

The stated failure mode of `serial-only-bounded` is "a branch with a dynamic address needs its
allowlist maintained, and a wrong allowlist is a silently offline terminal". Silently is the whole
problem. A restaurant on a domestic Pakistani connection *will* have its public address change, and
without this the symptom is "the clock stopped working" with nothing in the product that says why —
a support call, on a weekend, about attendance data nobody can reconstruct.

Recording the observed address turns that into a visible, self-service fix. 30-04's failure recorder
already exists; this is a column and a button on a screen this phase is already building.

The information-disclosure objection is real and small: someone who knows a serial can write their
own IP address into an admin's device screen. They cannot read anything, cannot authenticate, and
the address they inject is their own. Against a support burden that would otherwise land on every
dynamic-IP customer, that trades correctly. It is bounded by rate limiting, which 25-08 gives its
own per-tenant bucket in the same plan.

## Constraints carried unchanged from the plan (non-negotiable)

1. **No existing device changes mode by migration, default, or as a side effect of registration.** A
   device authenticating with a token today keeps doing so until a person decides otherwise and the
   decision is audited.
2. **A mode that presents no secret cannot be selected without a non-empty source-address
   restriction.** Serials are globally unique and the resolver looks up by serial alone; serial-only
   with no network bound means anyone who learns a serial can post punches into that tenant's
   payroll. Empty allowlist fails closed, checked before anything else.
3. **Changing a device's mode is an audited act**, with actor, before-value and after-value.
4. **The existing resolver is untouched**: constant-time comparison, active check, resolve-then-bind
   ordering, and the clearing of tenant context in a `finally` block all stay exactly as they are.
   This adds modes beside that path; it does not restructure it.
5. **Every refusal is indistinguishable.** Same status, same body, same refusal code, whatever the
   mode and whatever the cause — asserted by comparing responses, not by reading them.

## Residual risk, in one paragraph

A `serial-only-bounded` device is trusted on two facts an attacker can obtain: a serial number,
which is printed on the device and appears in support tickets and photographs, and a source address,
which is the restaurant's public IP. An attacker on the same NAT — a guest on the restaurant's
wifi — can therefore post fabricated punches for that branch, and the ceiling on the damage is
payroll fraud bounded by whatever the attendance-to-payroll review catches. This is materially
weaker than `token` or `host-mapped` and it is the mode most customers will run. It is accepted
because the alternative is not a stronger deployment, it is no deployment: the customer buys a
different ADMS server, one that made the same trade without writing it down. What makes it
defensible rather than negligent is that it is per-device, opt-in, audited, bounded at the network,
never a default, never applied by migration, and visible on the device screen as a weaker mode.

## What an installer is told

**Token mode (default — bridge agent, or firmware that permits a query string).** Register the
device in HR → Attendance Devices. The registration response gives the full server address and the
device token. Configure the bridge agent with both.

**Serial-only, address-bounded (most single-restaurant terminals).** Register the device, choose
"Serial + network address", and enter the branch's public IP address or CIDR — the allowlist cannot
be left empty. On the terminal: **COMM → Cloud Server → Enable = ON**, Server Address = the address
shown on the registration screen, Server Port = the port shown. Nothing else. If the terminal shows
as refused, open its device screen: the address it is actually dialing from is displayed there, and
"allow this address" adds it. If the restaurant's internet connection changes address regularly, ask
the ISP for a static IP — it is a small monthly cost and it removes this class of problem entirely.

**Host-mapped (chains with per-branch DNS).** Register the device, choose "Hostname", and enter the
branch hostname. On the terminal, put that hostname in **Domain Name** and leave Server Address
empty. Requires the hostname to resolve to the platform and to be covered by the certificate.

*Decision made by Claude on 2026-08-11 under the user's standing instruction to proceed
autonomously. It is reversible per device and changes nothing about any device already registered.
If the intended first deployment is a chain with static addressing rather than a single restaurant,
say so and `serial-only-bounded` can be left unoffered — the seam supports withdrawing a mode
without touching the resolver.*
