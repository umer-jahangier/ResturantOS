<objective>
Build the thing that makes this phase testable: a program that is, on the wire, a ZKTeco terminal.

D-25-04 is the load-bearing decision of the phase. An ADMS device is an HTTP client sending plain
text — no binary framing, no TLS client certificate, no handshake secret. Everything except what
firmware does with our responses can therefore be settled today, on a laptop, for free. Research
searched and found no existing ZKTeco *device* simulator: every open-source project in this space is
a server. That is fine, because the device side is small.

The instruction that governs this plan is the negative one. Do not defer to hardware what a simulator
can answer. Phase 26's plan-checker caught two questions filed as printer-dependent that an emulator
answered in an afternoon, and each would have parked real work behind a purchase for no reason. When
in doubt about whether a question needs U5, the answer is to write the scenario and find out.

Purpose: every plan from 30-04 onward asserts against this, and 30-12 proves the phase with it.
Output: a standard-library Python simulator, a named scenario library, its own wire-fidelity test,
and the phase's shell harness.
</objective>

  <action>
    Create `scripts/adms-sim/adms_device_sim.py`, standard library only — `argparse`, `urllib.request`,
    `http.client`, `datetime`, `json`, `random`, `time`. No third-party import appears anywhere in
    this directory, and nothing is added to any manifest.

    Model one device as a class holding a base URL, a serial, an optional token and a device
    timezone offset. Give it four methods, one per protocol verb.

    The handshake issues a GET to the attendance-data path carrying the query parameters a real unit
    sends — the options flag, the push version, the language code, and optionally the device-type and
    push-options flags seen in one of the two captured examples. Whether the token query parameter is
    included is a flag, defaulting to **excluded**, because excluded is what a stock terminal does and
    the default should be the truth about hardware rather than the thing that makes our server happy.
    Parse the response body into a dictionary of the configuration keys and expose it, so a caller can
    assert on the realtime and transfer settings rather than eyeballing a string.

    The upload issues a POST to the same path with the table parameter set to the attendance table
    and a body of one record per line. Build each line by joining fields with a real tab character and
    terminate lines with a real newline; encode to bytes once, at the end. Take the Content-Type as a
    parameter with three permitted values — plain text, form encoding, and omitted entirely — because
    firmware varies and one of those three is a silent-data-loss branch in the current server.

    The poll issues a GET to the command path and returns the raw body verbatim, uninterpreted. The
    acknowledgement issues a POST to the command-result path with the documented key-and-ampersand
    body form, one command per line, taking the return code as a parameter so the documented failure
    codes can be exercised and not only the success code.

    Every method returns a small result record: status, headers, body and elapsed time. Nothing prints
    from inside the class; printing belongs to the caller, so the class is usable from a test.

    Refuse to run against anything but loopback unless an explicit acknowledgement flag is passed, and
    make the refusal message say why: this program fabricates attendance punches, and attendance
    punches become wages. Require the serial and token as arguments with no defaults.

    Emit, on request, a machine-readable summary object to standard output — counts by status, rows
    claimed sent, and per-request timings — so a shell script can assert on it without parsing prose.

    Write the README alongside. It has four sections: what this is, how to run it, the scenario list
    (populated by task 2), and a **Limits** section stating precisely what this program cannot settle:
    which transfer-flag encoding a given firmware honours, whether a firmware tolerates a zero-length
    command response, what Content-Type a given firmware actually sends, whether a model requires the
    registry or test endpoints this server does not implement, whether any firmware field can carry a
    per-device secret, and the real field count and ordering a specific model emits. That list is the
    seed of the hardware sign-off in 30-12, and it must contain nothing a scenario could answer.
  </action>

  <action>
    Create `scripts/adms-sim/scenarios.py`: a registry of named scenarios, each a function taking a
    configured device and returning a result summary. Each carries a one-line docstring stating **the
    question it answers**, not what it does — a scenario whose docstring describes its mechanics is a
    scenario nobody will know when to run.

    Implement at least these, and add any the executor finds while working:

    *Boot as a stock terminal.* Handshake with no token, exactly the query string firmware sends.
    Answers: can a device fresh out of its box reach us at all?

    *Happy punch.* One mapped reference, plain text, seven fields. Answers: does the ordinary case work?

    *Replayed batch.* Send an identical multi-record body twice, then a third time after a delay.
    Answers D-25-05: does a device that buffered through a network blip double-count anyone?

    *Out-of-order arrival.* Send a batch whose records descend in time, then an earlier punch after a
    later one. Answers: does ordering affect what is stored?

    *Drifted clock.* Offset the device clock forward and backward by a configurable number of minutes.
    Answers: is drift measurable after the fact from the two stored timestamps, and is a punch stamped
    in the future distinguishable from one stamped in the past?

    *Unknown reference.* A device user reference mapped to no employee. Answers D-25-03: is the punch
    retained and surfaced, or lost?

    *Malformed and short lines.* Bodies with two, three and four fields; an empty line; a line of
    whitespace; a line whose timestamp is a Unix epoch integer; a line whose timestamp is unparseable.
    Answers: which of these silently vanish? Each is a potential unpaid hour, so the scenario reports
    per-line outcomes rather than one aggregate.

    *Content-Type sweep.* The same body under plain text, form encoding, and no Content-Type header.
    Answers: does a header the device chooses decide whether an employee gets paid?

    *Offline flush.* Accumulate records locally for a configurable window, then send them as one
    batch, then repeat the batch. Answers: does the real reconnection shape behave like the synthetic
    replay?

    *Command poll loop.* Poll at the documented three-to-eight second cadence for a configurable
    duration, acknowledging anything returned, including with the documented failure return codes.
    Answers: does an idle device get a well-formed response, and does an acknowledged command settle?

    *Rate-limit probe.* Fire a burst above the configured per-device budget through the gateway.
    Answers: does the per-device limit bind on the device path, and does it bind per device rather
    than globally? Run it with two distinct serials to tell those apart.

    *Multi-device soak.* K devices, each on its own thread, for N minutes, mixing mapped and unmapped
    references. Answers: does anything cross tenants or devices under concurrency, and does the
    context-clearing on pooled threads hold?

    Give the entry point a `--scenario` flag, a `--list` that prints each name with its question, and
    a non-zero exit on any scenario whose own expectation was not met. Update the README's scenario
    section from the registry rather than by hand, or the two will drift.
  </action>
