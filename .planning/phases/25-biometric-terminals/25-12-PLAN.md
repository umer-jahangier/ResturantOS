<amendments date="2026-08-12" authorized-by="coordinator">
**Name the two halves of "enrolment" separately, in the UI copy itself.**

A fingerprint template is captured **at the terminal**, by a person putting a finger on a sensor. It
cannot be enrolled from a browser, and no ADMS command substitutes for it. The honest flow is:

> create the employee in the cloud → the terminal learns the PIN via `DATA UPDATE USERINFO`
> → **someone walks to the device and enrols the finger** → the template syncs back

This screen must say which half it is doing. A screen that shows an employee as "enrolled" when only
the PIN has been pushed implies the biometric half happened, and the user discovers otherwise when the
employee stands at the terminal and it does not know them — **a support ticket per employee**, at the
worst possible moment, on their first shift.

Use two distinct words in the interface, not one word with a tooltip.
</amendments>

<objective>
Make the mapping a place rather than a side effect.

The device knows a number and the platform knows an employee, and the bridge between them is a
durable reference stored on the employee record. That design is the strongest part of this
integration: resolution is a stored mapping rather than a per-punch heuristic, an unmapped reference
is parked with its raw line rather than dropped, resolving one re-ingests the parked punch and makes
every subsequent punch for that reference resolve itself, and re-pointing a reference at a second
employee is refused.

What it does not have is a surface. The mapping is a text field on the employee form. The queue is a
four-column table at the bottom of the attendance screen with a dropdown, showing the device
reference and nothing about the device. After 30-06 the queue also holds a second kind of entry — a
line the parser could not interpret — which that table has no column for and no action for.

D-25-03 asks for a real screen with an unmapped-punch queue an administrator can resolve, and it says
why in one sentence: a dropped punch is an unpaid hour. This is the screen.

Purpose: D-25-03's manageable half, and the visibility that keeps the queue from quietly growing.
Output: the mapping and queue layers, one screen that owns both, and one place in the product where
unattributed punches live.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| an unauthenticated device to an administrator's screen | The raw line is attacker-controlled text rendered to a privileged user |
| an administrator to attendance | Resolving creates paid time; dismissing destroys a claim to it |
| one branch's administrator to another's queue | The queue is where a cross-branch resolution would be attempted |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-12-A | Elevation of Privilege | Markup in a raw line executing in an administrator's session | critical | mitigate | The line renders as text through a component with no markup-interpreting path, asserted by a test whose fixture contains markup and whose expectation is literal characters |
| T-30-12-B | Repudiation | Attendance dismissed with no reason and no name | high | mitigate | A typed reason is required with no prefilled suggestion, the confirmation states the consequence, and the server records the acting user |
| T-30-12-C | Tampering | A morning's attendance deleted in one bulk action | high | mitigate | Bulk resolution exists; bulk dismissal does not exist anywhere in the interface |
| T-30-12-D | Tampering | A client-side default becoming the guess the server refused to make | high | mitigate | The interpretation form prefills nothing; the refusal-to-guess lives in the service and the screen does not route around it |
