<objective>
Give D-25-01 a place a person can stand.

There is no device screen. A repository-wide search for the device endpoint across the frontend
returns nothing: registration, listing and deletion are API-only, so today a restaurant owner who
buys a terminal must be handed a curl command. Meanwhile the ADMS integration underneath is
substantially complete, which is the worst combination — a working feature nobody can reach.

The screen has one job beyond the obvious CRUD, and it is D-25-02's. A terminal that stopped talking
three days ago is a payroll problem discovered at month-end, and a screen that reports it correctly to
somebody who opens the screen has not solved that, because the whole problem is that nobody opened
the screen. So the count of unhealthy terminals travels with the HR navigation, and the screen sorts
the quiet ones to the top and says how long in words a person thinks in.

Purpose: D-25-01 in full and D-25-02's visibility half.
Output: the four frontend layers for devices, a terminals screen, and a badge that makes silence
audible from three tabs away.
</objective>

  <behavior>
    - The device list schema parses a response carrying health, last contact, drift and configuration, and rejects one missing a required envelope field.
    - The list schema rejects any response containing a token field. A list that carried one would be a server defect, and the client refusing it is how that defect is found in a test rather than in a screenshot.
    - The registration and rotation schemas accept exactly one token field and the adapter surfaces it as a value that exists only in the mutation result, never in any cached query.
    - The adapter maps every field; a test enumerates the domain model's keys and asserts none is undefined after adapting a full fixture, so a silently dropped field fails the build.
    - A drift measurement that is absent adapts to null, distinct from a drift of zero, and the model's type makes the two impossible to confuse.
    - Every mutation hook invalidates the device keys and the health summary key, so an action that changes health does not leave a stale badge.
  </behavior>
  <action>

    reasons: 30-12 adds the mapping screen in the next wave and a shared file would serialise them for
    no reason, and the device surface is large enough that folding it into the general HR repository
    would make that file the biggest in the layer.

    Extend the shared query-key registry with a device namespace and a health-summary key. Do not add
    a local key array; the registry exists because local arrays drift.

    Write the token refusals into the schema deliberately. The list must reject a token field, and the
    two minting responses must carry exactly one. This is the client half of a server guarantee, and
    it is worth duplicating because the consequence of the server ever leaking a token into a list is

    has shipped before.

    **The list.** One row per terminal, sorted so anything not healthy is at the top. Each row shows
    the name, the branch, the model and serial, the connection and authentication mode, and the health
    state. Show last contact as a duration a person thinks in — three days ago, eleven minutes ago —
    with the exact instant available in the row without navigating away. A column of raw timestamps is
    how a Tuesday goes unnoticed until month-end, which is the failure this screen exists to prevent.
    Show drift where it is measured, and where it is not, say so rather than showing a zero.

    navigation. State in text, not only in colour: an icon plus a word. Somebody scanning this screen
    at speed and somebody who cannot distinguish the colours are the same person as far as this
    requirement is concerned.

    itself, fed by the branch health summary, so a person working in Payroll sees it. Suppress it at
    zero — a badge that is always present is furniture.

    authentication mode. On success, a panel showing the token once, the exact Server Address and
    Server Port strings to type into the terminal, and the mode-specific instructions the API returned.
    Say plainly that the token will not be shown again. Give it a copy affordance for each field —
    somebody is retyping these on a keypad in a stockroom.

    **The actions.** Rename inline. Reassign branch. Enable and disable. Rotate. Archive. Edit the
    sync configuration — timezone, expected contact interval, skew threshold and the handshake values —
    because that is the concrete meaning of the terminals auto-syncing with the app. A named
    sync-now action queueing an allowlisted command. Never a free-text command field.

    Guard every mutating action by the manage permission, following the house pattern, so a viewer
    sees state without controls rather than controls that fail.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the browser to a minted device token | The one-time panel holds a credential that authenticates a device for its lifetime |
| a viewer to another branch's terminals | The list is the surface where an isolation failure becomes visible |
| the screen to the command queue | A person's click becomes an instruction executed by a device |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-11-A | Information Disclosure | A device token in a URL, storage or a cached query | critical | mitigate | The token exists only in a mutation result rendered once; the list schema rejects a token field outright; no token enters a route, a query string or browser storage |
| T-30-11-B | Elevation of Privilege | A free-text command field reaching a terminal | critical | mitigate | The screen offers named actions only; the closed set lives on the server and the client has no way to widen it |
| T-30-11-C | Elevation of Privilege | Acting on another branch's terminal | high | mitigate | Enforced server-side by 30-09; the screen's checkpoint verifies it is neither visible nor actionable, which is where a regression would first show |
| T-30-11-D | Repudiation | Silence visible only to somebody already looking | high | mitigate | The count travels on the HR navigation, suppressed at zero, and the checkpoint verifies it from a different screen |
| T-30-11-E | Tampering | A rotation performed without understanding its cost | medium | mitigate | The confirmation states that the terminal stops working until the credential is retyped and that the value is shown once |
| T-30-11-F | Information Disclosure | Health conveyed by colour alone | medium | mitigate | The badge renders an icon and a word; asserted in the acceptance criteria and checked by a human |
| T-30-11-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan adds no package to any manifest. If a component genuinely requires one, halt and require the package-legitimacy audit plus a blocking human checkpoint |
