<objective>
Prove the phase against the running product, and write down exactly what is left for the terminal.

30-CONTEXT states six definition-of-done items. This plan produces the commands and the browser
journey that demonstrate each, and it adds a seventh that the definition of done does not contain and
the user's own sentence requires: that a terminal configured with nothing but a server address and a
port can authenticate and deliver a punch. A phase can satisfy all six items and still ship a device
nobody can connect, and that gap is worth stating in the artefact rather than discovering later.

It also produces the hardware list. D-25-04 requires that the items genuinely needing U5 be listed
explicitly rather than left implied, and that nothing appear on it which a simulator can settle. Each
earlier plan wrote its own hardware section, several of which say "nothing", and two of which record
questions this phase deliberately removed by building so the answer no longer changes the outcome.
This plan consolidates all of it into one document somebody can take to a supplier.

Purpose: definition-of-done items one through six, the seventh the user asked for, and D-25-04's
explicit-list requirement.
Output: a live end-to-end script, a browser journey, and `HARDWARE-SIGNOFF.md`.
</objective>

  <action>
    Create `phase30-biometric-e2e.sh` sourcing this phase's harness, one labelled section per item,
    each printing pass or fail, exiting non-zero on any failure.

    **Item one — an administrator manages a terminal without SQL.** Through the gateway, register a
    terminal with a name, rename it, reassign its branch, disable it and assert a punch is refused,
    re-enable it and assert a punch is accepted, rotate its token and assert the old token is refused
    and the new one works, then archive it and assert it is refused and its punches remain
    attributable. Every one of those is an operation that did not exist before this phase; assert each
    rather than assuming the group.

    **Item two — simulated punches become attendance for the right employee.** Register a device and an
    employee with a known device user reference. Run the happy-punch scenario. Read the attendance API
    for that employee and assert the punch is there, that the device-reported instant equals what the
    simulator sent, and that the server-received instant is a different, later value. Never assert
    either against a literal.

    **Item three — last contact is visible and silence is surfaced.** Assert the device's last contact
    through the API after a punch. Then set that device's expected interval to something short, stop
    sending, trigger the sweep, and assert three things: the health state changed, the branch summary
    count rose, and a silence event was published. Read the event from wherever the audit trail records
    it, so this proves somebody would have been told rather than proving a column changed. Then send a
    punch and assert the recovery announcement, because a fault with no all-clear is a fault people
    learn to ignore.

    **Item four — an unmapped reference is resolvable and never dropped.** Run the unknown-reference
    scenario. Assert no punch exists and one queue entry does, carrying the raw line the simulator
    sent, compared against what the simulator reported sending. Resolve it through the API, assert a
    punch now exists, then send the same reference again and assert it becomes a punch with no new
    queue entry. Then run the malformed-lines scenario and assert every line it sent is accounted for
    as a punch or a queue entry — the sum, not the cases.

    **Item five — a replayed batch does not double-count.** Run the replayed-batch and offline-flush
    scenarios. Capture punch count, queue count and event count before and after each replay and assert
    they are unchanged after the first delivery. This is D-25-05 and it is the assertion most likely to
    be quietly weakened later; express it as a comparison between two readings taken in the run.

    **Item six — the hardware list.** Print `HARDWARE-SIGNOFF.md` at the end of the run so the list
    travels with the evidence.

    **Item seven — a stock terminal can actually connect.** Run the boot-as-a-stock-terminal scenario
    against a device configured for whichever authentication mode 30-08's checkpoint selected, using
    only the address and port the registration response handed back. Assert the handshake returns the
    configuration block, then deliver a punch and assert it becomes attendance. Then assert the
    negative: the same request from outside the device's source restriction, or with the wrong host, is
    refused, and refused with the same body as every other refusal. This section is not in
    30-CONTEXT's definition of done. It is in the user's sentence, and its absence from the definition
    of done is worth recording in the summary.

    Every assertion reads both sides in the same run. No literal counts, references or instants
    anywhere in the script.

    If the stack, the simulator or the sweep cannot be driven, report the affected assertions as
    skipped with the reason and exit with a status distinct from a clean pass, so a pass with skips is
    never mistaken for a pass.

    Archive every device the run registered in the teardown, and never write a token to a file.
  </action>
