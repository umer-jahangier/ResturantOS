<objective>
Turn a stub into a mechanism, and close the seam before anything can reach through it.

Three separate things sit behind the command poll. The first is small: the queue returns a zero-length
body when empty, where the Go reference implementation probed against real hardware and the PHP
package both return the two-character acknowledgement. Whether firmware tolerates a zero-length 200
is unverified and returning the acknowledgement costs nothing, so this is a free reduction in the
number of things a physical terminal has to settle.

The second is what the user actually asked for. "Auto-sync the terminals with the app" is, on this
protocol, the handshake block: realtime push, poll delay, retry delay, transfer window, transfer
interval and transfer flag. Those nine lines are currently a string literal inside a controller
method, identical for every device in every tenant. 30-03 gave each device its own values; this plan
makes the handshake read them, which is the difference between a setting and a decoration.

The third is a security seam that must be closed now rather than when something reaches through it.
The ADMS command set includes running an arbitrary shell command on the terminal's Linux operating
system and returning its output. `DeviceCommandQueueService` is a stub today, so nothing can queue
anything — but the moment a queueing API exists, a free-text command field is remote code execution
on a device sitting in a restaurant. The allowlist is built here, in the plan that builds the queue,
and the API that uses it is built in a later plan by a different pass. That ordering is deliberate.

Purpose: the handshake is where sync configuration becomes real, and the queue is where enrolment
becomes possible — which is the only way a new hire's first punch stops being a queue entry.
Output: a durable command queue with a closed command set, a per-device handshake, and one less
question for the hardware list.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the platform to a terminal's operating system | A queued command is executed by a Linux device in a restaurant |
| an unauthenticated device to the queue | A poll and an acknowledgement both arrive on the public device path |
| one tenant's queue to another's device | Commands are addressed by serial, which is globally unique |

<hardware_signoff>
**Requires U5 — two genuine items, and one this plan removes.**

Removed: whether firmware tolerates a zero-length command response no longer matters, because the
queue now returns what two independent implementations return. It moves to the answered-by-design
list.

Genuine: **which transfer-flag encoding the target firmware honours** — a bitmask string and a word
list are both observed in the wild, and a wrong value produces a terminal that connects and then
uploads nothing, which is the worst failure shape available here because it looks like success. And
**whether the target firmware accepts the data-update enrolment form** — research states real firmware
rejects the naive add-user form with a syntax error and accepts the data-update form, but that is one
model on one firmware version. The simulator proves our queue, our rendering, our acknowledgement
handling and our expiry; it cannot prove a device's parser. Both go on 30-13's list.
</hardware_signoff>
