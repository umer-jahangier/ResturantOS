<objective>
Answer the question this phase cannot ship without, and record the answer as a decision rather than
as an accident.

30-CONTEXT says the protocol work is largely done and the gap is management, sync and visibility.
That is true of everything except one thing, and the exception is decisive: **the token this
implementation requires is a query parameter, and a stock ZKTeco terminal has no field to type it
into.** Its configuration menu offers Enable, Domain Name, Server Address, Server Port and proxy
settings; the request path and its query string are generated by firmware. Research searched for any
documented ADMS parameter or header carrying a per-device secret and found none — the one
authentication-adjacent concept in the ecosystem, the communication key, belongs to the separate
binary pull protocol, not to this one.

So the current state is not "the protocol is done and the management is missing". It is: the protocol
is done for a client we write ourselves — which the USB bridge agent is — and no stock terminal can
walk it. Verified live on 2026-08-11: the exact boot request a terminal sends is refused.

Research offers three ways out and is explicit that the choice depends on the customer's network
topology, which is not a thing a planner can decide. This plan therefore implements the seam and all
three modes, defaults nothing, changes no existing device, and puts the choice in front of a human
before the modes can be selected in the product.

Purpose: D-25-06 says do not weaken the device authentication path. The only way to honour that while
also letting a real terminal connect is to make each weakening explicit, bounded, audited and chosen.
Output: a credential policy, an honest feature gate, a usable registration response, and a written
decision.
</objective>

  <name>Task 1: Choose how a stock terminal authenticates (D-25-06)</name>
  <decision>
    Which device authentication modes may a tenant select, and under what constraints? The product
    keeps the existing token-in-query mode for the bridge agent and for any firmware that permits a
    query string. The question is which of the two alternatives — host-mapped or serial-only with a
    network bound — is built, offered and supported.
  </decision>
  <context>
    A stock ZKTeco terminal can be given a server address and a port, and nothing else. There is no
    documented way to make it present a per-device secret over this protocol. Until one of these is
    chosen and built, a physical terminal cannot connect at all, and the rest of this phase manages
    devices that can never talk. Research §3.1 lists the options in order of how much of the current
    security posture they preserve, and states the choice depends on the customer's network topology.

    This is also the item 30-CONTEXT does not lock. Its locked decisions cover management, health,
    mapping, testing, idempotency and not weakening the auth path — but a phase that honours all six
    and ships a device nobody can connect satisfies its definition of done and not the user's sentence.
  </context>
  <options>
    <option id="host-mapped">
      <name>Host-mapped secret — one hostname per branch, resolved to a device secret at the edge</name>
      <pros>Preserves the current posture: every device still authenticates against a per-device secret, the resolver is unchanged, and a leaked serial is worth nothing on its own. The device's Domain Name field is a typeable place to put a per-branch hostname.</pros>
      <cons>Needs a DNS name and a certificate per branch, or a wildcard certificate plus per-branch subdomains. Operationally heavier at onboarding, and it fails in exactly the deployments most likely to have a biometric terminal — a single restaurant behind a domestic connection.</cons>
    </option>
    <option id="serial-only-bounded">
      <name>Serial-only trust, bounded by a mandatory source-address restriction per device</name>
      <pros>What most commercial ADMS servers do, including the products this integration would be compared against; works with any firmware; nothing to type beyond an address and a port. The bound makes it a stated trade rather than an open door.</pros>
      <cons>Anyone who learns a serial and can reach the endpoint from an allowed address can post punches for that tenant. A branch with a dynamic address needs its allowlist maintained, and a wrong allowlist is a silently offline terminal.</cons>
    </option>
    <option id="bridge-only">
      <name>Neither — every terminal goes through the USB bridge agent, which can hold a token because we write it</name>
      <pros>No protocol concession at all, and the device path keeps exactly the posture it has today.</pros>
      <cons>The bridge agent binary does not exist in this repository — only its wire contract does. It is an on-premise process per branch, which is the largest operational commitment of the three, and it makes a network terminal's chief advantage (dials out, needs no inbound rule, needs nothing installed) unavailable.</cons>
    </option>
    <option id="both">
      <name>Build the seam and both alternatives; let a tenant choose per device</name>
      <pros>The topology varies by customer, so the choice varies by customer. The cost over building one is small once the policy seam exists, and it removes the risk of choosing wrong for a customer nobody has met.</pros>
      <cons>Two modes to document, support and test; two ways for an installation to be misconfigured; a larger surface for the review this plan's checkpoint exists to give.</cons>
    </option>
  </options>
  <action>
    Present the four options with the evidence above. State plainly that this is a decision 30-CONTEXT
    did not lock and that the phase's definition of done can be met without it while the user's actual
    request cannot.

    Whatever is chosen, the constraints are not negotiable and must be restated when presenting: no
    existing device changes mode by migration or default; a mode with no secret requires a non-empty
    source-address restriction; changing a device's mode is audited; and the constant-time comparison,
    the ordering and the context clearing in the existing resolver are untouched.

    Record the outcome in `.planning/phases/25-biometric-terminals/25-AUTH-MODES.md`: what was chosen,
    what was rejected and why, what the residual risk is in one paragraph, and what an installer is
    told to do. That document is the artefact D-25-06 implies — a weakening of a public credential
    path needs a written trade, not an inferred one.
  </action>
  <verify>
    <human-check>The developer has chosen a mode set, and 25-AUTH-MODES.md records the choice, the rejected options, the residual risk and the installer instructions.</human-check>
  </verify>
  <done>The one question that blocks a physical terminal from ever connecting has an answer with a name on it.</done>

    whether this request may act as this device. One method, one closed set of modes, one refusal type.

    structure byte-for-byte: resolve by serial through the definer-context function, check active,
    then policy, then and only then bind tenant context and set the transaction-local GUC, then write
    last-seen. The ordering is the control; the policy is a substitution inside it, not a rewrite
    around it.

    Implement only the modes task 1 chose. For any mode without a secret, treat an empty restriction as

    allowlist that silently matches a load balancer's address allows everyone.

<hardware_signoff>
**Requires U5 — the decisive item on the whole list.** Whether any firmware field can carry a
per-device secret is the question that determines whether the token mode is ever usable by a stock
terminal, and no simulator can answer it: it is a property of a configuration menu, not of the
protocol. Research read a manual and three integrator guides and found only address, port, domain and
proxy fields.

That is why this plan builds a policy seam rather than a single mode. If a physical unit turns out to
offer a field that carries a secret, that becomes a fourth mode and every device can move to it; if it
does not, the decision made at task 1 stands and nothing built here is wasted. The item goes to 30-13
as the highest-value question to put to a real terminal.
</hardware_signoff>
