<objective>
Establish what is actually broken in purchasing and inventory by driving the whole procure-to-pay
chain with real data through the live stack (D-31-01), and record where it breaks with evidence a
sceptic can re-run.

This is deliberately the first plan and deliberately fixes nothing. Eight defects in this project
were green in tests and broken in reality; phase 22 found the ninth — a four-day-old jar that made
"we fixed it" false everywhere — by driving money, not by reading code. Plans 31-02 through 31-06
each repair one locked decision, and each of them reads its inbox out of this plan's findings
document.

Purpose: nothing else in this phase is trustworthy if it is planned against an inferred defect.
Output: a reusable live-drive harness and a findings register naming every break, its evidence and
the decision it belongs to.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| harness to gateway | The drive authenticates as real personas and exercises real write endpoints against a shared stack |
| harness to purchasing_db / inventory_db | Assertions read tenant-scoped rows under FORCE row-level security |
| harness to the broker | Queue depths are read from the management API with operator credentials |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-31-01-A | Information Disclosure | Service-role SQL helpers | critical | mitigate | Every helper connects as the owning service role and refuses a superuser role, so an assertion cannot pass by bypassing the policy under test |
| T-31-01-B | Information Disclosure | Persona credentials and tokens in logs | high | mitigate | The drive log records status codes, error codes and row values only; tokens are held in shell variables and never echoed, matching the phase 13 harness contract |
| T-31-01-C | Tampering | Writes against a shared live stack | medium | accept | The drive creates tenant-scoped procurement data in the demo tenant only, using idempotent markers as the seed does; no destructive statement is issued and nothing is deleted |
| T-31-01-D | Repudiation | A result produced by a stale process | critical | mitigate | The freshness gate compares open jar inodes against on-disk inodes and abandons the run when any relevant service is stale |
| T-31-01-E | Elevation of Privilege | Deliberate probes with an unknown ingredient id | low | mitigate | The probe uses a generated identifier inside the caller's own tenant; it tests referential validity, never another tenant's data |
| T-31-01-F | Spoofing | Assertions made against a service port rather than the gateway | high | mitigate | Every assertion targets the gateway origin; the library exposes no service-port helper |
| T-31-01-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages. If one becomes necessary, halt and require the package-legitimacy audit plus a blocking human checkpoint |
</threat_model>
