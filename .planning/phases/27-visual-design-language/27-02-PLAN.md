<objective>
Add the surface vocabulary — glass and depth — as measured tokens, with no component consuming it
yet. Tokens and their proof land together; application comes in 27-04 and later.

D-27-04 says glass must degrade. The usual way that promise is kept is a fallback declared in a
negated feature query, which is a branch nobody renders in development, nobody screenshots, and
nobody measures. So this plan inverts it: the opaque colour is the base declaration and the
translucent fill is layered on top inside a positive feature query. The degraded rendering is then
the default state of the stylesheet, and it is impossible to ship a glass surface whose fallback
was never considered, because the fallback is the thing you wrote first.

D-27-01 says every new surface treatment carries its own measured contrast figure. A translucent
fill has no contrast figure on its own — only a composite does — so this plan teaches the repo's
validator to composite, and constrains what a glass surface may sit over so that the composite is
a finite, enumerable set rather than "whatever happens to be behind it".

Purpose: 27-04 through 27-07 all consume these tokens. If the numbers are wrong here they are
wrong on every screen.
Output: a composite-aware validator, a glass surface manifest, the glass and depth token layer,
and a contrast table measured under both deployment conditions.
</objective>

    - frontend/__tests__/lib/theme/design-tokens.test.ts lines 1-60 — the measurement basis note: unquantised OKLCH, not the 8-bit hex, is what all 53 numbers reproduce from

  </read_first>
  <behavior>
    - A fully opaque fill composited over any substrate returns the fill unchanged.
    - A fully transparent fill composited over a substrate returns the substrate unchanged.
    - A 50% white over black composites to the midpoint in linear-light terms consistent with how a browser composites, and the result is asserted against a value derived independently rather than against the function's own output.
    - Compositing is associative over a stack: a fill over a fill over an opaque substrate equals the same result as folding the stack pairwise from the bottom up.
    - The contrast of a foreground over a composited background equals the contrast of that foreground over an opaque colour equal to the composite, so the new path and the existing path agree wherever they overlap.
    - An input carrying no alpha channel is treated as fully opaque rather than throwing.
    - A substrate that is itself translucent is rejected, because a stack with no opaque floor has no defined result.
  </behavior>
  <action>
    Extend the validator with a composite operation that takes a possibly-translucent foreground
    colour and an opaque substrate and returns the opaque colour a browser would paint. Use the
    source-over compositing rule. Do the arithmetic in the colour space the browser composites in
    rather than in OKLCH: OKLCH is a perceptual space and interpolating alpha in it does not
    reproduce what the compositor does. Convert, composite, and return a CSS-parseable string so the
    result drops straight into the existing contrast function without a second code path.

    Add a convenience that measures a foreground against a translucent fill over a named substrate
    and returns the same result shape the existing check returns, so callers and tests read
    identically whether the background is opaque or not.

    Reject a translucent substrate explicitly with a message naming the problem. A stack without an
    opaque floor is the shape that produces a plausible-looking number with no physical meaning, and
    silently treating it as opaque is how such a number gets published.

    Write the seven behaviours as tests. The 50% case in particular must be asserted against a value
    computed by hand or by an independent route, not against whatever the implementation returns —
    a test that asserts a function equals itself is the standard way a compositing bug survives.

    Do not change the existing exported signatures. Phase 20's design-tokens.test.ts measures through
    this module and its 53 numbers must reproduce unchanged.
  </action>

  <action>
    Author two token families and one manifest.

    The glass family. Two surface weights are enough — a light panel weight and a heavier overlay
    weight — and each needs four values: an opaque fallback colour, a translucent fill, a blur radius,
    and a hairline border colour. Author every one at the brand hue through the existing custom
    property, never at a literal, so the existing regeneration test keeps holding. Starting values to
    measure and then adjust: in light theme, a near-white fill around 0.72 alpha with a 12px blur for
    the panel weight and around 0.60 alpha with a 20px blur for the overlay weight; in dark theme the
    equivalent stops near the surface-2 and surface-3 lightnesses at the same alphas. A modest
    saturation boost alongside the blur is what makes glass read as glass rather than as fog; keep it
    subtle. The hairline is decorative under SC 1.4.11 and is exempt from the 3:1 floor — say so in a
    comment beside it, because the next reader will otherwise either over-constrain it or fail to
    notice the distinction phase 20 was careful to draw.

    Then the class that consumes them, and this is the part with a specific required shape. Declare
    the surface class ONCE with the opaque fallback as its background. Then, inside a positive feature
    query for the compositing filter, and only under the expressive zone selector, override the
    background to the translucent fill and add the filter. Base is solid; enhancement is glass; the
    enhancement is zone-scoped so the cascade — not a reviewer — is what keeps it out of the
    operational zone.

    Supply the overlay effect that plan 27-01 removed from the two dialog overlays, as one rule in
    this same expressive-zone feature query keyed on the overlay's data-slot. Because those overlays
    portal to the body and carry a stamped zone attribute rather than inheriting one, the selector
    must match on the element's own zone attribute, not on an ancestor's. Getting this wrong produces
    a rule that is present in the stylesheet and never matches — precisely the failure this phase is
    meant to be immune to — and plan 27-01's runtime spec is what catches it.

    The depth family. Layered shadows for the expressive zone: an ambient wide-soft layer plus a key
    tight-dark layer per level, three levels, at chroma zero so depth never tints. A lift value used
    on hover, expressed as a translation distance and its paired shadow, so a hover lift is one token
    pair rather than a magic number at each call site. An inset for pressed states. Dark theme keeps
    the geometry and deepens the alpha, exactly as the existing elevation tokens already do. These
    are additive: do not touch the four existing elevation levels, which components depend on today.

    The manifest. A plain data module listing every glass surface, and for each: its fallback token,
    its fill token, the exhaustive set of substrate tokens it is permitted to sit over, and the
    foreground tokens that may be placed on it. This is what makes D-27-04 checkable — an enumerable
    substrate set is measurable, an arbitrary one is not — and it is what makes the prohibition on
    glass over photographs enforceable rather than aspirational. Keep it free of imports from the
    component layers so both the test and any documentation can read it.

    Finally, bridge the new colour tokens into the theme layer the way every other token family in
    this file is bridged, so they are addressable as utilities, and leave the shadow and blur values
    unbridged unless a utility is genuinely needed.
  </action>
