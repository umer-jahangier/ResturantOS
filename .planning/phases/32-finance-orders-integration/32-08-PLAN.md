<objective>
Build the query behind the centrepiece. D-32-01 asks for every order, payment, refund and void,
filterable by date, branch, terminal, cashier, tender and status, with a path from any row to the
order and to the journal entry it produced.

The data exists across three pos tables — `orders`, `order_payments`, `order_refunds` — and has never
been queryable together. `OrderController` lists orders by branch and status with no date range and no
tender filter; nothing lists payments at all. So an owner asking "show me today's card takings at the
Gulberg branch" has no surface to ask it of.

The grain decision is the one that has to be made deliberately and written down: a row in this register
is a **money event**, not an order. An order settled by cash and card is two rows, because the question
"what came in by card today" has to be answerable, and an order-grain register cannot answer it without
the caller doing arithmetic the product should have done. The order's own totals ride on each row for
context, clearly marked as the order's, not the row's, so nobody sums them.

Plan 32-11 renders this. Plan 32-04 supplies the ledger link.

Purpose: there is no system to see all the orders' transactions in the app. This is that system's query.
Output: a filtered, paginated, branch-scoped money-event register with a path to the ledger.
</objective>
