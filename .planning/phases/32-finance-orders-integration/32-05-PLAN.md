<objective>
Close 22b's D-9, the half of it this phase owns.

`finance.invoice-matched.queue` is durable, bound to a live routing key, growing by one message per
vendor invoice matched, and declared by nothing in this repository — not `FinanceRabbitConfig`, not
the definitions file, not any consumer. It is the residue of a version of finance that once consumed
that event. `reporting.invoice-matched.queue` is the live, healthy consumer of the same key. So every
vendor invoice matched from now until the broker is rebuilt leaks one message into a queue nobody
reads, with no TTL and no length bound.

22b declined to delete it mid-audit, correctly: deleting a bound durable queue on a shared stack while
four other agents are working is not a unilateral change. This plan makes it deliberately, captures
what was in it, and — the part that matters more than the deletion — adds the check that would have
caught it. A queue that exists only in the broker is invisible to every code review this project will
ever run, so the only thing that finds it is a comparison against the broker itself.

The second orphan, `notification.low-stock.queue`, is explicitly out of scope: it has a tracked owner,
its consumer is unbuilt rather than deleted, and its 24 messages are a real backlog.

Purpose: an undeclared durable queue is an unbounded leak nobody can see in the source.
Output: the queue retired with evidence, and a drift check that runs from one command.
</objective>

  <action>
    Create `scripts/verify-queue-ownership.mjs`, a plain Node script using the standard library only.

    Read the live queue list from the broker's management API, including each queue's durability,
    consumer count, message depth and bindings. Fail loudly if the broker is unreachable rather than
    passing vacuously — a check that silently succeeds when it cannot see the thing it checks is worse
    than no check, and this repository has already been bitten by exactly that shape.

    Build the declared set from two sources: every queue name string in the definitions file, and every
    queue name constant declared in service configuration code. Scan for the latter by name rather than
    by parsing Java: a queue name is a string literal and a literal grep across `services/**` is both
    sufficient and robust to refactoring. Exclude build output and the worktrees directory.

    Report, per queue: whether it is declared, whether it has a consumer, its depth, and whether it has
    a dead-letter exchange. Then fail on any queue that is durable AND bound AND undeclared. Warn — do
    not fail — on a queue that is declared but has zero consumers, because that is the legitimate state
    of a service that is simply not running, and a check that cries wolf gets muted.

    Support an exceptions file so a knowingly-tolerated queue can be listed with a written reason and a
    tracking reference. `notification.low-stock.queue` goes in it, citing its tracked owner. An
    exception with no reason string is itself a failure.

    Print PASS/FAIL per queue and a summary, and exit non-zero on any failure. Add a
    `verify-queue-ownership` Makefile target.

    Accept a `--from-snapshot <file>` option that reads the queue list from a saved JSON file instead
    of the broker, and a `--snapshot <file>` option that writes one. This exists so the check's own
    logic is testable after the drift it was written to find has been fixed: run it once against the
    live broker now, save that snapshot as a fixture, and assert the check fails against the fixture
    forever. Without this, task 1's gate would pass today and become unrunnable the moment task 2
    lands, which is a gate that verifies nothing a week from now.

    Write `scripts/ops/phase32-retire-orphan-queue.sh` performing the retirement as an evidenced,
    reversible sequence rather than a delete:

      1. Assert the queue exists, is durable, and has zero consumers. Abort if a consumer has appeared
         since — that would mean someone shipped the missing code and this plan's premise is stale.
      2. Drain every message to a timestamped file on disk, including headers and routing key. Print
         the count. A message is a record of a vendor invoice that matched; discarding it unread is
         throwing away a fact about money even if nothing was going to read it.
      3. Print the drained payloads' invoice identifiers so the operator can confirm against
         `reporting.invoice-matched.queue`'s successfully-processed set that nothing was lost.
      4. Unbind, then delete the queue.
      5. Re-run the ownership check and assert it now exits zero.

    no reference there, so most likely the file needs no change — but check, and if a stale entry
    exists, remove it, because a definitions file that recreates the queue on the next broker rebuild
    would undo this within a day.
