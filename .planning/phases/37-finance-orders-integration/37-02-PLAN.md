<objective>
Build the mechanism that keeps the guide honest, before any of the guide is written.

D-37-03 asks for a guide a restaurant owner can trust, and states the reason plainly: a guide that
lies is worse than no guide, because it is trusted. Hand-written prose about system behaviour drifts
the moment behaviour changes, and nothing notices — the 22b audit found exactly this shape three
times over, where a documented contract was implemented on one side and unreachable on the other.

So the guide is not authored as prose. It is authored as a registry: each behavioural claim is a row
carrying its plain-language sentence, the surface it belongs to, and the identity of the test that
proves it. A two-way gate then refuses to pass if a claim has no live assertion, or if an assertion
names a claim nobody declares. Plan 32-13 renders the guide FROM this registry; it cannot render a
sentence the registry does not hold, and the registry cannot hold a sentence no test defends.

This plan seeds the registry with the four claims D-37-03 names explicitly, each wired to an
assertion that already exists in the repository today, so the mechanism is proven against real
passing tests rather than against fixtures written for it.

Purpose: the guide's trustworthiness must be a build property, not an author's diligence.
Output: a registry, a two-way gate, and four claims already defended by existing tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| product behaviour to documented behaviour | A sentence an owner will act on claims something about the running system |
| test suite to gate | The gate's verdict depends on tests being genuinely enabled |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-32-02-A | Repudiation | Guide prose drifting from behaviour | high | mitigate | Every claim resolves to a named, enabled test; the gate fails the build otherwise |
| T-32-02-B | Tampering | A claim "covered" by a disabled test | high | mitigate | The gate inspects for disable/skip annotations around the named test and rejects them explicitly |
| T-32-02-C | Repudiation | An orphan marker outliving its claim | medium | mitigate | Direction two resolves every marker back to a registry row |
| T-32-02-D | Tampering | A literal the product no longer emits | medium | mitigate | Direction three greps each declared literal against non-test service source |
| T-32-02-E | Information Disclosure | Guide prose naming internal identifiers | low | accept | The registry is authored for owners; the gate does not restrict vocabulary, and review catches it |
| T-32-02-SC | Tampering | npm/pip/cargo installs | high | mitigate | The gate uses the Node standard library only; no package is added. If one becomes necessary, halt and require the package-legitimacy audit plus a blocking human checkpoint |
</threat_model>
