<objective>
Build the auth-service half of blocker B3 (D-11): there is no user-creation API anywhere in the
repository, so a tenant cannot onboard a single cashier. `users` lives in `auth_db`, and the established
architecture is that auth-service is the system of record while user-service is the public surface — so
the lifecycle operations land here and plan 13-12 exposes them.

Purpose: nothing in a tenant works without staff accounts, and today none can be created.
Output: paginated list, get, create with temporary password and optional role, update, deactivate and
reactivate — plus per-tenant email uniqueness at the schema level.
</objective>

    Create changeset 057 and register it.

    First determine and record in the SUMMARY whether email is currently unique globally, unique per
    tenant, or unconstrained. This matters more than it appears: login looks a user up by email with the
    tenant GUC set, so row-level security already scopes the read to one tenant, which means a
    globally-unique constraint is stricter than the code requires while an unconstrained column permits
    two rows one tenant apart that behave correctly and one row's worth of ambiguity if the GUC is ever
    unset.

    Add a unique index over tenant id and lowercased email, restricted to rows that are not soft-deleted
    if the table carries a deleted-at column. Repair any existing violations before creating it, using the
    same deterministic-retention pattern plan 13-02 established, and deactivate rather than delete the
    losers.

    Do not remove any existing broader constraint without recording why in the changeset comment; if a
    global unique constraint exists today, keeping it is a deliberate product decision about whether one
    human may hold accounts in two tenants under one address, and this plan must state which way it went
    rather than changing it as a side effect.

    Add supporting indexes for the list operation's sort and filter columns so pagination does not degrade.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user-service to auth-service internal | A tenant-scoped administrative request crosses on a shared secret plus a tenant header |
| auth-service to auth_db | User rows are created and modified under row-level security |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-11-A | Information Disclosure | Cross-tenant user reads | critical | mitigate | Tenant GUC set as the first statement of every transaction so row-level security scopes the read on the same connection; cross-tenant fetch asserted to return not-found by both test and live script |
| T-13-11-B | Spoofing | Tenant id supplied by the caller in the internal header | critical | mitigate | The internal endpoints are reachable only with the internal secret and only from user-service; plan 13-12 derives the tenant from the verified JWT, never from client input |
| T-13-11-C | Elevation of Privilege | Caller-supplied password on create or update | high | mitigate | The create request declares no password field; update rejects a body carrying one rather than ignoring it |
| T-13-11-D | Elevation of Privilege | Unvalidated role code on create | high | mitigate | Validated against the roles table with the helper from plan 13-06, the same source the catalog reads |
| T-13-11-E | Information Disclosure | Temporary password handling | critical | mitigate | Returned once; never logged, persisted plaintext or evented; the forced-change flag bounds its useful life |
| T-13-11-F | Repudiation | Hard-deleting a user | high | mitigate | Deactivation is a flag flip; rows and assignments survive so audit, order and journal references stay resolvable |
| T-13-11-G | Elevation of Privilege | A deactivated user retaining access | high | mitigate | Sessions revoked on deactivation and login refuses inactive users, both asserted live |
| T-13-11-H | Denial of Service | Unbounded list queries | medium | mitigate | Pagination is mandatory with a bounded page size, and supporting indexes are added in task 1 |
| T-13-11-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages. If one becomes necessary, halt and require the package-legitimacy audit plus a blocking human checkpoint |
