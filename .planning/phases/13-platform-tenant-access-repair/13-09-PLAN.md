<objective>
Harden the password-reset flow along the four defects the audit rates most serious in section 2.1, and
resolve the notification-service question CONTEXT.md leaves open (D-31).

The plaintext reset token written into the outbox alongside its hashed copy (D-19) is the single most
serious finding in that section: it defeats the hashing entirely for anyone with database, backup or
replica read access. The reset that does not clear the login lockout (D-18) is the one most likely to
strand a real user. Unlimited concurrently valid tokens with no throttle (D-21) is the one most likely
to be abused.

Purpose: make the reset path safe and honest before plan 13-13 layers admin-initiated reset on top.
Output: a redacted event, cleared lockouts, single-live-token semantics, a cooldown, and a resolved
delivery story.
</objective>

## Resolved: the notification-service question (D-31)

CONTEXT.md required a resolution: implement a minimal reset-email consumer, or declare email out of
scope — but in either case, do not leave a flow that silently does nothing.

**Decision: declare email delivery out of scope for this phase, and make the reset-request endpoint say
so explicitly rather than pretend.**

Rationale. `notification-service` is an empty Maven module with zero source files. Building a real email
consumer means an SMTP or provider integration, per-tenant sender configuration, bounce handling and a
template story — none of which is in CONTEXT.md's in-scope list, and all of which would consume the
budget this phase needs for the three blockers. Building a fake one that logs and drops is strictly
worse than the status quo, because it makes the dead flow look alive.

**Implementation.** A delivery-mode configuration property with two values, disabled and outbox, default
disabled. In disabled mode the request endpoint performs no token issuance at all and returns a
deterministic response naming the supported recovery route — an administrator-initiated reset, which
plan 13-13 delivers — with an error code that a UI can render. Critically, that response is identical for
a known and an unknown email, so the existing non-enumeration property is preserved rather than traded
away. In outbox mode the flow behaves as it does today, minus the plaintext token.

**Consequence.** The supported password-recovery path in this milestone is administrator-initiated
(plan 13-13), plus self-service change for a user who can still log in (plan 13-04). Self-service
forgot-password is unavailable and says so. This is recorded as a named gap in a docs file rather than
buried in a commit message, so the next phase can pick it up deliberately.

**Consequence.** The token-redaction, lockout-clearing, cooldown and single-live-token work still lands
in full, because outbox mode must be correct the day a consumer is written, and because plan 13-13's
admin reset reuses the same issuance path.
</decision_record>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated caller to the reset endpoints | Anyone may request a reset for any address |
| auth-service to the outbox table | An event payload becomes durable, replicated and backed up |
| auth-service to auth_db | Token hashes and credential material are written |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-09-A | Information Disclosure | Raw reset token in the outbox payload | critical | mitigate | The payload carries identity plus a non-secret row handle; asserted directly against the database by both a test and the live script |
| T-13-09-B | Information Disclosure | Account enumeration through the reset request | high | mitigate | Every branch returns a byte-identical body, asserted by equality rather than by status; the cooldown refusal is deliberately indistinguishable |
| T-13-09-C | Denial of Service | Unbounded reset requests per account | high | mitigate | A per-account cooldown independent of the gateway's per-IP budget, plus single-live-token semantics |
| T-13-09-D | Spoofing | Multiple concurrently valid reset tokens | high | mitigate | Issuing invalidates outstanding unredeemed tokens for the account |
| T-13-09-E | Denial of Service | A reset that leaves the account locked | high | mitigate | Confirm clears the counter and the timestamp through the shared policy routine; proven live from a genuinely locked account |
