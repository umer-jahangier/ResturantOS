<objective>
Make the WAITER role delivered by 13-02 actually usable, by moving the till requirement from order
creation to cash settlement — where the money actually moves.

13-02 seeded WAITER with `pos.order.create`, `pos.order.send_to_kds` and deliberately no till
permission, which is correct: in table service a waiter takes the order and a cashier settles it.
But `OrderServiceImpl.createOrder` (services/pos-service/.../OrderServiceImpl.java:177-185) requires
the *creating* user to hold an OPEN till and throws `NoOpenTillException` otherwise. A waiter cannot
open a till by design, so a correctly-permissioned waiter is authorized to take an order and then
refused by the service with `409 NO_OPEN_TILL`. The grants are right and the workflow is impossible.

Purpose: an end-to-end waiter persona that 13-15's seed script can demonstrate.
Output: order creation binds a till opportunistically; cash settlement requires one.
</objective>

<context>
**This tightens financial integrity rather than relaxing it, and that is the reason to do it this
way.** Today the two halves are strict in the wrong places:

- `OrderServiceImpl.createOrder` HARD-requires the creator's open till — but only when a userId is
  present. Any path without one (service-to-service, internal flows) already creates orders with
  `till_session_id = null`, so the guard does not actually establish the invariant it claims.
- `PaymentServiceImpl.recordPayment` (line 77) already backfills the till at settlement, but only
  best-effort: `.ifPresent(...)`. A cash payment by a user with no open till is accepted today and
  the order stays unlinked — precisely the "charged but till shows 0" gap that comment describes.

After this plan, the invariant is stated once, at the point where cash changes hands: **no cash
payment without an open till.** That closes the null-till settlement hole that exists today, which
is why the net effect is stronger reconciliation, not weaker.

Do not widen this to non-cash payments. Card and wallet tenders do not pass through the drawer, and
requiring a till for them would break exactly the counter-less flows this phase is enabling. Bind
the till when one is present, require it only for `PaymentMethod.CASH`.

Counter service is unaffected: a cashier who opens a till before taking orders gets identical
behaviour to today, because the creation-time binding is retained whenever a till exists.

**Deferred to Phase 16 deliberately.** The user's requirement is that an admin configures each POS
profile (combined food+drink, or separate food POS and bar counter). Making
"orders require a till at creation" a per-profile setting belongs with that work. This plan
establishes the correct default so the seed script and the waiter persona work; it does not build
the configuration surface.
</context>

<tasks>

### Task 1 — Specify both behaviours before changing either (RED)

Write `WaiterOrderNoTillIT`: a user with `pos.order.create` + `pos.order.send_to_kds` and **no** till
session creates an order and sends it to the KDS. Assert the order persists with
`tillSessionId == null` and that the `ORDER_SENT_TO_KDS` outbox entry is emitted. Fails today with
`NoOpenTillException`.

Write `CashPaymentRequiresTillIT` with three cases:
1. Cash payment by a user with an OPEN till → accepted, and the order's `tillSessionId` equals that
   till (covers both the create-time-bound and the backfilled-at-settlement paths).
2. Cash payment by a user with **no** open till → rejected. Assert the specific exception, not merely
   that something threw.
3. Cash payment by a user whose only till session is CLOSED → rejected. This is the case a naive
   `findByCashierId` would wrongly admit.

Add a non-cash case asserting a card payment still succeeds with no till, so the scope of the new
requirement is pinned by a test rather than by a comment.

Follow `StationAdminIT` for the authentication pattern — service-layer permission gates read the
Spring `SecurityContext`, which `TenantContext` does not populate. Both new ITs must call
`authenticateAs(...)`; a test that only sets `TenantContext` will fail on the permission gate for a
reason unrelated to what it is asserting.

### Task 2 — Order creation binds a till only when one exists (GREEN)

In `OrderServiceImpl.createOrder`, replace the `orElseThrow(NoOpenTillException::new)` with a lookup
that sets `tillSessionId` when the creating user has an OPEN till and leaves it null otherwise. Keep
setting `cashierId` from the tenant context unchanged.

Rewrite the block comment. The existing one (lines 166-176) asserts a financial-integrity rationale
that will no longer be true of this method, and leaving it would actively mislead the next reader —
state that the till is bound opportunistically here and required at cash settlement, and name
`PaymentServiceImpl` as the enforcement point.

### Task 3 — Cash settlement requires an open till (GREEN)

In `PaymentServiceImpl.recordPayment`, before any amount is applied: if the method is
`PaymentMethod.CASH`, resolve the paying user's OPEN till and throw if there is none, binding it to
the order when the order has none. For non-cash, keep the existing best-effort backfill.

Ensure the status filter really is on OPEN — reuse `findByCashierIdAndStatus(userId, TillStatus.OPEN)`
rather than adding a new query that could drift.

Confirm `NoOpenTillException` maps to a sensible status in `PosGlobalExceptionHandler` for this new
call site; it currently surfaces as `NO_OPEN_TILL`. A rejected cash payment is a business-rule
refusal, so 409 is right — verify rather than assume, and do not change the code for the existing
call site's sake.
