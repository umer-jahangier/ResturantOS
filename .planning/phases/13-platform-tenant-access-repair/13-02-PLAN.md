<decision_record>
## Resolved: the TENANT_ADMIN authority question (D-23)

CONTEXT.md required the planner to choose. **Decision: split.** Three new permission codes are
introduced — one for user administration, one for role administration, one for branch administration —
and both OWNER and TENANT_ADMIN are granted all three. The existing umbrella RBAC permission stays in
the catalog, stays granted to OWNER, and stays excluded from TENANT_ADMIN.

**Consequence, stated explicitly.** `AuthServiceImpl.requiresTotpStepUp` triggers mandatory TOTP
step-up when the resolved permission list contains the umbrella RBAC code. Granting that code to
TENANT_ADMIN would have forced TOTP enrolment on every tenant admin as an invisible side effect of an
authorization change, and a tenant admin with no enrolled secret would be met with
TotpEnrollmentRequiredException at login — i.e. the fix would have re-broken login for the exact
persona it was meant to enable. The split avoids that. OWNER keeps the umbrella code and therefore
keeps TOTP step-up, which is the intended behaviour for the highest-privilege tenant role.

**Second consequence.** The blanket grant statements in changesets 030, 044, 045 and 046 are
point-in-time inserts. New permission codes are not retro-granted by them, so this plan must grant the
three new codes to OWNER explicitly as well as to TENANT_ADMIN.

**Third consequence.** `PermissionCatalogClosureTest` scans every `@PreAuthorize` expression in the
repository and requires each dotted code to exist in the auth-service permissions catalog. The three
new codes are therefore introduced in the catalog changeset *and* in the controller gates in the same
plan, or the build breaks.

## Resolved: multi-role per branch (D-24)

CONTEXT.md required a choice between a partial unique index and a permission-union resolver.
**Decision: the partial unique index**, because CONTEXT.md itself says "enforce it at the schema
level", and because a union resolver would make the JWT's `roles` claim plural, which every downstream
consumer of that claim currently assumes is singular.

**Consequence.** A user holds at most one active role per branch. Assigning a second role to the same
branch is a replacement, not an addition: the assign path deactivates any other active row for that
pair inside the same transaction and reports what it displaced. Permission unions across roles are not
supported in this milestone; a tenant needing a blend must be given a role that carries the blend.
</decision_record>
