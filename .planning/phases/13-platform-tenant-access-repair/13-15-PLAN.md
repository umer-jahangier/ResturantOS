## Resolved: language and API-versus-database strategy (D-27, D-28, Claude's discretion)

**Language: Python 3, matching the existing seeders.** `scripts/onboarding.py` and
`scripts/seed_test_env.py` are Python with psycopg2 and already solve deterministic identifiers via
uuid5, bcrypt cost 12 hashing, and the row-level-security GUC handling every direct write needs. A bash
script would not be cross-platform on Windows, and this repository's convention is a PowerShell twin for
each shell script. The PowerShell artifact in this plan is therefore a thin launcher that resolves the
interpreter and forwards arguments, not a reimplementation.

**Strategy: drive the real API wherever one now exists.** CONTEXT.md states the preference plainly and
gives the reason — driving the real API is what proves the repair. Direct database writes are permitted
only where no API exists, and every such case must be listed. The script prints that list on every run,
so the set of remaining gaps is visible rather than archaeological.

Expected API-driven: SuperAdmin login, tenant provisioning, tier change, feature toggles, user creation,
branch-role assignment, forced password change, branch creation beyond the first.

Expected direct-write, to be confirmed and listed at implementation time: menu and catalog master data
where no seeding endpoint exists, and any transactional back-dating required to make reports non-empty
across historical periods. Each entry states which service owns the table and what endpoint would replace
the write.
</decision_record>
