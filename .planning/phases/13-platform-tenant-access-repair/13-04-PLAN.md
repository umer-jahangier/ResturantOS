<objective>
Deliver the two password primitives everything else in this phase builds on: one shared strength
constraint (D-20) replacing today's length-only rule on a single DTO, and the self-service
change-password endpoint (D-15) that the audit found does not exist anywhere in the repository.

Plan 13-08 adds forced-change enforcement at login on top of this; plan 13-09 hardens the reset flow;
plan 13-13 adds admin-initiated reset. All three depend on the policy service this plan extracts.

Purpose: no password lifecycle work in this phase is testable until a user can change a password.
Output: a shared constraint, an extracted policy service, and an authenticated change endpoint.
</objective>

  <name>Task 1: A shared password-strength constraint in shared-lib (D-20)</name>
  <files>shared-lib/src/main/java/io/restaurantos/shared/validation/StrongPassword.java, shared-lib/src/main/java/io/restaurantos/shared/validation/StrongPasswordValidator.java, shared-lib/src/test/java/io/restaurantos/shared/validation/StrongPasswordValidatorTest.java, services/auth-service/src/main/java/io/restaurantos/auth/dto/request/PasswordResetConfirmRequest.java</files>
  <read_first>
    - services/auth-service/src/main/java/io/restaurantos/auth/dto/request/PasswordResetConfirmRequest.java — the single length-only rule that is the whole policy today
    - services/auth-service/src/main/java/io/restaurantos/auth/dto/request/LoginRequest.java — a password-bearing DTO that must NOT gain the constraint, because validating an existing password against a new policy would lock out every user whose password predates it
    - shared-lib/src/main/java/io/restaurantos/shared/exception/ — the existing exception and error-envelope conventions
    - services/auth-service/src/main/java/io/restaurantos/auth/exception/AuthExceptionHandler.java — how validation failures currently surface
  </read_first>
  <behavior>
    - A value shorter than the configured minimum is rejected.
    - A value longer than the configured maximum is rejected — an unbounded password is a bcrypt cost amplification vector.
    - A value missing any required character class is rejected, and the violation message names the missing classes without echoing the value.
    - A value meeting every rule is accepted.
    - A null value is accepted by the validator itself, so nullability stays the responsibility of a separate not-blank annotation and the two concerns do not fight.
    - The violation message contains no substring of the submitted value.
  </behavior>
  <action>
    Create a StrongPassword annotation and its validator in a new shared-lib validation package,
    following the Jakarta Bean Validation constraint conventions already used elsewhere in the codebase.
    The policy: a minimum length of 12, a maximum of 128, and at least one lowercase letter, one
    uppercase letter, one digit and one non-alphanumeric character. Make the minimum overridable per
    annotation use so a future looser context is possible without a second annotation, but default it to
    12. Bcrypt truncates beyond 72 bytes; note that in the javadoc so the maximum is understood as a
    denial-of-service bound rather than a security bound.

    The violation message must describe the unmet requirements and must never include the submitted
    value or any part of it — a validation error is frequently logged and frequently returned to the
    caller.

    Apply the annotation to the reset-confirm DTO's new-password field, replacing the length-only rule.
    Do not apply it to the login request: validating an existing credential against a newly tightened
    policy would refuse logins for every account created before this change, which is precisely the
    class of self-inflicted lockout this phase exists to fix. Record that reasoning in a comment on the
    login DTO so a later reader does not "fix" the omission.

    Write StrongPasswordValidatorTest covering the six behaviours, including an explicit assertion that
    the message contains no fragment of the input.
  </action>
  <acceptance_criteria>
    - All six behaviours pass.
    - The reset-confirm DTO carries the shared constraint and no longer carries a bare length rule.
    - The login DTO is unchanged.
    - The full backend still packages.
  </acceptance_criteria>

  </verify>

    reuse rejection against the current hash and the last five history rows; the history append; the
    revoke-all-refresh-sessions helper; and the tenant GUC setter. Have PasswordResetService delegate to
    it rather than keeping duplicates — the audit's recurring theme is two code paths that drift, and a
    reset that enforces reuse rules while a change does not is exactly that shape. Add one behaviour the
    reset path does not have today and both paths now need: clearing the failed-login counter and the
    lockout timestamp. Plan 13-09 wires that into reset; this plan wires it into change.

    Create ChangePasswordRequest carrying the current password as a not-blank string and the new
    password annotated with the shared strength constraint.

    Create PasswordChangeService with a changeOwnPassword operation taking the authenticated user id,
    the current password and the new password. Order matters: resolve the user, set the tenant GUC
    before any row-level-security-scoped read so the GUC and the read share one connection — the
    codebase has a documented prior bug of exactly that shape — verify the current password with the

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated user to auth-service | A credential change is requested for the caller's own account |
| auth-service to auth_db | Password hashes and history rows are written under row-level security |
| auth-service to the outbox | A password-lifecycle event leaves the transaction boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-04-A | Elevation of Privilege | Change-password target selection | critical | mitigate | The user id comes from the authenticated principal only; the DTO has no user-id field, so a caller cannot name another account |
| T-13-04-B | Spoofing | Current-password verification | critical | mitigate | Verified with the injected bcrypt-cost-12 encoder before any write; failure throws the shared generic authentication exception so no oracle is created |
| T-13-04-C | Information Disclosure | Validation and error messages | high | mitigate | The strength message names unmet rules only; an explicit test asserts no fragment of the input appears; the failure body is byte-identical to other authentication failures |
| T-13-04-D | Information Disclosure | Password material in logs and events | critical | mitigate | The success event carries user id and tenant id only; no logging statement takes a password parameter |
| T-13-04-E | Elevation of Privilege | Session survival after a change | high | mitigate | All refresh sessions for the user are revoked in the same transaction; the residual access-token lifetime is asserted explicitly so the window is known rather than assumed |
| T-13-04-F | Denial of Service | Unbounded password length | medium | mitigate | Maximum length of 128 enforced by the shared constraint before hashing |
| T-13-04-G | Tampering | Divergence between reset and change policy | high | mitigate | Both paths delegate to one extracted policy service; the reset service is left with no private copy |
| T-13-04-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages. If one becomes necessary, halt and require the package-legitimacy audit plus a blocking human checkpoint |
</threat_model>
