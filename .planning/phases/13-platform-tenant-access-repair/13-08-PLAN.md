<decision_record>
## Chosen enforcement mechanism

Two designs were available: issue a token with an emptied permission list and a marker claim, or refuse
the login outright and hand back a scoped change token.

**Decision: refuse the login and hand back a scoped change token.**

Rationale: an emptied-permission token is still a valid access token to every filter in the system, and
its correctness would depend on every current and future authorization check treating an empty
permission list as a refusal. That is an invariant nobody can hold. A refusal is checkable at exactly
one place.

**Consequence.** Every caller that provisions a user must expect its first login to be refused. Plan
13-15's seed script therefore performs a real forced change for each persona it creates, which turns
the seed script into the live proof of this behaviour rather than a workaround for it.
</decision_record>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-08-A | Elevation of Privilege | The public forced-change endpoint | critical | mitigate | Requires both a valid single-use change token and the current password; the user id comes from the token, never the request; one generic failure for every token defect |
| T-13-08-B | Information Disclosure | Forced-change response as an account oracle | high | mitigate | The branch runs only after a successful password comparison, so a wrong password yields the ordinary generic failure; asserted by test and by the live script |
| T-13-08-C | Spoofing | Change-token replay | high | mitigate | Single use enforced by the used-at column; issuing a new token invalidates outstanding ones; ten-minute expiry |
| T-13-08-D | Information Disclosure | Change token at rest | high | mitigate | Only the SHA-256 hash is persisted, reusing the reset-token treatment; the raw value exists only in the refusal response |
| T-13-08-E | Elevation of Privilege | Cross-purpose token redemption | high | mitigate | A purpose discriminator with a check constraint; redemption matches hash and purpose together; refusals asserted in both directions |
| T-13-08-F | Denial of Service | Brute-forcing the change token | medium | mitigate | 256 bits of entropy from the existing generator, ten-minute expiry, and the auth route's per-IP rate limit |
| T-13-08-G | Repudiation | Forced change lost from the audit trail | medium | mitigate | The login-succeeded event still fires on the credential check, and the change emits the plan 13-04 success event |
| T-13-08-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages. If one becomes necessary, halt and require the package-legitimacy audit plus a blocking human checkpoint |
