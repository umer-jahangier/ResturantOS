<objective>
Make inventory master data complete in the product (D-36-06): stock, ingredients, categories, units,
storage locations, reorder points and opening stock, each creatable, readable, changeable and
retirable without a script.

Most of this already exists and works. The measured gap is units: the endpoint offers a list and a
create and nothing else, so a tenant who mistypes a house unit — or provisions one with the wrong
family base, which the create path validates precisely because such a unit can never convert — is
stuck with it forever and it stays in every picker. That is also the entity with the least forgiving
blast radius, because a unit code is referenced by value from another database.

The larger point is the second one: nobody can currently say which master-data operations exist. The
user's report was that these things "are not linked properly or not working", and the honest answer
to that is a matrix that is asserted rather than remembered.

Purpose: definition-of-done item 5, and the master-data surface every other plan in this phase
depends on being trustworthy.
Output: units gain change and retire with a guard that names its references, and a coverage matrix
that fails the build when an operation goes missing.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated user to inventory-service | Master-data writes cross a permission check and row-level security |
| inventory-service to purchasing-service | The retire guard reads vendor catalog references across a database boundary |
| the unit registry to every conversion | A unit's identity is a foreign key by value into three tables and two databases |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-31-05-A | Tampering | Unit code mutation | critical | mitigate | A code change is refused outright; the code is referenced by value across services and a rename would orphan ingredients, conversions and vendor catalog rows silently |
| T-31-05-B | Denial of Service | Retiring a unit still in use | high | mitigate | The retire guard counts references in four places, names them in the refusal, and refuses when the cross-service count cannot be evaluated |
| T-31-05-C | Repudiation | Historical rows that stop converting | high | mitigate | Retirement is a timestamp, never a delete, and the conversion reads deliberately ignore it so past receipts still convert |
| T-31-05-D | Tampering | A unit created or edited outside its family invariant | high | mitigate | The change path reuses the create path's dimension and family-base validation rather than restating it |
| T-31-05-E | Information Disclosure | Cross-tenant unit visibility | high | mitigate | Every read is tenant-scoped under forced row-level security, and the live script asserts it as the service role rather than as a superuser |
| T-31-05-F | Elevation of Privilege | Master-data writes by a read-only role | medium | mitigate | The new operations carry the same manage-level authorization the existing create carries; no new authority is introduced |
| T-31-05-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages. If one becomes necessary, halt and require the package-legitimacy audit plus a blocking human checkpoint |
</threat_model>
