<objective>
Refuse a purchase-order line that inventory cannot honour, at the API, with an error that names the
problem (D-36-04) — and refuse the unit that inventory would otherwise receive at face value
(D-36-05, the purchasing half).

Phase 22 drove this end to end: purchasing accepted a line for an ingredient id inventory had never
seen, the receipt dead-lettered, the purchase order showed closed, and there was no stock and no
ledger entry. The audit named the durable fix precisely — a validity check at the purchasing to
inventory boundary, at the line entry point, because making inventory tolerate the unknown id would
turn a loud failure into a silent one.

Two of the three pieces already exist and neither is reachable from this path. An ingredient
reference validator was built for vendor-catalog rows and is disabled by default, because it is gated
on the same setting that decides whether goods receipts are simulated — two unrelated questions
sharing one switch. A pack-unit validator exists for the same catalog rows and never sees a
hand-typed purchase-order line, whose unit is free text and, by its own author's admission, usually
will not resolve.

Purpose: every downstream number in this phase — stock, moving-average cost, the inventory control
account — is derived from a line that must first be honourable.
Output: one gate, applied at line creation and again at receipt, and a seam that no longer conflates
simulation with validation.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated user to purchasing-service | Caller-supplied ingredient ids and unit codes enter a cross-database reference |
| purchasing-service to inventory-service | An internal, shared-secret lookup decides whether a reference is real |
| purchasing-service to the broker | A goods-receipt event commits inventory to a stock write and a ledger entry |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-31-04-A | Tampering | Caller-supplied ingredient id | high | mitigate | Every line's ingredient is resolved against the caller's own tenant through the internal lookup before anything is persisted; a definitive absence is refused |
| T-31-04-B | Information Disclosure | Cross-tenant ingredient probing | high | mitigate | The lookup answers only within the caller's tenant, so an id belonging to another tenant is indistinguishable from one that does not exist |
| T-31-04-C | Denial of Service | Unbounded id lists on the internal lookup | medium | mitigate | The internal endpoint already caps its batch; the gate batches per request and stays inside that cap, failing the request rather than splitting silently |
| T-31-04-D | Denial of Service | Coupling purchasing availability to inventory uptime | high | mitigate | Transport failure degrades open and is logged once per request; only a definitive negative is fail-closed |
| T-31-04-E | Tampering | A refusal leaving a partial order or a burnt idempotency key | high | mitigate | All lines are validated before any persistence, and a refusal does not consume the idempotency key |
| T-31-04-F | Repudiation | A receipt that succeeds on paper and produces no stock | critical | mitigate | The receipt path re-runs the gate before writing anything, and the live script asserts the dead-letter queue does not grow |
| T-31-04-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages. If one becomes necessary, halt and require the package-legitimacy audit plus a blocking human checkpoint |
