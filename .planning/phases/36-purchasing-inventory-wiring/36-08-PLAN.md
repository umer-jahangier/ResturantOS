<objective>
Sign the phase off the way its definition of done is written (D-36-01): an owner completes the whole
procure-to-pay chain entirely in the UI, and the master-data screens behind it work, proven in a
browser rather than through the API.

Every earlier plan in this phase verified itself through the gateway with a shell script, which is
the right instrument for asserting that a service behaves. It is the wrong instrument for the claim
this phase actually makes, which is that a person can do this. The user's report was about using the
product; the sign-off has to be about using the product.

Purpose: definition-of-done items 1 and 5, and a record that says which screen answered which locked
decision.
Output: one browser journey covering the chain and the master data, and a short acceptance document.
</objective>

    - It creates a supplier and a catalog item for that ingredient with a pack unit and pack quantity, and sees the catalog row.
    - It sets an approval limit on a user through the user administration screen and sees the limit rendered on that user's assignments.
    - It raises a purchase order from the catalog item, submits it, approves it, and sees the order reach the approved state on the orders screen.
    - It sends the order, receives it, and sees the received quantity on the order and the resulting stock on the stock screen.
    - It books a vendor invoice against the order and sees the three-way match result on the invoice.
    - It posts a payment and sees the invoice settled.
    - A purchase-order line for an ingredient that no longer exists is attempted and the screen shows a message naming the problem, not an empty state and not a generic failure.

  <action>
    Write the journey as one test telling one story, in the journeys project so it runs against a real
    stack, using the existing signed-in-persona fixture and the existing purchasing selectors. Keep it
    a single narrative rather than nine independent tests: the claim is that the chain connects, and
    nine isolated tests can all pass while the chain does not.

    Do every state transition by clicking. Not one step may be prepared through the API, including the
    approval limit — the limit set on a screen in step three is what makes the approval in step six
    possible, and that dependency is the point. Where the product needs a fresh sign-in for a limit to
    take effect, sign in again in the browser, because that is what a person would have to do and the
    journey should show whether it is tolerable.

    Assert rendered state after each step, on the screen that would show it. A toast is not evidence:
    this repository has already shipped a screen where a failed request rendered as an empty state,
    and a passing toast over an unchanged database is the same class of lie.

    Include the negative case, driven through the form: attempt a line for an ingredient that has been
    retired or does not exist, and assert the screen names the problem. A refusal a user cannot read
    is a refusal that generates a support ticket.

    Use no tolerance entries. If a step cannot pass, the journey fails and the phase is not done —
    which is the honest outcome and the one this phase's method requires.
  </action>

    - No step is prepared through the API, verified by the absence of any direct request in the spec.

    - No known-defect tolerance is used.
