<objective>
Settle which permission purchasing actually demands, who should hold it, and whether the demand is
right — and repair the cause that made purchasing answer 403 for the MANAGER, at that cause
(D-36-02).

This is a permission-model question and not a grant to hand out. Plan 13-02 split `rbac.manage`
deliberately so that anyone able to edit a user could not thereby grant themselves an owner role,
and plan 19b minted `pos.tables.admin` rather than reuse a code a waiter already held. The same
discipline applies here: if the seed's call failed because a database is missing rows a changelog
already declares, that is drift and is repaired as drift; if it failed because the tenant does not
have purchasing switched on, that is not a permission problem at all and must not be "fixed" by
granting anything.

Purpose: every remaining plan in this phase writes through purchasing endpoints, and none of them
can be verified while the role that owns procurement cannot reach them.
Output: a reachability test that cannot go stale, a repair at the recorded cause, and a 403 a human
can act on.
</objective>
