**On-hand stock page reading server-decided reorder/oversell flags, plus opening-balance/receipt/transfer(ship+receive)/count dialogs built on a new `GET /api/v1/inventory/transfers/pending` backend endpoint and a full frontend data-layer extension for the four Phase-8 write endpoints.**

## Accomplishments

- Shipped `/app/inventory/stock`: a real read view over `GET /api/v1/inventory/stock`, with search + client-side category filter, a total-stock-value summary line, and per-row emphasis driven ENTIRELY by the server's `belowReorderPoint`/`nonPositive` flags — zero client-side `qtyOnHand` vs `reorderPoint` arithmetic anywhere in the file.

## Decisions Made

See `key-decisions` in frontmatter — summarized: (1) added the missing `GET .../transfers/pending` backend endpoint since the Transfer-receive flow cannot exist without it; (2) dropped the UI-SPEC's vendor/PO-reference receipt-header fields since the real backend DTO has no such fields (a UI control with nowhere to persist would be dead/misleading); (3) StockCountDialog sources expected qty from the same `useStockLevels()` data the stock page renders, never a second fetch; (4) row/variance emphasis threshold is "any nonzero variance," the simplest deterministic rule matching the UI-SPEC's "small threshold" language; (5) fixed a pre-existing MSW mock inaccuracy in `belowReorderPoint` while touching the same handler file, since it's exactly the class of frontend/mock divergence this phase exists to close.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical Functionality] Added `GET /api/v1/inventory/transfers/pending`**
- **Found during:** Task 2 (StockTransferDialog's Receive section)
- **Issue:** The UI-SPEC's Transfer-receive flow requires "a list of in-transit transfers awaiting this branch," but `TransferController` only had `POST /ship` and `POST /receive` — no read endpoint existed anywhere for in-transit transfers. Without it, the Receive section of the dialog is structurally impossible to build honestly.
- **Fix:** Added `StockTransferRepository.findByTenantIdAndToBranchIdAndStatusOrderByShippedAtAsc`, `TransferService.listPendingForBranch` (reusing the existing `toDto` mapper so the list-item shape never drifts from the ship/receive response shape), and `TransferController.pending` (own-branch-only enforcement mirroring `StockLevelController` exactly).
- **Files modified:** `StockTransferRepository.java`, `TransferService.java`, `TransferController.java`, plus the frontend `listPendingTransfers`/`usePendingTransfers` consumers.
- **Verification:** `mvn -q -pl services/inventory-service compile -o` passes clean; frontend `tsc`/`eslint`/`vitest` all pass.
- **Committed in:** `4bbb91e` (Task 2 commit)

**2. [Rule 1 - Bug] Fixed the mock `belowReorderPoint` formula's missing positive-reorder-point guard**
- **Found during:** Task 3 (constructing a destructive-only test fixture)
- **Issue:** `mocks/inventory.handlers.ts`'s `GET /stock` handler computed `belowReorderPoint: qtyOnHand < reorderPoint` with no guard for `reorderPoint <= 0`, unlike the real `StockLevelService.toDto()` (`reorderPoint.signum() > 0 && qtyOnHand.compareTo(reorderPoint) <= 0`). A row with `reorderPoint: "0"` would be incorrectly flagged `belowReorderPoint: true` in the mock but never in the real backend — precisely the class of frontend/mock divergence CONTEXT.md's origin bug documents.
- **Fix:** Corrected the formula to `reorderPoint > 0 && qtyOnHand <= reorderPoint`.
- **Files modified:** `frontend/mocks/inventory.handlers.ts`.
- **Verification:** `countRowWithLargeVarianceIsEmphasised`/`rowAtOrBelowZeroGetsTheDestructiveWash` tests pass against the corrected formula; full `npx vitest run` shows zero new failures.
- **Committed in:** `4bbb91e` (Task 2 commit)
