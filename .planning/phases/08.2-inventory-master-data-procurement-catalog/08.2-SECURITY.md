## Resolved Finding (remediated 2026-07-25, commit `31a072e`)

### T-08.2-044 (medium, Tampering) — Cross-service `ingredient_id` validation — CLOSED

**Resolution:** A service-layer existence-and-ownership guard was added at vendor-catalog create
time, delivering the check plan 08.2-04 promised. `VendorItemService.create()` now calls
`IngredientReferenceValidator.requireIngredientInTenant(req.ingredientId())` before persisting.
The validator follows the phase's existing `restaurantos.inventory.integration-mode` seam:
- `FeignIngredientReferenceValidator` (`integration-mode=feign`) reuses the shipped
  `GET /internal/inventory/ingredient-categories` endpoint (plan 08.2-09) as an existence oracle —
  a live in-tenant ingredient returns a non-null `categoryId` (ingredients carry a NOT NULL category
  FK since plan 08.2-01), an unknown or foreign id returns `categoryId: null`. Absence of a non-null
  match throws 422 `IngredientNotInTenantException` (mapped in `PurchasingExceptionHandler`, matching
  the sibling PO-line cross-tenant guard `VENDOR_ITEM_CATALOG_MISMATCH`). Degrades open on a transport
  failure, consistent with the same seam's T-08.2-112 resilience contract.
- `MockIngredientReferenceValidator` (`integration-mode=mock`, the default) is a permissive no-op —
  no reachable inventory-service in mock mode — so dev and all integration tests are unaffected.

### T-08.2-044 (medium, Tampering) — Cross-service `ingredient_id` validation never implemented (as-found)

**Declared in:** 08.2-04-PLAN.md, deferred explicitly to land in plan 08.2-08: "service-layer
validation in plan 08.2-08 (the ingredient must resolve under the caller's tenant) — database FK
is impossible across databases and is deliberately not attempted."

**Checked:** `services/purchasing-service/src/main/java/io/restaurantos/purchasing/service/VendorItemService.java`
`create(UUID vendorId, CreateVendorItemRequest req)` (lines 76-121) sets
`item.setIngredientId(req.ingredientId())` directly with **no lookup, no Feign call, and no
existence/tenant check** against inventory-service. `CreateVendorItemRequest.ingredientId` carries
only `@NotNull` (type/presence validation, not existence/ownership).

Cross-checked 08.2-08-PLAN.md's own `<threat_model>` (T-08.2-081 through T-08.2-086): it does
**not** repeat or fulfill this promise anywhere in its `<action>` blocks or acceptance criteria.
08.2-08-SUMMARY.md's accomplishments/coverage sections make no mention of ingredient-existence or
cross-tenant-ingredient validation either. The only cross-service resolver that exists
(`InventoryCategoryClient`/`FeignIngredientCategoryResolver`) is for category-name resolution in
spend analytics (plan 08.2-11), unrelated to catalog-creation-time validation.

**Practical impact:** a tenant can supply an arbitrary UUID (including another tenant's real
ingredient id) as `ingredientId` when creating a `VendorItem`; the row persists with no error.
Downstream, `PurchaseOrderService` copies `catalogItem.getIngredientId()` onto PO lines
(`PurchaseOrderService.java:123`), so a bogus/foreign ingredient id can propagate onto purchase
orders and spend analytics (surfaced there as an unresolvable ingredient, degrading to
"Uncategorized" per T-08.2-112 — no crash, but silently wrong data lineage).

**Severity re-confirmed as medium** (Tampering; requires an authenticated `vendor.manage`
principal to exploit; no cross-tenant *read* results, only a dangling/spoofed reference) — below
`block_on: high`, so this does **not** block phase advancement, but is tracked here as a genuine
implementation gap, not a documentation-vs-reality mismatch that merely needs re-verification.

**Recommendation:** add a Feign call (reusing the `InventoryCategoryClient`/`FeignClientConfig`
pattern already proven for category resolution) or a lightweight internal
`/internal/inventory/ingredients/{id}/exists`-style check in `VendorItemService.create`, gated the
same way `InternalIngredientCategoryController` already is, before persisting a new `VendorItem`.

## RLS posture caveat (affects T-08.2-041, informational — not a new finding)

`vendor_items`/`vendor_item_prices`/`vendor_categories` (V5, plan 08.2-04) use `ENABLE ROW LEVEL
SECURITY` **without** `FORCE`, unlike every inventory-service table in this same phase
(`item_categories`, `ingredient_uom_conversions`, `ingredient_allergens` — all `ENABLE`+`FORCE`).
PostgreSQL bypasses RLS entirely for a table's owning role; if `purchasing_user` owns these
tables (consistent with the project's known `pos_db`/`kitchen_db` owner-bypass pattern — see
project memory `pos-kitchen-rls-owner-bypass`), the `tenant_isolation` policy on these three
tables is advisory-only at the database layer. This was independently caught by this phase's own
code review (`08.2-REVIEW.md` WR-03) and **explicitly skipped by design** in `08.2-REVIEW-FIX.md`
("Skipped Issues" §WR-03), deferring it to the project's coordinated `deploy/pending-migrations/`
FORCE-RLS activation package rather than a one-off fix. The threat's literal mitigation text
("ENABLE ROW LEVEL SECURITY + a tenant_isolation policy... service-layer tenant predicates are
added in plan 08.2-08") is satisfied, and the service-layer tenant predicate is independently
verified present and correct (T-08.2-081/101/102). No action required by this audit; recorded so
the caveat travels with the phase rather than being re-discovered.
