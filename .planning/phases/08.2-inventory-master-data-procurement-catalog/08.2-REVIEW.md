# Phase 08.2: Code Review Report

**Reviewed:** 2026-07-25
**Depth:** standard
**Files Reviewed:** 56 (prioritized production code across inventory-service, purchasing-service, and the Next.js frontend; test files scanned for correctness but not exhaustively)
**Status:** issues_found

## Summary

Phase 08.2 adds inventory master-data (item categories, ingredient master data, recipe cost preview, stock levels, inter-branch transfers) and the procurement catalog (vendor items, append-only pricing, catalog-driven PO lines, spend analytics with Feign category resolution). The code is unusually well-documented and most tenant/authorization seams are handled carefully: controllers enforce own-branch guards via JWT claims (`StockLevelController`, `TransferController`, `RecipeController`), the append-only pricing invariant is respected end-to-end, money is kept in paisa with `BigDecimal` arithmetic rounding only at the paisa boundary, and the previously-reported CR-1/CR-2/CR-3 gaps (transfer destination-branch guard, zero-price PO derivation, negative-qty guard) are all closed.

The one genuine data-integrity defect is a **missing state/idempotency guard on stock-transfer receive**: `TransferService.receive` never checks that the transfer is still `SHIPPED`, so a replay or double-submit re-increments destination stock, re-recomputes moving-average cost, and re-emits `TRANSFER_RECEIVED`. That is a BLOCKER. The remaining items are robustness/consistency concerns: overship into negative on-hand, an unvalidated PO `vendorId`, `ENABLE`-not-`FORCE` RLS on the purchasing tables (consistent with the documented repo posture but inconsistent with this phase's own inventory migrations), unscoped `findById` on PO lifecycle methods, and a branch-scope inconsistency in the single-item current-price endpoint.

No structural pre-pass (`<structural_findings>`) was provided, so this report is entirely narrative findings.

## Critical Issues

### CR-01: Stock-transfer receive has no state guard — a transfer can be received more than once, inflating destination stock

**File:** `services/inventory-service/src/main/java/io/restaurantos/inventory/service/TransferService.java:159-272`

**Issue:** `receive(...)` loads the transfer with `findByIdAndTenantId`, enforces the destination-branch guard, and then unconditionally processes every line — incrementing `qtyOnHand`, recomputing MAC via `MacCalculator.recomputeAvgCostPaisa`, inserting a new `StockLot` and `InventoryMovement`, and publishing `TRANSFER_RECEIVED`. It never verifies the transfer's current `status`. After the first call the status is set to `"RECEIVED"`, but a second call (a duplicate submit, an at-least-once client retry, or a deliberate replay) passes every check and runs the whole body again. `StockTransfer` carries no `@Version` optimistic-lock column and there is no `SHIPPED`-only precondition anywhere, so each replay permanently adds the shipped quantity to the destination branch and re-pollutes the moving-average cost and the outbox event stream. `ship()` is safe because it always creates a new transfer, but `receive()` mutates an existing one and must be idempotent. Contrast the sibling PO flow (`PurchaseOrderService.getDraft`/`send`/`close`) which all assert the expected source state before mutating.

**Fix:** Reject a non-`SHIPPED` transfer before any write, inside the same transaction that already holds the row:

```java
StockTransfer transfer = transferRepository.findByIdAndTenantId(request.transferId(), tenantId)
        .orElseThrow(() -> new IllegalArgumentException("Unknown transferId: " + request.transferId()));
if (!transfer.getToBranchId().equals(receivingBranchId)) {
    throw new AccessDeniedException("Cannot receive a transfer destined for another branch");
}
if (!"SHIPPED".equals(transfer.getStatus())) {
    throw new StateInvalidException("Transfer " + transfer.getId() + " is not awaiting receive (status="
            + transfer.getStatus() + ")");
}
```

Consider also adding a `@Version` column to `StockTransfer` so concurrent receive attempts collide on optimistic lock rather than racing between the status read and write.

## Warnings

### WR-01: `TransferService.ship` does not validate available stock — ships phantom inventory and drives on-hand negative

**File:** `services/inventory-service/src/main/java/io/restaurantos/inventory/service/TransferService.java:107-145`

**Issue:** For each ingredient, ship does `stockRepository.findForUpdate(...).orElseGet(() -> save(newStockRow(...)))` and then `stock.setQtyOnHand(stock.getQtyOnHand().subtract(qty))` with no check that `qtyOnHand >= qty`. Shipping from a branch that has never stocked the ingredient creates a fresh zero row and immediately drives it negative, emitting a `TRANSFER_OUT` movement and shipped-event line at `unitCostPaisa = 0` (the new row's avg cost). The receiving branch then books real stock at cost 0. Even for an existing row, any over-ship silently produces negative on-hand. Additionally there is no guard that `fromBranchId != toBranchId`, so a self-transfer is accepted (decrement source with no receiving counterpart). The FEFO floor-at-zero on lots is intentional, but the *aggregate* going negative with zero-cost valuation is a data-integrity hazard for Phase 9's GL posting.

**Fix:** Before decrementing, assert sufficient on-hand and reject self-transfers:

```java
if (request.fromBranchId().equals(request.toBranchId())) {
    throw new StateInvalidException("Cannot transfer stock to the same branch");
}
// inside the per-ingredient loop, after loading `stock`:
if (stock.getQtyOnHand().compareTo(qty) < 0) {
    throw new StateInvalidException("Insufficient on-hand for ingredient " + ingredientId
            + " at branch " + request.fromBranchId());
}
```

### WR-02: `PurchaseOrderService.create` never validates the PO `vendorId` exists / belongs to the tenant

**File:** `services/purchasing-service/src/main/java/io/restaurantos/purchasing/service/PurchaseOrderService.java:64-137`

**Issue:** `create` sets `po.setVendorId(req.vendorId())` and only uses `vendorId` to scope the catalog lookup (`findByTenantIdAndVendorIdAndArchivedAtIsNull`). It never confirms the vendor exists for this tenant — unlike `VendorItemService.requireVendor`, which every catalog write goes through. A request with a nonexistent or foreign `vendorId` plus legacy `ingredientId` lines (the DTO still supports the ingredient-typed path) is accepted and persists an orphan PO pointing at a vendor that does not exist for the tenant. Catalog-driven lines happen to fail with 422 (empty catalog), but the legacy path has no such backstop.

**Fix:** Resolve and tenant-check the vendor at the top of `create`, mirroring `VendorItemService.requireVendor`, before building the PO:

```java
vendorRepository.findById(req.vendorId())
        .filter(v -> tenantId.equals(v.getTenantId()))
        .orElseThrow(() -> new ResourceNotFoundException("Vendor", req.vendorId()));
```

### WR-03: Purchasing V5 tables use `ENABLE ROW LEVEL SECURITY` without `FORCE` — RLS is inert for the app role

**File:** `services/purchasing-service/src/main/resources/db/migration/V5__vendor_item_catalog.sql:51-53, 83-85, 111-113`

**Issue:** `vendor_items`, `vendor_item_prices`, and `vendor_categories` enable RLS but never `FORCE` it, and grant full DML to `purchasing_user`. If `purchasing_user` owns (or is the connecting role for) these tables, PostgreSQL bypasses the `tenant_isolation` policy for that role, so the policy is decorative and tenant isolation rests entirely on service-layer predicates. This matches the known repo-wide posture (see MEMORY: "pos/kitchen RLS owner-bypass"), but it is inconsistent with this phase's own inventory migrations (`V5__item_categories.sql:126-127`, `V6__ingredient_master_data.sql:87-88,108-109`), which correctly use both `ENABLE` and `FORCE`. The service layer here is careful (`findByTenantIdAnd...` everywhere), but the defense-in-depth the migration comment implies ("the database itself refuses the row") does not actually hold for these three tables.

**Fix:** Add `ALTER TABLE <t> FORCE ROW LEVEL SECURITY;` for each of the three tables in a follow-up migration (matching the inventory convention), or explicitly document in the migration that RLS is intentionally advisory-only here and isolation is service-layer, so the discrepancy is a deliberate decision rather than an oversight.

### WR-04: PO lifecycle methods use unscoped `findById`, unlike the tenant-scoped transfer path

**File:** `services/purchasing-service/src/main/java/io/restaurantos/purchasing/service/PurchaseOrderService.java:149-209, 236-242`

**Issue:** `withdraw`, `send`, `get`, `close`, and `getDraft` all call `purchaseOrderRepository.findById(id)` with no tenant predicate. `toDto` re-derives the tenant from `TenantContext` and correctly filters catalog denormalization by it, but the PO header/lines themselves are returned/mutated for whatever id resolves. This is the exact "relying on FORCE-RLS + Hibernate filter alone" defect class that `StockTransferRepository.findByIdAndTenantId` and `IngredientRepository.findByTenantIdAndId` were explicitly introduced to eliminate (per their own Javadoc). If the Hibernate tenant filter or RLS lapses on any path (as has happened historically per MEMORY), these become cross-tenant read/mutation. These methods predate 08.2, but the file is in scope and the inconsistency is real.

**Fix:** Add a `findByIdAndTenantId(UUID id, UUID tenantId)` to `PurchaseOrderRepository` and route every lifecycle method through it with `tenantContext.requireTenantId()`, throwing `ResourceNotFoundException` on miss — matching the transfer/ingredient precedent.

### WR-05: `VendorItemPriceService.currentPrice` can return a branch-specific row while every other "current price" path filters to tenant-wide

**File:** `services/purchasing-service/src/main/java/io/restaurantos/purchasing/service/VendorItemPriceService.java:101-107`

**Issue:** The single-item `currentPrice(vendorItemId, at)` calls `findCurrentForVendorItems(...).stream().findFirst()` with no branch filter. `findCurrentForVendorItems` returns both tenant-wide (`branchId == null`) and branch-specific rows ordered by `effectiveFrom DESC`, so `findFirst` may return a branch-scoped price. Meanwhile `VendorItemService.currentPricesByItem` and `PurchaseOrderService.currentPricesByItem` both `.filter(p -> p.getBranchId() == null)` to deliberately pick the tenant-wide price. The result: the catalog list, PO-line derivation, and this endpoint can disagree about "the current price" for the same item whenever a branch override exists — a subtle inconsistency in a money-bearing path.

**Fix:** Make the single-item lookup's branch semantics explicit — either accept a `branchId` parameter and prefer the branch-specific row falling back to tenant-wide, or filter `branchId == null` to match the batch enrichment paths. Do not leave it as "whichever row sorts first."

### WR-06: `VendorAnalyticsService.spendReport` does not validate the reporting window

**File:** `services/purchasing-service/src/main/java/io/restaurantos/purchasing/service/VendorAnalyticsService.java:154-183`

**Issue:** `resolvedCompareFrom = resolvedCompareTo.minusDays(ChronoUnit.DAYS.between(from, to))`. If a caller passes `from` after `to`, `ChronoUnit.DAYS.between` is negative and the prior window silently inverts/extends in the wrong direction, producing a nonsensical comparison window rather than a validation error. There is no `@AssertTrue`/service-side check that `from <= to` (nor that `compareFrom <= compareTo` when both supplied).

**Fix:** Validate the window at the controller/DTO boundary (or first line of `spendReport`) and reject inverted ranges with a 400, e.g. `if (to.isBefore(from)) throw new StateInvalidException("'to' must be on or after 'from'");` and the analogous check for the explicit compare window.

## Info

### IN-01: `VendorItemService.replaceCategories` can hit a DB unique-constraint violation on duplicate `categoryId`

**File:** `services/purchasing-service/src/main/java/io/restaurantos/purchasing/service/VendorItemService.java:165-185`

**Issue:** The incoming `List<VendorCategoryDto>` is inserted verbatim after a delete. Two entries with the same `categoryId` violate `uq_vendor_category (tenant_id, vendor_id, category_id)` and surface as a raw `DataIntegrityViolationException` (500) rather than a clean 422. `vendorCategoriesInputSchema` on the client does not dedupe either.

**Fix:** De-duplicate by `categoryId` before `saveAll` (e.g. collect into a `LinkedHashMap` keyed by `categoryId`), or validate distinctness and throw a `StateInvalidException` with a readable message.

### IN-02: PO form treats an equivalent-but-differently-typed price as an override

**File:** `frontend/components/purchasing/PurchaseOrderFormDialog.tsx:93-103`

**Issue:** `priceUnchanged` compares `l.unitPriceRupees.trim()` to the catalog price formatted via `.toFixed(2)`. A user who types `120` for a catalog price of `120.00` fails the string equality, so `unitPricePaisa` is sent and the line comes back flagged `priceOverridden` despite being economically identical. Harmless to totals (same paisa) but produces a misleading "price overridden" badge.

**Fix:** Compare numerically (`Number(l.unitPriceRupees) === catalogItem.currentUnitPricePaisa / 100`) or compare the computed paisa values rather than the raw strings.

### IN-03: `RecipeCostPreviewService.dimensionMatches` can NPE on a null ingredient base UOM

**File:** `services/inventory-service/src/main/java/io/restaurantos/inventory/service/RecipeCostPreviewService.java:201-207`

**Issue:** `ingredientBase.equals(uom.getBaseUnitCode())` dereferences `ingredientBase = ingredient.getBaseUomCode()`. `base_uom_code` is `NOT NULL` at the DB/entity level so this is currently unreachable, but the method is a pure static helper with no null guard; a future nullable field or a detached/partially-built entity would throw inside the preview loop instead of degrading the line to the warning path the rest of the method is built around.

**Fix:** Null-guard defensively: `return ingredientBase != null && ingredientBase.equals(uom.getBaseUnitCode());` (the `equalsIgnoreCase` branch above already tolerates a null argument).
