# Phase 08.2 Plan 10: Catalog-Driven PO Line (Server Side) Summary

**PurchaseOrderService.create() derives ingredientId/uom/unitPricePaisa from a vendor's catalog when a PO line supplies vendorItemId, rejecting cross-vendor/archived/unknown/cross-tenant references with a new 422 mapping, while every legacy hand-typed-ingredient PO line keeps working unchanged.**

## Performance

- **Duration:** ~50 min
- **Tasks:** 3 completed
- **Files modified:** 7 (4 modified, 3 new)

## Accomplishments
- `PurchaseOrderLine.vendorItemId` maps the nullable FK column plan 08.2-04's V5 migration already created — not a `@ManyToOne`, so PO serialization never drags in the catalog row.
- `CreatePurchaseOrderRequest.Line` accepts an optional `vendorItemId` alongside a now-nullable `ingredientId`, enforced mutually-exclusive via a record `@AssertTrue`; a legacy 4-arg constructor overload keeps every existing direct-construction Java caller compiling unchanged.
- `PurchaseOrderService.create()` loads the PO's own vendor's active catalog in ONE tenant-scoped query before the line loop (`VendorItemRepository.findByTenantIdAndVendorIdAndArchivedAtIsNull`), deriving `ingredientId`/`uom`/`unitPricePaisa` from the matched catalog row, or rejecting with the new `VendorItemCatalogMismatchException` (422) when the id is unknown, archived, from another vendor, or from another tenant — all indistinguishably, per the threat model.
- A supplied `unitPricePaisa` still overrides the catalog price for a one-off deal; `toDto()` derives `priceOverridden` by comparing the persisted price against the catalog's currently effective price (batched via `VendorItemPriceRepository.findCurrentForVendorItems`), and denormalizes `vendorSku`/`packDescription` onto every response line for catalog-derived lines.
- No vendor category tag is referenced anywhere in `PurchaseOrderService` (grep-gated at 0).
- `PurchaseOrderVendorItemIT` — 10 MockMvc tests covering derivation, override-and-flag, the three rejection paths, the legacy compatibility gate, the 400 neither-id case, response enrichment, and effective-at-order-time pricing.
- Full `services/purchasing-service` module `mvn test`: all IT classes green, no regression against the relaxed request contract.

## Decisions Made
- Kept the legacy 4-arg `Line` constructor as an explicit overload rather than touching `PurchaseOrderApprovalIT`/`PurchaseOrderCloseIT`/`PurchasingMockE2EIT`/`PurchasingOpaPolicyIT` — none of those files were in this plan's `files_modified` scope, and the overload is the standard Java-record technique for adding a field without breaking existing direct-construction callers.
- Reused `VendorItemRepository.findByTenantIdAndVendorIdAndArchivedAtIsNull` (already existing from 08.2-08) for the batched catalog-validation query instead of adding a new repository method — it is exactly the right shape (tenant + vendor scoped, archived excluded) and keeps this plan's changes within its declared `files_modified`.
- `priceOverridden`/`vendorSku`/`packDescription` are computed at every `toDto()` call rather than persisted, since no new migration was in scope. Documented trade-off: `priceOverridden` reflects the mismatch against the catalog's *current* price, not the price at order-creation time, if the catalog price has since changed. No test in this plan exercises that edge case.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] Added VendorItemCatalogMismatchException + local PurchasingExceptionHandler for the 422 the plan itself requires**
- **Found during:** Task 2, while implementing the cross-vendor/archived/unknown catalog rejection
- **Issue:** The plan's own action text and acceptance criteria require a 422 response for an invalid `vendorItemId`, but shared-lib's `GlobalExceptionHandler` has no 422 mapping at all (`RestaurantOsException`'s base handler always resolves to 400, `StateInvalidException` to 409). The plan's dependency context also explicitly warned against a bare `@ResponseStatus` exception, since `GlobalExceptionHandler`'s `@ExceptionHandler(Exception.class)` catch-all silently resolves any unmapped exception to 500 — the exact latent defect 08.2-08-SUMMARY.md documented and fixed for `BackdatedPriceException`/duplicate-SKU rejection in the same module.
- **Fix:** Added `VendorItemCatalogMismatchException` (extends `RestaurantOsException`) and a new local `PurchasingExceptionHandler` (`@RestControllerAdvice`) with a dedicated `@ExceptionHandler` mapping it to `HttpStatus.UNPROCESSABLE_ENTITY`, mirroring inventory-service's `IngredientCategoryInvalidException`/`InventoryExceptionHandler` pair exactly (same javadoc rationale, same shape).
- **Files modified:** `exception/VendorItemCatalogMismatchException.java` (new), `web/PurchasingExceptionHandler.java` (new)
- **Verification:** `PurchaseOrderVendorItemIT#vendorItemFromAnotherVendorIsRejected`/`#archivedVendorItemIsRejected`/`#unknownVendorItemIsRejected`/`#catalogItemFromAnotherTenantIsInvisible` all assert HTTP 422 via a real MockMvc round trip.
- **Committed in:** `d50b983` (Task 2 commit)

**2. [Rule 1 - Bug] Preserved source compatibility for existing Line constructor callers**
- **Found during:** Task 1, after adding `vendorItemId` to `CreatePurchaseOrderRequest.Line` changed its canonical (all-args) constructor shape
- **Issue:** `PurchaseOrderApprovalIT`, `PurchaseOrderCloseIT`, `PurchasingMockE2EIT` and `PurchasingOpaPolicyIT` all construct `CreatePurchaseOrderRequest.Line` directly via its old 4-arg canonical constructor (`ingredientId, qty, uom, unitPricePaisa`). Adding `vendorItemId` as a new leading field changed the canonical constructor to 5 args, which would have broken compilation for all four files — caught only after a full `test-compile` (the earlier `mvn compile` check only compiles main sources, not test sources, so it missed this).
- **Fix:** Added an explicit legacy 4-arg constructor overload on the `Line` record that delegates to the new 5-arg canonical constructor with `vendorItemId = null`, preserving both source and binary compatibility for every existing caller without modifying any of those four test files.
- **Files modified:** `dto/CreatePurchaseOrderRequest.java`
- **Verification:** `mvn -pl services/purchasing-service test-compile` succeeds; `PurchaseOrderApprovalIT`/`PurchaseOrderCloseIT` (Task 2's own `<verify>` command) pass 9/9; full module `mvn test` passes with no regression.
- **Committed in:** `bb53155` (Task 1 commit)
