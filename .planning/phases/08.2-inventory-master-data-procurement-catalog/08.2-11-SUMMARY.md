# Phase 08.2 Plan 11: Real ingredient-category resolver for spend analytics Summary

Replaced purchasing-service's fabricated spend-by-category analytics (a static classpath YAML mapping a handful of hardcoded ingredient UUIDs) with a batched, Feign-backed resolver that calls the real inventory-service internal endpoint shipped in plan 08.2-09, degrading to "Uncategorized" rather than failing when inventory-service is unreachable.

## What Was Built

**`IngredientCategoryResolver`** (interface, rewritten): single-id `resolve(UUID)` replaced with `Map<UUID, String> resolveAll(Collection<UUID>)`. There is no single-id overload anymore — a caller cannot reintroduce per-invoice-line resolution.

**`InventoryCategoryClient`** (new Feign client): `@FeignClient(name = "inventory-service", contextId = "inventoryCategoryClient", configuration = FeignClientConfig.class)` declaring `GET /internal/inventory/ingredient-categories`, returning a nested `IngredientCategoryResponse(ingredientId, categoryId, categoryName, categoryPath)` record mirroring inventory-service's `IngredientCategoryLookupDto` field-for-field.

**`FeignIngredientCategoryResolver`** (new adapter, `integration-mode=feign`): dedupes the requested ids, chunks them into batches of at most 500 (the internal endpoint's cap), issues one Feign call per chunk, substitutes `"Uncategorized"` for a blank/null category name, and — critically — catches any transport/connection failure per chunk, logs a WARN naming the failure and affected id count, and resolves every id in that chunk to `"Uncategorized"` instead of letting the exception propagate. The spend report keeps rendering through an inventory-service outage.

**`MockIngredientCategoryAdapter`** (new adapter, `integration-mode=mock`, not in the original files_modified list — see Deviations): resolves every requested id to `"Uncategorized"`. This exists solely so the Spring context still has exactly one `IngredientCategoryResolver` bean and boots in mock mode after the classpath mock was deleted; it produces no fabricated category names.

**`VendorAnalyticsService.spendReport`** (rewired): after `loadPoLines(...)` builds the PO-line map, a new `resolveCategoryLabels(...)` helper collects every distinct non-null `ingredientId` across both the current and prior windows and calls `ingredientCategoryResolver.resolveAll(...)` exactly once for the whole report. `aggregate(...)` now takes that resolved `Map<UUID, String>` as a parameter and looks up each line's category label from it (falling back to `"Uncategorized"` for a null ingredient id or an id absent from the map) instead of calling the resolver per line.

**Deleted**: `MockIngredientCategoryResolver.java` (classpath-backed resolver, loaded `spend-category-map.yml` via snakeyaml) and `spend-category-map.yml` itself — both removed via `git rm`, satisfying ROADMAP Success Criterion 7 / decision D-09 ("delete the mock, don't bypass it") literally, not just functionally.

**Tests**: `SpendAnalyticsIT` updated to stub `IngredientCategoryResolver` via `@MockitoBean` (returning known "Meat"/"Produce"/"Dairy" labels for the fixed seed ingredient ids) instead of relying on the deleted YAML fixture — its existing vendor/category-aggregation-with-deltas assertions are otherwise unchanged. New `SpendByRealCategoryIT` (5 tests) exercises the real `FeignIngredientCategoryResolver` end to end via `VendorAnalyticsService.spendReport(...)`, with only the outbound `InventoryCategoryClient` mocked:
1. `spendBucketsUseCategoryNamesReturnedByInventoryService` — real category names ("Produce"/"Dairy") reach `byCategory` buckets with correct paisa totals.
2. `categoryResolutionIsCalledOncePerReportNotOncePerLine` — 6 invoice lines across 3 ingredients, `verify(inventoryCategoryClient, times(1)).getIngredientCategories(anyList())`.
3. `unresolvedIngredientFallsBackToUncategorized` — client response omits one requested id; its spend lands in the `Uncategorized` bucket rather than being dropped.
4. `inventoryServiceFailureDegradesInsteadOfFailingTheReport` — client throws; the report still returns (no exception propagates), every affected category bucket is `Uncategorized`, and the vendor-spend bucket for the same invoice is unaffected (proving vendor aggregation doesn't depend on category resolution at all).
5. `nullIngredientIdOnALegacyPoLineIsUncategorized` — an invoice line whose `poLineId` doesn't resolve to any loaded `PurchaseOrderLine` (the real-world stand-in for a "legacy" line, since `purchase_order_lines.ingredient_id` is DB `NOT NULL` and cannot itself be null on a persisted row) also falls back to `Uncategorized`.

Full module regression via `mvn verify`: 86 IT tests + 25 unit tests, 0 failures/errors.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — blocking build/boot failure] `InventoryCategoryClient` needed a distinct Feign `contextId`**
- **Found during:** Task 3, first test run of `SpendByRealCategoryIT`/`SpendAnalyticsIT`.
- **Issue:** `InventoryGrnClient` (from Phase 8) already declares `@FeignClient(name = "inventory-service", configuration = FeignClientConfig.class)`. Declaring `InventoryCategoryClient` with the identical bare `name` (as the plan's `<action>` text literally specified) causes Spring Cloud OpenFeign's `FeignClientsRegistrar` to register a second `FeignClientSpecification` bean under the same bean name (`inventory-service.FeignClientSpecification`), throwing `BeanDefinitionOverrideException` at context startup — this broke context bootstrap for **every** existing purchasing-service Spring Boot test (`SpendAnalyticsIT` included, not just the new `SpendByRealCategoryIT`), and would have broken the real running service too.
- **Fix:** Added `contextId = "inventoryCategoryClient"` to `InventoryCategoryClient`'s `@FeignClient` annotation — Spring Cloud OpenFeign's documented mechanism for multiple clients sharing one downstream service `name`.
- **Files modified:** `services/purchasing-service/src/main/java/io/restaurantos/purchasing/feign/InventoryCategoryClient.java`
- **Commit:** 619d95a

**2. [Rule 2 — missing critical functionality] Mock-mode needs a replacement `IngredientCategoryResolver` bean**
- **Found during:** Task 2 (deleting `MockIngredientCategoryResolver`).
- **Issue:** The plan's `files_modified` list didn't include a new mock-mode implementation file, but `VendorAnalyticsService` constructor-injects a single `IngredientCategoryResolver` bean; deleting the only mock-mode implementation with nothing replacing it under `integration-mode=mock` (the mode every existing IT in the module runs under, per `PurchasingTestBase`) would fail Spring context bootstrap for the entire module.
- **Fix:** Added `MockIngredientCategoryAdapter` (mirrors `MockGrnAdapter`'s `@ConditionalOnProperty(havingValue = "mock", matchIfMissing = true)` selection), resolving every requested id to `"Uncategorized"` — explicitly documented as a degraded-mode stub, not a resurrection of the deleted fixture.
- **Files modified:** `services/purchasing-service/src/main/java/io/restaurantos/purchasing/adapter/MockIngredientCategoryAdapter.java` (new)
- **Commit:** 34b860b

**3. [Rule 1 — bug/prohibition violation] Pre-existing javadoc reference to the deleted mock class name**
- **Found during:** Task 2, verifying the plan's own `grep -rl 'MockIngredientCategoryResolver' services/` prohibition returns nothing.
- **Issue:** `services/inventory-service/.../InternalIngredientCategoryController.java` (shipped in the prior plan 08.2-09, outside this plan's declared `files_modified`) has a javadoc comment literally naming `MockIngredientCategoryResolver`. This plan's own acceptance criteria requires a **repo-wide** zero-reference grep, so the pre-existing reference would fail that verification even though the file lives in a different service.
- **Fix:** Reworded the javadoc to say "the classpath-backed category mock" instead of naming the deleted class. Also scrubbed equivalent self-introduced references in this plan's own new/modified javadoc (`IngredientCategoryResolver.java`, `InventoryCategoryClient.java`, `FeignIngredientCategoryResolver.java`, `MockIngredientCategoryAdapter.java`) so no source file under `services/` names the deleted class or fixture.
- **Files modified:** `services/inventory-service/src/main/java/io/restaurantos/inventory/web/InternalIngredientCategoryController.java`
- **Commit:** 34b860b

### Commit-sequencing note (not a deviation)

Task 1's own `<verify>` (`mvn -q -pl services/purchasing-service -DskipTests compile`) cannot pass in isolation from Task 1's file set alone — `IngredientCategoryResolver`'s new batch-only interface (Task 1) doesn't compile until `VendorAnalyticsService` and the deleted mock resolver are updated in the same tree (Task 2), since the old classpath mock still implemented the old single-id method. This is inherent to how the plan split an interface-signature change from its implementers, not a defect introduced during execution; the module was verified to compile clean once both tasks' file sets were present, and the full test suite was run once — after all three tasks — as the true acceptance gate.
