# Phase 08.2 Plan 01: Item Categories Master Data Migration Summary

**Additive Flyway V5 migration turning ingredient categories into first-class, 3-level-max self-referencing master data with a DB-enforced depth trigger and a required, RESTRICT-only `ingredients.category_id` FK backfilled from the legacy free-text column.**

## Performance

- **Started:** 2026-07-23T01:52:00+05:00
- **Completed:** 2026-07-23T02:08:30+05:00
- **Tasks:** 3

## Accomplishments

- `item_categories` table: self-referencing tree, `level BETWEEN 1 AND 3`, `NULLS NOT DISTINCT` unique constraint on `(tenant_id, parent_id, name)`, FORCE RLS + `tenant_isolation` policy, `GRANT ... TO inventory_user`.
- `enforce_item_category_depth()` BEFORE INSERT/UPDATE trigger: rejects a 4th level, a level that skips a rung, a self-parent, and a cross-tenant parent - all as real database exceptions (SQLSTATE 23514), not service-layer convention.
- `ingredients.category_id UUID NOT NULL REFERENCES item_categories(id) ON DELETE RESTRICT`, backfilled from the legacy free-text `ingredients.category` (defaulting blank/null to `"Uncategorized"`), with the migration's temporary `NO FORCE`/`FORCE` window on `ingredients` closed again in the same file and proven closed by a dedicated regression test.
- `SchemaMigrationIT` extended (11 -> 12 domain tables) with `itemCategories_hasForceRlsAndTenantIsolationPolicy()`.
- New `ItemCategoryMigrationIT` (5 tests): 3-level accept / 4th-level reject, level-mismatch reject, cross-tenant-parent reject, NOT NULL + FK RESTRICT proof, FORCE-RLS-after-backfill regression guard.
- Compensating fix (see Deviations): `IngredientService.createIngredient`/`updateIngredient` and the shared `InventoryFixtures.seedIngredient` test helper now resolve `category_id` via a new idempotent `IngredientRepository.resolveOrCreateCategoryId` seam, keeping every existing ingredient-creation path (production and test) working against the new NOT NULL column.

## Decisions Made

- `NULL` literals inside a `SELECT DISTINCT` list must be cast explicitly (`NULL::UUID`) - Postgres otherwise infers `text` for the untyped literal and the subsequent `INSERT` into a `UUID` column fails with SQLSTATE 42804 ("column is of type uuid but expression is of type text"). Fixed inline in the migration before it ever reached a committed state.
- The compensating ingredient-creation fix (see Deviations) deliberately reuses V5's own backfill rule (`COALESCE(category, 'Uncategorized')` -> find-or-create a root category) rather than inventing a different default, so a category resolved at write-time today is indistinguishable from one the migration itself backfilled for pre-existing rows. This keeps exactly one deterministic default-category rule in play until a later wave (08.2-09/10, per ROADMAP) adds real category selection UI/API.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `NULL` literal type mismatch in the V5 backfill INSERT**
- **Found during:** Task 1 (`mvn -Dtest=SchemaMigrationIT test` against a live Postgres 16 container)
- **Issue:** `INSERT INTO item_categories (tenant_id, parent_id, level, name) SELECT DISTINCT tenant_id, NULL, 1, ... FROM ingredients` failed with `ERROR: column "parent_id" is of type uuid but expression is of type text` - Postgres defaults an untyped `NULL` literal inside a `SELECT DISTINCT` projection to `text`.
- **Fix:** Cast explicitly: `NULL::UUID`.
- **Files modified:** `services/inventory-service/src/main/resources/db/migration/V5__item_categories.sql`
- **Verification:** `SchemaMigrationIT` passes; Flyway applies V1..V5 cleanly.
- **Committed in:** `a85ecb4` (Task 1 commit; caught and fixed before that commit was made)

**2. [Rule 1 - Bug] Ingredient creation broke for every existing code path once `category_id` became NOT NULL**
- **Found during:** Task 3, running the full `mvn -pl services/inventory-service test-compile failsafe:integration-test failsafe:verify` regression this task's own acceptance criteria requires.
- **Issue:** The `Ingredient` JPA entity had no `category_id` mapping, so Hibernate's `INSERT` never included that column and Postgres rejected every insert with a NOT NULL violation. This broke `IngredientService.createIngredient` in production (surfaced as `500`s in `IngredientAdminIT`/`InventoryAccessControlIT`) and 14 pre-existing integration tests that seed ingredients via the shared `InventoryFixtures.seedIngredient` helper (`DepletionConsumerIT`, `LiveDepletionProofIT`, `MacRecomputeIT`, `OpeningBalanceIT`, `ReceiptServiceIT`, `StockCountIT`, `TransferLifecycleIT`, and their access-control/low-stock/expiry-sweep counterparts) - a direct violation of this plan's own success criterion "no existing inventory test regresses" and CONTEXT.md's "must not disturb the depletion loop."
- **Fix:** Mapped `Ingredient.categoryId`; added `IngredientRepository.resolveOrCreateCategoryId(tenantId, categoryText)` - an idempotent find-or-create against `item_categories` using the migration's own `COALESCE(category, 'Uncategorized')` root-category rule (same `uq_item_category_tenant_parent_name` conflict target, `ON CONFLICT ... DO NOTHING` then a lookup); wired it into `IngredientService.createIngredient`/`updateIngredient` (no DTO/API change - still driven by the existing free-text `category` field) and into `InventoryFixtures.seedIngredient`.
- **Files modified:** `Ingredient.java`, `IngredientRepository.java`, `IngredientService.java`, `InventoryFixtures.java`
- **Verification:** Full `mvn -pl services/inventory-service test-compile failsafe:integration-test failsafe:verify` - 64/64 tests pass, 0 failures, 0 errors (up from 2 failures + 31 errors before the fix).
- **Committed in:** `5398b49` (Task 3 commit)
