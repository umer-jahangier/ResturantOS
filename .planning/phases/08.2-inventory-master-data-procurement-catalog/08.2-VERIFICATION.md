### Blocker 2 — Transfer ship/receive authorization gap + CR-1 fix

**Prior finding:** `GET /transfers/pending` (plan 08.2-17) had zero backend IT coverage. Code review
conducted in the same pass separately surfaced CR-1, a real cross-branch authorization bug: neither
`ship()` nor `receive()` verified the caller's branch against the transfer's source/destination
branch.

**Code verification — `TransferController.java`:**
- `ship()`: after `authz.authorizeManage(...)`, throws `AccessDeniedException` when
  `!request.fromBranchId().equals(claims.branchId())` — rejects shipping stock out of a branch the
  caller doesn't belong to, before calling `transferService.ship(...)`.
- `receive()`: passes `claims.branchId()` into `transferService.receive(request, claims.branchId())`
  — the destination-branch check is delegated to the service, ahead of any write (see below).
- `pending()`: `authz.authorizeView(...)` then `AccessDeniedException` when
  `!branchId.equals(claims.branchId())` — mirrors `StockLevelController`'s established
  own-branch-only pattern.

**Code verification — `TransferService.java` `receive()` (lines 159-171):** the transfer is loaded
via `transferRepository.findByIdAndTenantId(...)`, then `transfer.getToBranchId().equals(receivingBranchId)`
is checked and `AccessDeniedException` thrown on mismatch — **this check precedes
`tenantRegistryService.registerTenant(tenantId)` (line 175) and all stock/lot/movement writes**,
confirming a denied caller performs zero side effects. Comment at line 163-165 explicitly documents
this ordering intent ("This precedes registerTenant() so a denied caller performs no side effect at
all"), and the code matches the comment.

**Test verification — `TransferAccessControlIT.java`:** read in full, 7 `@Test` methods present:
1. `viewOnlyPrincipal_isDeniedOnShip_andNoTransferOutMovementWritten` — OPA-permission denial path
2. `viewOnlyPrincipal_isDeniedOnReceive_andNoTransferInMovementWritten` — OPA-permission denial path
3. `inventoryManager_succeedsOnShipAndReceive` — happy path, receive performed by a manager at the
   correct destination branch
4. `managerAtOwnBranch_cannotShipFromAnotherBranch` — CR-1 cross-branch ship denial; asserts 403 +
   zero `TRANSFER_OUT` movements + zero `TRANSFER_SHIPPED` outbox rows
5. `managerAtNonDestinationBranch_cannotReceive` — CR-1 cross-branch receive denial; asserts 403 +
   zero `TRANSFER_IN` movements + zero `TRANSFER_RECEIVED` outbox rows, against a real seeded
   SHIPPED transfer
6. `managerCannotListAnotherBranchesPendingTransfers` — GET /pending own-branch-only; asserts 403
7. `managerListsOwnBranchesPendingTransfers` — GET /pending happy path; asserts 200 + correct
   `toBranchId`/`status` in the response body

All CR-1-relevant tests (4, 5) assert both the 403 status AND the absence of any movement/outbox
side effect, correctly proving the guard fires before mutation, not just that the HTTP response is
wrong. Test count matches claim (7/7). **RESOLVED.**

### Additional fixes verified (CR-2, CR-3 — commit `20a78f7`, not original blockers but confirmed non-regressive)

**CR-2 — `PurchaseOrderService.java`:** the vendor-item catalog price-derivation path (around line
118-124) now throws `VendorItemCatalogMismatchException` when `currentPriceById.get(lineReq.vendorItemId())`
returns null, instead of silently defaulting to a 0 price. Inline comment explicitly documents the
bug this closes: a zero-priced line would under-report `po.totalPaisa`, which `submit()` feeds into
`requiredTiersForAmount(...)`, potentially lowering a real PO's required approval tier. **Confirmed
present and correctly reasoned.**

**CR-3 — `CreatePurchaseOrderRequest.java`:** `Line.qty` is now annotated `@NotNull @Positive
BigDecimal qty` (line 34), rejecting zero/negative quantities at the DTO validation layer before
they can reach total/tier computation. **Confirmed present.**

Both fixes are additive input/exception guards on the purchasing PO-line derivation path already
verified as SC-6/SC-7 in the original report; no change to catalog-picker UI, vendor-item schema, or
spend-analytics wiring — no regression risk to those success criteria.
