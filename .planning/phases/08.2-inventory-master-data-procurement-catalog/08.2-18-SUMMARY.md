**Vendor detail page at `/app/purchasing/vendors/[id]` with a Catalog/Price-Changes section switcher, an add-or-edit catalog-item dialog with an edit-mode-locked ingredient link, an append-only price-recording dialog, and filter-only category tags — closing PUR-07's UI half after `vendor_catalogues` existed in SQL with no frontend since purchasing V1.**

## Accomplishments

- `VendorItemFormDialog` — one dialog for add-or-edit a vendor catalog row. The linked-ingredient `CatalogItemCombobox` is disabled in edit mode with an explanatory note (re-pointing to a different ingredient means creating a new catalog item — the backend's `UpdateVendorItemRequest` has no ingredient field at all). Preferred/catch-weight are `aria-pressed` toggle buttons, matching the codebase's no-checkbox-primitive convention. Create mode only offers an initial price (rupees, converted to paisa) and effective-from date, which seeds the first append-only price row through the same `initialUnitPricePaisa` path the create endpoint already supports.
- `VendorItemPriceDialog` — the only vendor-item price write anywhere in this plan's files. Calls `useRecordVendorItemPrice` exclusively (no update-price hook exists to call instead), shows the current price via `MoneyDisplay` for comparison, and its description states verbatim that recording a price creates a new effective-dated row and the old price is kept for history, never overwritten.
- `VendorCategoryTags` — `aria-pressed` removable pills when `editable`, plain muted pills otherwise, backed by `useVendorCategories`/`useReplaceVendorCategories`. The "Used to filter and suggest — does not restrict what can be ordered." caption always renders, including when the tag list is empty, so the D-01 invariant reaches the user regardless of data state.
- `vendors/[id]/page.tsx` — the new routed detail page: back-link + vendor name/payment-terms/lead-time/contact header, editable category tags gated by `vendor.manage`, a `SectionSwitcher` (no Radix Tabs dependency) between Catalog and Price Changes. The Catalog `DataTable` shows vendor SKU/description/pack/order-unit/current-price/MOQ/lead-time/status/linked-ingredient with Edit/Record-new-price/Archive row actions (all permission-gated); Price Changes is a read-only report where a positive delta renders in the warning token with a `TrendingUp` icon and a negative delta in the success token with `TrendingDown` — colour is never the sole signal. `vendors/page.tsx` gained a "Manage catalog →" link per row.
- 6 component tests (`vendor-catalog.test.tsx`) driven through the real MSW purchasing handlers: recording a price appends to history without touching the old row's amount, the price dialog states the old price is never overwritten, the catalog row actions expose no in-place price-edit control, the category-tag caption renders whether the tag list is populated or empty, the linked-ingredient combobox locks (with its re-map note) in edit mode, and a positive delta carries a directional icon alongside its colour token.

## Decisions Made

- `VendorItemFormDialog`/`VendorItemPriceDialog` use the controlled-or-uncontrolled dialog shape (`open`/`onOpenChange`/`trigger` all optional, `useEffect` resets the form on open) rather than the plan text's literal trigger-only `VendorFormDialog` signature. This is necessary because the detail page's row actions open these dialogs from inside a `DropdownMenuItem`, which has no button of its own to host a `DialogTrigger` — the same reasoning `IngredientFormDialog` documents for its own extension of `VendorFormDialog`'s original shape (08.2-14).
- No single-vendor `GET` endpoint exists on the backend or in `PurchasingRepository`, so the detail page derives the vendor header from the existing `useVendors()` list (find-by-id) rather than inventing a new hook/endpoint — consistent with the plan's own note that the flat vendors list stays the place vendor header data lives.
- The price dialog's "branch scope" is a simple `aria-pressed` "this branch only / all branches" toggle (using the current user's `branchId`) rather than a full branch-select dropdown, since no `useBranches`/branch-list hook exists anywhere in the purchasing frontend and adding one was out of this plan's scope.
- Category-tag creation generates a client-side `crypto.randomUUID()` id for the array element sent in the `PUT` replace-set body; the server/mock is the source of truth for whatever id comes back on the next fetch — appropriate since these are filter/suggestion tags, never a real category-master foreign key.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Split `VendorDetailPage` to make it testable without fighting React's `use()`/Suspense timing**
- **Found during:** Task 3, writing `vendor-catalog.test.tsx`
- **Issue:** Rendering the page's default export directly (which does `const { id } = use(params)` on a `Promise<{ id }>`) left the component permanently suspended on the "Loading…" fallback in jsdom/Vitest — no prior test in this codebase exercises a dynamic-route page's `use(params)` pattern, so there was no established harness to copy.
- **Fix:** Extracted the entire page body into a named export, `VendorDetailPageContent({ vendorId }: { vendorId: string })`, taking a plain string prop. The default export is now a thin two-line wrapper: `const { id } = use(params); return <VendorDetailPageContent vendorId={id} />;`. Tests render `VendorDetailPageContent` directly with a plain string, sidestepping the Suspense/`use()` resolution timing entirely. Real app behavior is unchanged — Next.js still calls the default export with the real params Promise.
- **Files modified:** `frontend/app/(tenant)/app/purchasing/vendors/[id]/page.tsx`
- **Verification:** `npx tsc --noEmit` clean; all 6 tests in `vendor-catalog.test.tsx` pass.
- **Committed in:** `0257ef3` (Task 3 commit)

**2. [Rule 1 - Bug] Flattened the price-delta cell's text into one node for reliable rendering/testing**
- **Found during:** Task 3, writing the `priceChangeDeltaUsesAnIconNotColourAlone` test
- **Issue:** The delta cell originally interleaved three separate JSX expressions (`{icon}{"+"}{pct.toFixed(2)}%`) as siblings inside one `<span>` — functionally correct visually, but it produces multiple sibling text nodes that `testing-library`'s `getByText` cannot reliably match as one string, and is generally fragile markup.
- **Fix:** Wrapped the percentage text in its own inner `<span>{`${sign}${pct.toFixed(2)}%`}</span>`, keeping the icon as a sibling — a single text node per element, same visual output.
- **Files modified:** `frontend/app/(tenant)/app/purchasing/vendors/[id]/page.tsx`
- **Verification:** `npx tsc --noEmit` clean; `priceChangeDeltaUsesAnIconNotColourAlone` passes.
- **Committed in:** `0257ef3` (Task 3 commit)
