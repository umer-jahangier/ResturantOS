# Phase 08.2 Plan 02: Stock-Levels Read Model Summary

**GET /api/v1/inventory/stock — ingredient_branch_stock's first read path, OPA-gated and branch-pinned, with server-derived reorder/non-positive flags**

## Performance

- **Duration:** ~40 min
- **Started:** 2026-07-22T21:19:57Z (Task 1 commit)
- **Completed:** 2026-07-22T21:42:49Z (Task 3 commit)
- **Tasks:** 3
- **Files modified:** 6 (4 created, 2 modified — plus 1 additional repository fix, see Deviations)

## Accomplishments
- `ingredient_branch_stock` — write-only until now (receipts/transfers/counts/opening-balance) — has its first real read path: `GET /api/v1/inventory/stock`.
- Response carries ingredient name/sku/uom, qty on-hand, reorder point, avg cost, stock value, last-counted-at, and two server-derived flags (`belowReorderPoint`, `nonPositive`) so the frontend never re-derives warning/destructive row semantics itself.
- Ingredients with no stock row yet still appear (at zero on-hand) so a manager doesn't think a created-but-never-received ingredient vanished; archived ingredients are excluded unless they still hold nonzero stock.
- `StockLevelController` is gated through `InventoryAuthorizationService.authorizeView` (the OPA seam, not method-security annotations) and rejects any `branchId` query parameter that doesn't match the caller's JWT branch claim, before any data access.
- Fixed a real cross-tenant data leak discovered while writing the IT: `IngredientRepository.findByActiveTrue()` had no tenant predicate and was silently returning every tenant's active ingredients (surfaced as `4` items instead of `2` in the first test run). Added `findByTenantIdAndActiveTrue(UUID)` and switched the service to it.

## Decisions Made
- `categoryId`/`categoryName` are declared in `StockLevelDto` but populated as `null` in this plan — the ingredient DTO doesn't yet expose `item_categories` (that's 08.2-09's job), and the plan explicitly said not to add that dependency here. Declaring the fields now avoids a second frontend schema change.
- Used `ingredientRepository.findAllById(distinctIds)` for the bulk ingredient lookup exactly as the plan specified, rather than reusing the `findByTenantIdAndActiveTrue` list objects directly — this keeps the mapping loop's data source uniform (stock-only archived ingredients and always-included active ingredients both resolve through the same map) and satisfies the plan's explicit "no findById in a loop" acceptance criterion.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] Fixed cross-tenant leak in the active-ingredient master list query**
- **Found during:** Task 3 (writing `StockLevelsReadModelIT`) — the first test run returned 4 stock items instead of the expected 2, and the search-filter test returned 3 instead of 1.
- **Issue:** `IngredientRepository.findByActiveTrue()` has no `tenantId` predicate and relies solely on FORCE-RLS + the Hibernate tenant filter. Under the shared static-container test harness (and potentially in production connection-pooling scenarios), this returned active ingredients belonging to other tenants seeded earlier in the same JVM run — exactly the defect class 08.2-CONTEXT.md flags on `RecipeRepository.findByMenuItemIdOrderByVersionDesc`, which this plan's Task 1 was already told to avoid repeating for the new repository method. The pre-existing `findByActiveTrue()` had never been protected against it.
- **Fix:** Added `IngredientRepository.findByTenantIdAndActiveTrue(UUID tenantId)` (mirrors `MenuItemCatalogRepository.findByTenantIdAndActiveTrueOrderByNameAsc`'s existing pattern) and switched `StockLevelService.listStockLevels` to call it instead of the untenanted variant.
- **Files modified:** `services/inventory-service/src/main/java/io/restaurantos/inventory/repository/IngredientRepository.java` (not in the plan's declared `files_modified` list — added because the bug was directly blocking this plan's correctness), `services/inventory-service/src/main/java/io/restaurantos/inventory/service/StockLevelService.java`.
- **Verification:** `StockLevelsReadModelIT` now returns the expected item counts (2 total, 1 after search); full module regression (`mvn -pl services/inventory-service verify`) — 35 unit tests + 70 integration tests, 0 failures/errors.
- **Committed in:** `909c8c6` (part of the Task 3 commit).

## Issues Encountered
- **Environment-only, not a code issue:** running the module's integration tests locally required `RABBITMQ_USERNAME=restaurantos RABBITMQ_PASSWORD=dev_rabbit_2026` environment variables to match the dev-stack RabbitMQ container that happened to be running on the host during this session (Docker `restaurantos-rabbitmq`, port 5672). Without them, Spring Boot's default `guest`/`guest` credentials are rejected by the real broker (`ACCESS_REFUSED`), which blocks `@SpringBootTest` context startup for every IT in the module — unrelated to this plan's changes, reproduced identically against a pre-existing IT (`OpeningBalanceIT`) run in isolation. No code change was made for this; it is purely a local test-invocation detail (matches this project's `local-service-env.ps1` convention of sourcing `RABBITMQ_USER`/`RABBITMQ_PASSWORD` from `deploy/.env`).
- `mvn -pl services/inventory-service test` alone does **not** run integration tests — this module's `pom.xml` excludes `**/*IT.java` from surefire and binds them to failsafe's `integration-test`/`verify` goals instead. The plan's Task 3 acceptance criterion phrasing ("mvn ... test exits 0 (full module regression stays green)") is satisfied by `test`, but genuine full-module IT regression required `mvn -pl services/inventory-service verify`, which was run and passed (35 unit + 70 IT tests, 0 failures).
