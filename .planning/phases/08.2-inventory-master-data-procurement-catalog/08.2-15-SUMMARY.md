## Accomplishments

- `IngredientFormDialog.tsx`: one dialog for create and edit (mirrors `VendorFormDialog`'s shape, `RecipeFormDialog`'s `sm:max-w-2xl` scrollable-body sizing), with four grouped sections — General (name, short name, SKU — disabled in edit mode, required primary category, description, item type), Units (measure type, stock unit, recipe unit, default yield %, a static read-only purchase-UOM note, and a `useFieldArray` conversions line list), Stock (par level, reorder point, storage location, shelf-life days, an `aria-pressed` perishable toggle), and Compliance (`AllergenPillToggle` bound to `allergenCodes`). The server-computed `measureTypeLocked` flag disables the measure-type and stock-unit selects and wraps them in a `Tooltip` (plus a `title` attribute for synchronous testability) carrying the UI-SPEC's exact lock copy — never re-derived client-side.
- `ingredients/page.tsx`: the full INV-01/INV-14 screen — a `DataTable` grid (name with a muted short-name second line, a clickable category-name button that sets the category filter, stock unit, par level, reorder point, storage location, an active/archived `StatusBadge`, and a row-action `DropdownMenu` with Edit and Archive-or-Restore), a filter bar (debounced 300ms search, category select, status select defaulting to Active, and an `AllergenPillToggle` multi-select filter applied client-side), and an archive-confirmation `Dialog` using the Copywriting Contract's exact ingredient-archive string with no in-use refusal path (unlike categories).
- `IngredientFormDialog` gained an optional controlled `open`/`onOpenChange` pair (added during Task 2) so one shared dialog instance can serve both the header's "Add ingredient" trigger and every row's Edit action from inside a `DropdownMenu` — the identical architectural extension `CategoryFormDialog` needed in 08.2-14 for the same reason (a `DropdownMenuItem` has no button of its own to compose a `DialogTrigger` from).
- 6 component tests cover the required-primary-category client-side gate, both measure-type-lock directions (disabled+tooltip when locked, enabled when not), the conversions `useFieldArray` (add/remove tracked in the DOM), allergens rendering as `aria-pressed` pills with zero checkbox inputs anywhere, and edit-mode prefill across every grouped section (name, category, par level, storage location, allergens).

## Decisions Made

- `IngredientFormDialog` gained optional `open`/`onOpenChange` controlled props beyond the plan's literal `{ ingredient, trigger }` signature, reusing `CategoryFormDialog`'s exact 08.2-14 controlled-dialog pattern for the identical reason: a `DropdownMenuItem` row action has no button of its own to compose a `DialogTrigger` from, and the page needs one shared instance for both header-create and row-edit.
- The four outer grouped-section headings (General/Units/Stock/Compliance) use `text-sm font-semibold` (600 weight) rather than the `text-sm font-medium` the plan's action text literally suggested for "each" section. The UI-SPEC's binding Typography contract restricts `font-medium` (500) to exactly two mechanically-checkable forms: the `Label`/`FormLabel` primitive, and an `h3`/`h4` sub-heading sitting directly inside a `useFieldArray` dynamic-line-list matching `RecipeFormDialog`'s exact shape ("never... as a standalone hand-applied utility elsewhere"). Only the Conversions sub-list heading qualifies for that exception (and correctly uses `font-medium`); the four outer dividers use the standard 600-weight heading token instead, so the UI-SPEC's `font-medium` scope grep stays clean.
- SKU is shown (not hidden) in edit mode, disabled with a "can't be changed after creation" caption, rather than omitted from the General section entirely — `updateIngredientInputSchema` still excludes it from the wire payload, but this keeps the General section's layout stable across create/edit and signals immutability explicitly rather than silently.
- The ingredient grid's allergen filter uses OR semantics (a row matches if it carries any selected allergen code) — the UI-SPEC leaves the exact semantics unspecified for this filter; OR is the more common multi-select-filter UX ("show items containing peanuts or gluten").

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Accessible-name mismatches on three labelled selects, found while writing Task 3's tests**
- **Found during:** Task 3 (writing `editModePrefillsEveryGroupedSection` and the measure-type-lock tests)
- **Issue:** The "Primary category" select's `aria-label` ("Primary category") diverged from its visible `FormLabel` text ("Primary category *"); the conversions row's "From"/"To" selects had `aria-label="From unit"`/`"To unit"` while their `FormLabel`s read "From"/"To". A `<select>` labelled both by an associated `<label htmlFor>` and a differing `aria-label` produces an ambiguous accessible name and breaks `getByLabelText`-style queries (and, more importantly, is a genuine a11y defect — assistive tech would announce a name that doesn't match the visible label).
- **Fix:** Aligned every `aria-label` to match its `FormLabel`'s visible text exactly, mirroring `RecipeFormDialog`'s established convention (e.g. its "Ingredient"/"Qty"/"Unit"/"Yield %" row labels are each an exact `aria-label` match).
- **Files modified:** `frontend/components/inventory/IngredientFormDialog.tsx`
- **Verification:** `getByLabelText("Primary category *")`/`"From"`/`"To"` resolve to a single unambiguous element in `editModePrefillsEveryGroupedSection` and `conversionRowsCanBeAddedAndRemoved`; `npx tsc --noEmit` and `npx eslint` stayed clean.
- **Committed in:** `13261e4` (Task 3 commit)

**2. [Rule 3 - Blocking] `submitIsBlockedWithoutAPrimaryCategory` and `editModePrefillsEveryGroupedSection` timed out only under full-suite parallel contention**
- **Found during:** Task 3, running `cd frontend && npx vitest run` (the full-suite regression gate) after `npx vitest run components/inventory` had already passed 11/11 in isolation
- **Issue:** Both tests do multiple real-timer async round trips (typing, MSW-backed `useCategories`/`useUoms` fetches, `waitFor`) and exceeded vitest's default 5000ms per-test budget only when run inside the full suite (which also runs `__tests__/lib/eslint-boundary.test.ts` — a pre-existing, already-documented 08.2-14 flake of the identical class: CPU contention across parallel workers inflating a test's wall-clock time past its budget, not a logic defect).
- **Fix:** Gave both tests an explicit 15000ms timeout (third argument to `it(...)`), the standard mitigation for tests doing several real async round trips under a shared-runner's contention.
- **Files modified:** `frontend/components/inventory/__tests__/ingredient-form-dialog.test.tsx`
- **Verification:** Re-ran the full suite after the fix — 273/274 passing; only the pre-existing `eslint-boundary.test.ts` timeout remains, zero failures from this plan's own test file.
- **Committed in:** `13261e4` (Task 3 commit)
