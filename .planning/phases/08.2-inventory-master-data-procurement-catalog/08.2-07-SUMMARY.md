# Phase 08.2 Plan 07: Recipe Cost-Preview Endpoint Summary

**Non-persisting `POST /api/v1/inventory/recipes/preview` — batch/portion cost, food-cost %, and per-line plate-cost share, computed with batched repository reads and BigDecimal-only arithmetic that degrades gracefully per-line instead of failing the whole request.**

## Performance

- **Duration:** ~50 min
- **Tasks:** 3 (all `type="auto"`, no checkpoints)
- **Files modified:** 4 modified, 3 created (7 total)

## Accomplishments

- Added `PreviewRecipeCostRequest`, `RecipeCostLineDto`, `RecipeCostPreviewDto` records to `RecipeDtos.java`, additive alongside 08.2-03's three-state coverage records
- Implemented `RecipeCostPreviewService` — batches ingredient/UOM/stock lookups into three queries total (never one per line), reuses `UomConverter.effectiveBaseQty` and reads `IngredientBranchStock.avgCostPaisa` (the same value COGS is valued at), and degrades per-line (unknown ingredient, unknown UOM, dimension mismatch, or an ingredient never costed) with the UI contract's exact warning copy instead of throwing
- Added `POST /api/v1/inventory/recipes/preview`, gated at `inventory.item.manage` (not view) and rejecting any request `branchId` that doesn't equal the caller's JWT `branchId`
- 9 Mockito unit tests (arithmetic, degradation, zero-division safety, food-cost % rounding, yieldPct application) + 4 MockMvc/Testcontainers integration tests (hand-computed batch cost, non-persistence proof, foreign-branch rejection, view-only rejection)
- Full inventory-service module regression (`mvn verify`): 25 unit + 92 integration tests, all green — no regression to the existing depletion/receipt/transfer/count suites

## Decisions Made

- Gated `POST /preview` at `inventory.item.manage`, not `inventory.item.view` — per-ingredient moving-average cost is commercially sensitive (T-08.2-071); the recipe authoring surface that calls this endpoint already requires manage.
- Dimension-compatibility rule: a UOM is valid for an ingredient when its code IS the ingredient's own `baseUomCode`, or its declared `baseUnitCode` equals it. Anything else excludes the line with a warning rather than silently applying a wrong-dimension `toBaseFactor`.
- Used the UI-SPEC's exact warning copy verbatim ("Couldn't price this line — check the unit conversion for {ingredient}") for every degradation case, since the contract specifies one string, not per-case copy.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Added missing batch-lookup repository methods**
- **Found during:** Task 1 (RecipeCostPreviewService implementation)
- **Issue:** The plan requires "every referenced UOM code in ONE query" and "the `IngredientBranchStock` rows for `(tenantId, branchId, ingredientIds)` in one query," but `UnitOfMeasureRepository` only had a single-code `findByCode`, and `IngredientBranchStockRepository` had no batch-by-ingredient-set lookup. Without these, the service would need a per-line query, violating T-08.2-074 (DoS via unbounded query fan-out) and the plan's explicit "no per-line repository calls" instruction.
- **Fix:** Added `UnitOfMeasureRepository.findByCodeIn(Collection<String>)` and `IngredientBranchStockRepository.findByTenantIdAndBranchIdAndIngredientIdIn(UUID, UUID, Collection<UUID>)` — both simple additive Spring Data derived-query methods on existing repositories, not a schema or architectural change.
- **Files modified:** `services/inventory-service/src/main/java/io/restaurantos/inventory/repository/UnitOfMeasureRepository.java`, `services/inventory-service/src/main/java/io/restaurantos/inventory/repository/IngredientBranchStockRepository.java`
- **Verification:** `mvn -pl services/inventory-service -DskipTests compile` exits 0; the service issues exactly 3 batched queries regardless of line count (verified by reading the implementation — no loop-scoped repository calls)
- **Committed in:** `9be99b1` (Task 1 commit)

## Acceptance-Criteria Note (transparency, not a failure)

Two of the plan's literal `grep -c` acceptance-criteria bullets don't match verbatim, though the underlying invariant they're checking for is satisfied:

- `grep -c 'findAllById' RecipeCostPreviewService.java` returns **1**, not "at least 2." The plan's phrasing assumed a second `findAllById`-named call for the stock batch load, but `IngredientBranchStock`'s primary key is its own `id`, not `ingredientId` — a true `findAllById` can't express the `(tenantId, branchId, ingredientId IN …)` composite lookup the task requires. The batching invariant itself (one query per lookup kind, never per-line) is satisfied via `IngredientBranchStockRepository.findByTenantIdAndBranchIdAndIngredientIdIn`, just under a different, more accurate method name.
- All other acceptance-criteria greps (save/saveAll/delete/flush count 0, double/float count 0, `UomConverter.effectiveBaseQty` count 1, `RecipeCostPreviewDto` count ≥2, `@PostMapping("/preview")` count 1, `authorizeManage` count ≥2) match exactly, and `mvn -pl services/inventory-service -DskipTests compile` / `mvn -pl services/inventory-service verify` both exit 0.
