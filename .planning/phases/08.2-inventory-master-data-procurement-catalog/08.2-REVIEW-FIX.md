## Fixed Issues

### CR-01: Stock-transfer receive has no state guard — a transfer can be received more than once

**Files modified:** `services/inventory-service/src/main/java/io/restaurantos/inventory/service/TransferService.java`
**Commit:** de73b75
**Applied fix:** Added a `SHIPPED`-only precondition in `receive(...)`, thrown before any write
(after the destination-branch guard, before `registerTenant()` and all stock mutation). A
non-`SHIPPED` transfer now raises `StateInvalidException`, so a duplicate submit / at-least-once
retry / deliberate replay can no longer re-increment destination `qtyOnHand`, re-pollute the
moving-average cost, insert duplicate lots/movements, or re-emit `TRANSFER_RECEIVED`. This mirrors
the sibling `PurchaseOrderService` lifecycle methods that assert source state before mutating.
Imported `io.restaurantos.shared.exception.StateInvalidException` (already used elsewhere in the
service and mapped by the shared exception handler).

_Note: the reviewer additionally suggested a `@Version` optimistic-lock column on `StockTransfer`.
That was intentionally NOT applied here — it requires a schema migration and column addition that
is a larger design decision outside a focused review-fix. The status precondition is the
load-bearing correctness fix; the `@Version` hardening is left as a follow-up._

### WR-01: `TransferService.ship` does not validate available stock / allows self-transfer

**Files modified:** `services/inventory-service/src/main/java/io/restaurantos/inventory/service/TransferService.java`
**Commit:** 8b964f9
**Applied fix:** Added two guards to `ship(...)`: (1) a self-transfer rejection when
`fromBranchId == toBranchId`, thrown up-front; and (2) an insufficient-on-hand check
(`stock.getQtyOnHand().compareTo(qty) < 0`) inside the per-ingredient loop, after the row is
locked/loaded and before the decrement. This prevents driving aggregate on-hand negative at
`unitCostPaisa = 0` (a GL-posting hazard for Phase 9) while preserving the intentional FEFO
floor-at-zero behavior on individual lots. Both raise `StateInvalidException`.

### WR-02: `PurchaseOrderService.create` never validates the PO `vendorId`

**Files modified:** `services/purchasing-service/src/main/java/io/restaurantos/purchasing/service/PurchaseOrderService.java`
**Commit:** e49f783
**Applied fix:** Injected `VendorRepository` into `PurchaseOrderService` and, at the top of
`create(...)`, resolve + tenant-check the vendor (`findById(...).filter(tenant match)
.orElseThrow(ResourceNotFoundException)`) before building the PO — mirroring
`VendorItemService.requireVendor`, which every catalog write already goes through. Closes the
legacy ingredient-typed line path that previously had no empty-catalog 422 backstop and would
persist an orphan PO against a nonexistent/foreign vendor.

### WR-04: PO lifecycle methods use unscoped `findById`

**Files modified:** `services/purchasing-service/src/main/java/io/restaurantos/purchasing/repository/PurchaseOrderRepository.java`, `services/purchasing-service/src/main/java/io/restaurantos/purchasing/service/PurchaseOrderService.java`
**Commit:** e172586
**Applied fix:** Added `Optional<PurchaseOrder> findByIdAndTenantId(UUID id, UUID tenantId)` to
`PurchaseOrderRepository` and routed all five lifecycle lookups (`withdraw`, `send`, `get`,
`close`, `getDraft`) through it with `tenantContext.requireTenantId()`, throwing
`ResourceNotFoundException` on miss. This matches the `StockTransferRepository.findByIdAndTenantId`
/ `IngredientRepository.findByTenantIdAndId` precedent and removes reliance on the Hibernate tenant
filter / RLS alone for single-PO reads and mutations.

### WR-05: `VendorItemPriceService.currentPrice` can return a branch-specific row

**Files modified:** `services/purchasing-service/src/main/java/io/restaurantos/purchasing/service/VendorItemPriceService.java`
**Commit:** e06c1bf
**Applied fix:** Added a `.filter(p -> p.getBranchId() == null)` before `findFirst()` in the
single-item `currentPrice(vendorItemId, at)` lookup, so it returns the tenant-wide price —
consistent with `VendorItemService.currentPricesByItem` and
`PurchaseOrderService.currentPricesByItem`, which both already filter to `branchId == null`. The
single-item endpoint, catalog list, and PO-line derivation now agree about "the current price" in
this money-bearing path instead of "whichever row sorts first."

### WR-06: `VendorAnalyticsService.spendReport` does not validate the reporting window

**Files modified:** `services/purchasing-service/src/main/java/io/restaurantos/purchasing/service/VendorAnalyticsService.java`
**Commit:** 327069d
**Applied fix:** Added window validation at the first lines of `spendReport(...)`: reject an
inverted primary window (`to.isBefore(from)`) and, when both explicit compare bounds are supplied,
an inverted compare window (`compareTo.isBefore(compareFrom)`), each raising `StateInvalidException`.
Prevents `ChronoUnit.DAYS.between(from, to)` going negative and silently inverting/extending the
derived prior window.

## Skipped Issues

### WR-03: Purchasing V5 tables use `ENABLE ROW LEVEL SECURITY` without `FORCE`

**File:** `services/purchasing-service/src/main/resources/db/migration/V5__vendor_item_catalog.sql:51-53, 83-85, 111-113`
**Reason:** Skipped by design decision. This is a schema/migration change that ties directly into
the repo-wide deferred RLS-activation posture documented in project MEMORY ("pos/kitchen RLS
owner-bypass": tenant RLS is intentionally `ENABLE`-not-`FORCE` because the app owns the tables;
isolation is enforced at the service layer, with a deferred FORCE-RLS activation package staged in
`deploy/pending-migrations/`). Adding `ALTER TABLE ... FORCE ROW LEVEL SECURITY` to these three
purchasing tables in isolation would diverge from that coordinated activation plan and risks
locking the app role out of its own tables at runtime. The service layer here already scopes every
query by `tenantId` (and WR-04's fix further hardens the PO path), so the isolation invariant holds
without this change. Recommend folding these three tables into the deferred RLS-activation package
rather than a one-off migration. Per the fix directive, risky schema decisions are documented and
deferred rather than auto-applied.
**Original issue:** `vendor_items`, `vendor_item_prices`, and `vendor_categories` enable RLS but
never `FORCE` it and grant full DML to `purchasing_user`; if that role owns the tables, PostgreSQL
bypasses the `tenant_isolation` policy, making it advisory-only — inconsistent with this phase's own
inventory migrations (`V5__item_categories.sql`, `V6__ingredient_master_data.sql`) which use both
`ENABLE` and `FORCE`.
