# Phase 08.2 Plan 08: Vendor Item Catalog + Append-Only Pricing API Summary

**VendorItem/VendorItemPrice/VendorCategory entities, services and a 9-endpoint REST API putting Java behind the purchasing V5 vendor catalog schema — append-only effective-dated pricing, filter-only category tags, no permission codes added.**

## Performance

- **Duration:** ~55 min
- **Tasks:** 3 completed
- **Files modified:** 20 (18 new, 2 exception-shape fixes discovered mid-plan)

## Accomplishments
- `VendorItem`/`VendorItemPrice`/`VendorCategory` JPA entities mapped column-for-column to `V5__vendor_item_catalog.sql`, each `extends TenantAuditableEntity`, with javadoc stating the append-only and never-authorizes invariants.
- Tenant-scoped repositories, including a batched `findCurrentForVendorItems` query so a catalog page's current prices resolve in ONE query rather than fanning out per row.
- `VendorItemService`: catalog list/create/update/archive (no repository delete anywhere — archive sets `archivedAt`), duplicate-SKU 409 rejection, optional initial price on create delegated to the price service, and category replace-set (delete+insert in one transaction).
- `VendorItemPriceService.recordNewPrice` is the only writer of `VendorItemPrice` rows: closes the prior open row's `effectiveTo` and inserts a new row, rejects a backdated `effectiveFrom`, and never touches a prior row's `unitPricePaisa`. `priceChanges` walks each catalog item's history chronologically in one batched query with HALF_UP scale-2 percentage deltas.
- `VendorItemController`: 9 endpoints, reusing only `vendor.view`/`vendor.manage` (no new permission codes), no `@DeleteMapping` anywhere, no category reference in any authorization expression.
- `VendorItemCatalogIT` (10 MockMvc tests) and `VendorItemPriceAppendOnlyIT` (6 direct-service tests) — full purchasing-service module `mvn verify`: **71/71 ITs green**, no regression.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] New domain exceptions must extend a type GlobalExceptionHandler already dispatches on, not bare `@ResponseStatus`**
- **Found during:** Task 3, while writing `duplicateVendorSkuForTheSameVendorIsRejected` and running the new ITs
- **Issue:** The plan's own precedent in this service (`InvalidPoStateException`, `DuplicateApproverException`, `ApprovalLimitExceededException`) is a bare `RuntimeException` annotated `@ResponseStatus`. Copying that shape for the new `DuplicateVendorSkuException` (409) produced an actual HTTP 500 in the IT run. Root cause: `GlobalExceptionHandler` is a `@RestControllerAdvice` with `@ExceptionHandler(Exception.class)` as a catch-all; Spring's `ExceptionHandlerExceptionResolver` always resolves an exception through the closest-matching `@ExceptionHandler` in the class hierarchy before `ResponseStatusExceptionResolver` (which reads `@ResponseStatus`) is ever consulted. Since a bare `RuntimeException` has no closer handler than `Exception.class`, the annotation is silently ignored. This means the three pre-existing local exceptions above have never actually been proven to return their annotated status through a real HTTP round trip anywhere in this module (all existing coverage of them is `assertThatThrownBy` at the service layer, never MockMvc `.andExpect(status()...)`), so this is a latent pre-existing defect, not something this plan introduced — this plan only avoided reproducing it.
- **Fix:** Duplicate-SKU rejection now throws the shared-lib `StateInvalidException` (already wired to a dedicated `@ExceptionHandler(StateInvalidException.class)` → 409). `BackdatedPriceException` was changed to extend `RestaurantOsException` so `GlobalExceptionHandler`'s dedicated `@ExceptionHandler(RestaurantOsException.class)` resolves it to 400. The three pre-existing local exceptions (`InvalidPoStateException`, `DuplicateApproverException`, `ApprovalLimitExceededException`) are unchanged — fixing them is out of this task's scope (scope boundary: only fix issues directly caused by the current task's changes) and is flagged here for a future gap-closure plan.
- **Files modified:** `service/VendorItemService.java`, `exception/BackdatedPriceException.java` (deleted the broken `DuplicateVendorSkuException.java`)
- **Verification:** `VendorItemCatalogIT#duplicateVendorSkuForTheSameVendorIsRejected` asserts 409; `VendorItemPriceAppendOnlyIT#backdatingBeforeTheOpenRowIsRejected` asserts `BackdatedPriceException` is thrown
- **Committed in:** `28ed822` (Task 3 commit)

**2. [Comment rewording, not a behavior change] Avoided two literal grep trigger-words in javadoc**
- **Found during:** Task 1 and Task 2, running the plan's own acceptance-criteria greps
- **Issue:** `grep -c 'ingredientId' UpdateVendorItemRequest.java` and `grep -c '@DeleteMapping' VendorItemController.java` matched explanatory javadoc prose (not code), the same class of false-positive the 08.2-04 plan documented and fixed the same way.
- **Fix:** Reworded both javadoc comments to describe the same invariant without the literal trigger string.
- **Files modified:** `dto/UpdateVendorItemRequest.java`, `web/VendorItemController.java`
- **Committed in:** `08de986`, `d900934` (part of the respective task commits, before the acceptance-criteria greps were re-run)
