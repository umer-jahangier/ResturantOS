# Phase 20 — UI Design Contract (Full UI/UX Revamp)

> Visual and interaction contract for the complete ResturantOS frontend revamp.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Every colour number in this document was measured**, not estimated — computed with
> the repo's own `colorjs.io@0.6.1` (`frontend/node_modules/colorjs.io`) using the
> identical WCAG 2.1 relative-luminance algorithm as
> `frontend/lib/theme/wcag-validator.ts:9-38`, so any value here can be re-derived by
> the existing validator. CVD figures use the Viénot, Brettel & Mollon (1999)
> linear-RGB dichromat matrices; separation is ΔE2000.

---

## 0. What this contract is calibrated against

The user's brief said "award winning". For a POS/ERP that does **not** mean a showcase
marketing site. It means the craft standard of dense, fast, keyboard-first tools:
**Linear, Stripe Dashboard, Vercel, Height, Retool, Notion.**

The specific mechanisms borrowed, and what each buys:

| Borrowed from | Mechanism | What it buys the user |
|---|---|---|
| Linear | Command palette as the *primary* navigator; every action has a keystroke | A cashier or accountant who learns 6 keys stops using the mouse. Makes the two-tier nav (§5) survivable — if you can't find it, you type it. |
| Linear | One persistent "focused row" concept distinct from hover/selection | Enables the KDS bump bar (§7.2) and DataGrid keyboard model (§7.4) to share one mental model. |
| Stripe Dashboard | Data density with generous *vertical* rhythm; numbers right-aligned and tabular | A 50-row GL fits on one screen and still scans. |
| Stripe Dashboard | Empty states that teach the next action, never "No data" | 30+ ERP list screens currently dead-end (§4.7). |
| Vercel | Typographic restraint — few sizes, two weights, hierarchy by weight+colour not size | Removes the ad-hoc `text-2xl`/`text-xl` drift (see `components/dashboard/tenant-dashboard.tsx` vs `app/(tenant)/app/purchasing/purchase-orders/page.tsx`). |
| Retool | Chrome recedes; the data is the interface | Justifies deleting the page-transition animation (§6). |

**Explicitly rejected as defects for this product class:** scroll-jacking, parallax,
hero animation, entrance animation on navigation, unconventional/gestural navigation,
auto-playing carousels, and any motion on a data update. On a screen an operator hits
200 times a shift, motion is latency.

## 2. Brand colour — the D-UI-01 decision

D-UI-01 delegated the hue but demanded justification. **Chosen hue: `195` (deep
teal-cyan).** The whole system regenerates from this one number.

### 2.1 Why 195, numerically

The existing semantic hues are already sound and are kept: `--success` 149.6,
`--warning` 86.0, `--info` 237.3, `--destructive` 27.3 (`frontend/app/globals.css:80-86`).
That leaves four gaps on the hue circle. The widest usable gap is 149.6 → 237.3 (87.7°),
and **195 is within 2° of its midpoint**, maximising distance from both neighbours
simultaneously:

| Pair | Δhue | ΔE2000 (500 vs 500) |
|---|---|---|
| primary(195) vs success(149.6) | **45.4°** | 24.6 |
| primary(195) vs info(237.3) | **42.3°** | 26.7 |
| primary(195) vs warning(86) | 109.0° | 44.8 |
| primary(195) vs destructive(27.3) | 167.7° | 62.2 |

This directly satisfies **D-UI-01 constraint 4** ("semantic colours must not collide with
the brand hue"). It also improves on the earlier `uiux-direction.md §3.3` recommendation
of hue 178, which sits only **28.4°** from `--success` — a real risk on a KDS ticket
where brand chrome and a "fresh" ticket share a screen.

Separation is reinforced by chroma and lightness, not hue alone: the primary ramp peaks at
C 0.116 while `--success-500` sits at C 0.145, and the two never appear at the same
lightness in the same component.

### 2.2 Why teal and not the alternatives

| Candidate | Rejected because |
|---|---|
| **Indigo / violet (~275)** | Numerically the safest gap (237→27 wraps 150°) and the Linear/Stripe default — but it reads as generic dev-tool SaaS, and it loses luminance headroom on the permanently-dark KDS surface where a bright cyan stays legible at 2 m. |
| **Green (~140)** | Collides with `--success`, the single most safety-critical semantic in the product (a KDS "fresh" ticket). D-UI-01 constraint 4 says semantics win. |
| **Red / orange (~30)** | Collides with `--destructive` *and* `--warning`, and is the fast-food cliché the product should not wear. |
| **Amber (~85)** | Collides with `--warning`, which the KDS uses for the mid-ageing state. |
| **Teal 178** (prior recommendation) | Only 28.4° from `--success` — see §2.1. 195 dominates it on every measure at zero cost. |

Teal-cyan reads hospitality-adjacent (fresh, clean, service) without being "organic
health food" green, and it is the one hue that stays vivid on both a white office
monitor at noon and a near-black bar terminal at midnight — D-UI-01 constraint 5.

### 2.3 Regenerability — D-UI-01's hard requirement

> "the ramp must be regenerable by changing one hue value — do not hard-code hex values throughout."

Satisfied literally. Every stop is authored as `oklch(<L> <C> var(--brand-h))`. Changing
`--brand-h: 195;` to any other number regenerates the primary ramp, the neutral ramp
(which carries the same hue at C ≤ 0.010), the sequential ramp, and `--chart-1`.

```css
:root { --brand-h: 195; }
--primary-600: oklch(0.6060 0.1034 var(--brand-h));
```

`var()` substitution inside `oklch()` is computed-value-time substitution and is
supported by every browser that supports `oklch()` itself.

**Tenant override path.** `frontend/lib/theme/palette-generator.ts` already produces an
11-stop OKLCH ramp from one hex and validates it with `wcagContrastCheck`
(`palette-generator.ts:37-80`). It currently emits only `--primary*`
(`frontend/app/api/theme/route.ts:40-58`). Extend that route to also emit `--brand-h`
plus `--chart-1` and the `--seq-*` ramp derived from the tenant hue, leaving
`--chart-2..5` and all semantics fixed — a tenant may brand the product, but must not be
able to break chart distinguishability or the meaning of red. The generator itself is
kept as-is.

Neutrals carry the brand hue at imperceptible chroma so surfaces harmonise instead of
reading as dead grey — and so they regenerate from `--brand-h` too. 13 stops: `0` and
`1000` are added beyond the 50→950 range because light mode needs a true white above
`--neutral-50` and dark mode needs a surface below `--neutral-950`.

| `--neutral-600` | `oklch(0.5080 0.0100 h)` | `#5f6767` | text-tertiary | **`--border-interactive`** |

| `--neutral-950` | `oklch(0.1680 0.0060 h)` | `#0c1010` | text-primary | surface-1 (cards) |
| `--neutral-1000` | `oklch(0.1320 0.0060 h)` | `#050808` | | surface-0 (page) |

**Two border tokens, deliberately.** WCAG 2.2 SC 1.4.11 requires 3:1 only for boundaries
that *identify a component or its state*; a table gridline is decorative and exempt.
Conflating the two is why most design systems fail 1.4.11.

| Token | Light | Dark | Requirement |
|---|---|---|---|
| `--border` (decorative: gridlines, dividers) | `--neutral-200` — 1.23:1 | `--neutral-800` — 1.49:1 | none (exempt) |
| `--border-strong` (card/section edges) | `--neutral-300` — 1.47:1 | `--neutral-700` — 2.28:1 | none (exempt) |
| `--border-interactive` (input, checkbox, select, switch, unchecked control) | `--neutral-500` — **3.77:1** | `--neutral-600` — **3.48:1** | **≥3:1 — PASS** |

Any control the user can operate uses `--border-interactive`. This is a change from
today: `frontend/components/ui/input.tsx` uses `border-input` = `oklch(0.922 0 0)`,
which measures **1.23:1** on white and fails 1.4.11.

### 3.4 Chart series — five, CVD- and greyscale-verified

D-UI-01 constraint 3 required verification "with a deuteranopia/protanopia simulation,
not by eye", varying lightness so the series survive greyscale. Both were done, and the
result overturned the obvious answer.

**The Okabe–Ito palette was tested and rejected.** It is the standard published
CVD-safe qualitative set, so it was the first candidate. Measured with the brand teal
substituted as series 1:

| Metric | Okabe–Ito derived | **Adopted set** |
|---|---|---|
| min ΔE2000, deuteranopia | 8.0 (teal/purple) | **17.3** |
| min ΔE2000, protanopia | 10.2 (teal/purple) | **16.1** |
| min ΔE2000, normal vision | 21.1 | **26.9** |
| **min ΔL, greyscale** | **0.001** (bluish-green 0.620 vs vermillion 0.621 — indistinguishable when printed) | **0.060** |
| min contrast vs surface | 2.25:1 (fails 1.4.11) | **3.11:1** |

Okabe–Ito optimises hue separation under dichromacy; it was never designed for greyscale
survival, and it cannot absorb an externally-fixed brand anchor. Both are hard
requirements here, so the set was solved directly under all four constraints at once.

**Adopted set.** One hue per series across both themes, so a series keeps its identity
when the theme flips. Greyscale rank order is preserved across themes (chart-5 < chart-3
< chart-2 < chart-1 < chart-4), so relative visual weight never inverts.

| Token | Hue | Light | Hex (light) | Dark | Hex (dark) |
|---|---|---|---|---|---|
| `--chart-1` (brand) | 195 | `oklch(0.6200 0.1057 195)` | `#019a9a` | `oklch(0.7000 0.1194 195)` | `#00b5b5` |
| `--chart-2` | 35 | `oklch(0.5600 0.1900 35)` | `#cb380d` | `oklch(0.6400 0.1900 35)` | `#e8542f` |
| `--chart-3` | 262 | `oklch(0.5000 0.1900 262)` | `#1e59cd` | `oklch(0.5800 0.1900 262)` | `#3672e9` |
| `--chart-4` | 300 | `oklch(0.6800 0.1900 300)` | `#ac77fa` | `oklch(0.8800 0.0689 300)` | `#deceff` |
| `--chart-5` | 345 | `oklch(0.4400 0.1871 345)` | `#920069` | `oklch(0.5200 0.1900 345)` | `#ae2881` |

Measured guarantees:

| Guarantee | Light | Dark |
|---|---|---|
| min ΔE2000 deuteranopia | **17.3** (chart-1/chart-4) | **15.8** (chart-1/chart-4) |
| min ΔE2000 protanopia | **16.1** (chart-3/chart-4) | **15.6** (chart-1/chart-4) |
| min ΔE2000 normal vision | **26.9** | **34.8** |

Green hues 100–165 were excluded from the search space so no chart series can be mistaken
for `--success`. `--chart-2` at hue 35 sits near `--destructive` (27.3), which is
acceptable because `--destructive` never renders as a chart series — but a chart must
never place a red *alert marker* on a `--chart-2` series.

**Redundant encoding is mandatory, not optional.** A minimum ΔE of ~16 is good but not
absolute; no five-colour categorical palette is safe under dichromacy by colour alone.
Every multi-series chart MUST additionally carry **direct series labels at the line end**
(preferred, Stripe-style) **or** distinct dash patterns / point markers. A legend keyed
only by colour swatch is a contract violation.

### 3.10 Spacing scale

8-point grid, 4px half-steps. Tailwind's default `spacing` already matches; this table
fixes *usage*, which is what actually drifts.

| Token | Value | Usage |
|---|---|---|
| `xs` | 4px | Icon-to-label gap, chip inner padding |
| `sm` | 8px | Compact element spacing, table cell y-padding (compact density) |
| `md` | 16px | Default element spacing, card padding, table cell x-padding |
| `lg` | 24px | Section padding, page gutter (< 1024px) |
| `xl` | 32px | Layout gaps, page gutter (≥ 1024px) |
| `2xl` | 48px | Major section breaks |
| `3xl` | 64px | Page-level spacing, empty-state vertical padding |

**Exceptions — declared, and only these:**

| Exception | Value | Why |
|---|---|---|
| Control heights | 28 / 32 / 36 / **44** / 56px | Multiples of 4. 44px = WCAG 2.2 SC 2.5.5 (AAA) target size; 56px = POS tile/action minimum. |
| Space rail width | 64px | 4×16, holds a 24px icon + 20px padding each side. |
| Space panel width | 240px | 8×30. |
| Order ticket panel | 360px | 8×45. Today `w-80` = 320px (`components/pos/pos-terminal.tsx:223`) — too narrow for a modifier line plus quantity stepper plus money without truncation. |
| Shell bar height | 56px | 8×7. |
| Table row heights | 32px compact / 44px comfortable | Both on the 4-grid; 44 = touch target. |

`app/(tenant)/layout.tsx:93` hard-codes `p-4 lg:p-6` on `<main>`, which is why no page
can be full-bleed.

### 3.11 Typography

Geist Sans throughout; Geist Mono for identifiers only (order numbers, SKUs, journal
refs). **Exactly two weights** — 400 regular and 600 semibold. Hierarchy comes from
weight and colour, not from a ladder of sizes.

| Role | Token | Size / line-height | Weight | Usage |
|---|---|---|---|---|
| Display | `--text-display` | 30 / 36px (1.2) | 600 | Operator numerals only — order total, till count |
| Heading | `--text-h1` | 20 / 28px (1.4) | 600 | Page title — exactly one per page |
| Subheading | `--text-h2` | 16 / 24px (1.5) | 600 | Card / section title |

three places and misses others.

### 3.12 Radii, elevation, motion, z-index

**Radius.** `--radius: 0.5rem` (8px), down from the current `0.625rem` (10px)

unchanged and simply re-derives. POS tiles override to `0.75rem` where the larger surface
earns it.

**Elevation.** Four levels only. Shadows are near-neutral (chroma 0) so they do not tint.

| Token | Value | Usage |

## 6. Density, responsive breakpoints & chrome policy

**Chrome policy.** The data is the interface. Chrome recedes: no page-transition
animation (`page-transition.tsx` deleted, §10), no decorative illustration outside empty
states, no gradient, no glassmorphism, no shadow on a flat surface. Every pixel of
chrome must earn its place by answering "where am I", "what can I do here", or "what
changed".

**Density.** Two levels, set by a `data-density` attribute on the grid root and persisted
per user per table (following Toast's per-user-per-device precedent for its order table).

| Density | Row height | Cell padding | Font | Default for |
|---|---|---|---|---|
| `comfortable` | 44px | 12px y / 16px x | `--text-body` 15px | Touch contexts, first use |
| `compact` | 32px | 6px y / 12px x | `--text-sm` 13px | Finance, GL, stock — dense back office |

**Breakpoints.** Tailwind defaults, with declared behaviour:

| Range | Shell | Data surfaces |
|---|---|---|
| < 640px | Bottom tab bar; shell bar collapses to brand + search icon + avatar | DataGrid → **card list** (each row a stacked card with 3 primary fields + a chevron). Tables do not scroll horizontally on phones |
| 640–1023px | Rail+panel in a Sheet | DataGrid with 4–5 pinned columns, rest behind "Columns ▾" |
| 1024–1279px | Rail 64px, panel collapsed to icons | Full DataGrid; toolbar wraps to two rows |
| ≥ 1280px | Rail + expanded panel | Full DataGrid, single-row toolbar |
| ≥ 1920px | As above; content max-width 1600px for reading surfaces, full-bleed for grids | Grids use the width |

POS targets 1280×800 landscape tablet as the design origin and must work at 1024×768.
KDS targets 1920×1080 landscape wall-mounted and must not require scrolling to see the
oldest ticket.

### 7.1 POS Order Terminal — `app/(operator)/pos/**`

**Grid vs search-first — resolved, not chosen.** Every vendor ships both, and the split
is by service model, not preference. The contract is: **a persistent search field that
never loses focus, with the grid underneath as the default surface.** Typing filters;
`Enter` adds the top match; `Esc` clears and returns focus to search. This is already the
structure of `menu-grid.tsx`; only the sizing is wrong.

**Three service models, one screen.**

| Model | Flow | Screen behaviour |
|---|---|---|
| **Order-first** (dine-in, QSR counter) | build ticket → `Send` to kitchen → `Charge` later | Both actions enabled. `Send` primary-solid, `Charge` success-solid |
| **Bill-first** (fine dining, table service) | table selected → lines accumulate across courses → `Charge` closes | Table selector required before first line; `Send` fires per course; held orders list in the top strip |
| **Self-checkout / kiosk** | customer builds → pays | Categories column hidden, tiles at 128px, ticket panel becomes a bottom sheet, `Send` hidden, only `Pay`. Toggled by terminal config, not by a separate codebase |

**Modifiers.** Tapping a tile with modifier groups opens a **Sheet from the right**
(not a dialog — a dialog steals the whole screen and loses cart context), 480px wide:
required groups first with a `--danger` "Required" chip until satisfied, optional after;
each option a 56px row with a checkbox/radio at 44px hit area and a price delta;
`Add to order` button 56px, disabled with helper text ("Choose a spice level") until all
required groups are satisfied. Frequently-used modifiers get dedicated tiles on the
Favourites page so the common case costs zero navigation.

**Held orders.** Top strip shows `Held (n)`. Opens a popover listing held tickets by
table/customer with age; `Enter` resumes. A held order is a saved cart in the existing
offline outbox — no new persistence concept.

**Split bills.** `Charge` opens the charge surface with a `Split ▾` control offering:
*by amount* (numeric keypad, remaining balance always visible), *by item* (checkbox list,
two-column: unassigned / assigned per payer), *evenly by N* (stepper 2–12). Each split
part is its own payment row with its own tender type. **Invariant, displayed at all
times: `Assigned + Remaining = Total`.** The Charge button is disabled while
`Remaining ≠ 0`, with helper text naming the shortfall.

**Favourites page.** The default landing category is a staff-editable Favourites tile
page. v1 supports reorder and 1×1 / 2×1 tile size, stored as data (not developer-authored
layout). This is Square's operator-configurable model, reduced to the part that carries
most of the value.

**Keyboard mode.** A single-click toggle in the categories column switches to a
counter-biller mode: item codes typed, `Enter` commits, quantity via `*` prefix
(`3*` then code = qty 3). Tiles remain visible but shrink to 64px. This is Petpooja's
dual-mode idea, which is worth taking outright — a high-volume counter biller wants a
keyboard, a floor server wants a tablet, and they are the same shift in different hours.

### 7.2 KDS / BDS Station Board — `app/(kitchen)/kitchen/[stationCode]`

**Legibility at 2 metres is the governing constraint.** Item lines at `--text-kds`

The current card truncates all items into one comma-joined line
(`formatItemNames` + `truncate`, `kds-ticket-card.tsx:27,171`). That is unreadable at
2 m and must go: **one item per line, modifiers bold and inline beneath the item, notes

**Ticket face.**

**Bump-bar focus model.** USB bump bars enumerate as HID keyboards, so keyboard bindings
*are* bump-bar support. Two structural requirements the current board lacks entirely:
**every ticket carries a visible position number** (that is what makes number-key jump
work), and there is a **persistent "focused ticket" concept distinct from hover or
selection**, rendered as `--kds-card-focus` plus a 2px `--kds-text` outline.

| Key | Action |
|---|---|
| `↑` | Previous ticket — bottom→top, right→left |
| `↓` | Next ticket — top→bottom, left→right |
| `1`–`9`, `0` | Jump directly to the ticket showing that position number |
| `PageUp` / `PageDown` | Previous / next ticket page, focus resets to top-left |
| `Enter` | Open ticket detail; confirm; acknowledge a flashing ticket |
| `F` | Fulfil focused ticket (or focused item in item mode) |
| `R` | Recall last — un-fulfil the most recently bumped ticket |
| `V` | Toggle display of recently fulfilled tickets |
| `M` | Ticket menu — Rush / Print |

> **[UNVERIFIED — hardware check required before finalising.]** This key map mirrors
> Toast's documented bump-bar *functions*. Which bump-bar hardware the target market
> uses, and what scan codes it emits by default, is unconfirmed. Bind through the
> shortcut registry (§9.2) with a per-station remap table so a hardware mismatch is a
> config change, not a code change.

**Bump behaviour.** `F` bumps optimistically: the card collapses to a 1px line and is
removed after 400ms (the only animation permitted on this screen, because it confirms a
destructive-ish action). Bumping writes through the existing offline outbox; on failure
the card returns with a `--danger` "Not bumped — retry" chip. `R` restores the last
bumped ticket for 60 seconds.

**Station filtering.** Header (48px) carries: station name, ticket count, `All items ▾`
vs `By category ▾` routing mode, an "Only my station" toggle, and a connection dot. Per
Lightspeed KDS 2.0, ticket face fields are configurable per station — Customer, Order ID,
Covers, Server, Type, Floor, Source, Pickup time as independent toggles — and the "New" /
"Ready to collect" columns can be deactivated when the workflow does not need them.

**Ageing.** Keep `getAgingTreatment`'s fraction logic (`kds-ticket-card.tsx:77-86`)
exactly — it scales with the station's own `escalationThresholdSeconds` rather than a
fixed 5/8-minute convention, which is more principled and already correct. Keep the
shared clock (`lib/hooks/kds/use-kds-clock.ts` — one interval for all cards) and
`sortKdsTickets` in `station-board.tsx`. Only the colours become tokens (§3.7) and the
redundant encoding is added.

**Grid.** 4 columns at 1920, 3 at 1440, 2 at 1024. Tickets never scroll horizontally.
If tickets exceed one page, the page indicator shows `2 / 3` and the oldest page is
always page 1.

**BDS.** Identical component, different `station_type` (KITCHEN / BAR / EXPO) — one
board, parameterised. No forked codebase.

### 7.3 Role dashboards — `app/(tenant)/app/dashboard`

Today `components/dashboard/tenant-dashboard.tsx` shows every role the same four neutral
stat cards (closed sales, active orders, menu items, dining tables), which serve neither
an owner nor a manager.

**The dashboard is not a page; it is a container of role-assigned portlets.** Owner and
manager do not get the same page with different numbers — they get different portlet
sets. Presets ship as **data**, not as `if (permissions.includes(...))` branches.

| | **Owner** — "is the business healthy?" | **Manager** — "what needs me in the next five minutes?" |
|---|---|---|
| Time frame | This week / month vs prior | **Today, live** |
| **First thing seen** | Net sales + gross margin %, all branches | **Open orders + tickets over threshold** |
| Row 1 | KPI row: Net sales · Gross margin % · Labour % of sales · Covers — each with delta vs prior period and a sparkline | KPI row: Open orders · Late tickets · Till variance · Staff clocked in |
| Row 2 | Branch comparison table (sales, margin, labour by branch) — a DataGrid | Live order list + station load |
| Row 3 | Trend chart: sales vs labour, 8 weeks | Items 86'd |
| Exceptions | Voids/comps above threshold · negative-margin items · AP due this week | Late tickets · unapproved timesheets · till sessions open past close |
| Primary action | **Drill to report** | **Act now** — open the ticket, approve the till |
| Density | `comfortable` | `compact` — a manager scans, an owner reads |

A third preset, **Cashier**, shows only: my till state, my open orders, and a single
`Open POS` action at 72px. A cashier landing on an analytics dashboard is a bug.

**Portlet types for v1:** `KpiTile`, `TrendChart`, `RankedList` (top items,
worst-margin items), `ExceptionList`, `RecordList`, `Shortcuts`. **Every portlet has a
drill target** — a KPI you cannot click is a poster, not a dashboard. Every portlet
declares its permission; a portlet the user cannot see is **omitted from the layout**,
never rendered as an error or an empty box.

**Post-login routing** sends each role to its landing surface: Cashier → `/pos`,
Kitchen staff → `/kitchen`, Manager/Owner/Admin → `/app/dashboard`, Platform admin →
`/platform/tenants`.

Charts land here and only here — Recharts is imported in dashboard route segments only
(Next 16 code-splits per route) and **never on the POS path**, because its dependency
tree includes `@reduxjs/toolkit`, `react-redux`, `immer` and `victory-vendor`.

```
└─ Footer    "Showing 1–50 of 1,284" · page size · pagination
```

**Filter semantics (explicit, because ambiguity here is a data-integrity bug).**
Filters *within the same group* combine with **OR**; filters from *different groups*
combine with **AND**. Custom filters offer "Match **all** of the following rules" /
"Match **any** of the following rules", and rule branches nest with independent logic.
The active filter set is always visible as removable facet chips — never hidden in a
panel. Group By is layered: the first grouping is primary, each subsequent one
subdivides.

**Saved views.** Name · "Default for me" (becomes the view loaded on arrival) · "Share
with my team". Editable, archivable, deletable. Stored server-side per user per table
key.

**All grid state lives in the URL** — `?q=&f=&g=&sort=&page=&size=&view=&density=`.
Non-negotiable: it is what makes a grid state shareable in a support conversation, and it
is entirely absent today.

**Data volume policy.**

| Rows | Strategy |
|---|---|
| Known-small, bounded sets (< 200, e.g. branches, tax rates) | Client-side filter/sort/paginate — opt-in via `manualPagination={false}` |
| Everything else | **Server-side pagination, sorting and filtering by default** |
| Rendered rows > 200 | Row virtualisation via `@tanstack/react-virtual` |

Pagination (not infinite scroll) is the default for ERP lists: an accountant needs "page
7 of 42" to be a stable, citable location.

**Inline edit.** Double-click (or `Enter` on a focused cell) on permitted fields.
Optimistic with rollback, modelled on the existing `lib/offline` outbox pattern.
`Esc` cancels, `Enter` commits, `Tab` commits and moves right. A failed commit restores
the prior value and shows a cell-level `--danger` state with the reason.

**Wiring bug to fix.** `components/ui/data-table.tsx:65` calls
`table.getFilteredRowModel()` but `getFilteredRowModel` is **never registered** in the
`useReactTable` config (lines 44-52 register only core, sorted and pagination models).
It silently falls through to the core row model, so filtering can never work even if a
filter UI were added, and the "Showing 1–50 of N" count is wrong the moment a filter
exists. Register `getFilteredRowModel`, `getFacetedRowModel`, `getFacetedUniqueValues`,
`getGroupedRowModel`, `getExpandedRowModel`.

**Backward compatibility.** The grid grows behind **optional props**
(`enableFiltering`, `enableGrouping`, `enableColumnVisibility`, `enableRowSelection`,
`virtualize`, `manualPagination`, `savedViewKey`), all defaulting off, so the 4 existing
call sites compile and behave identically on day one. This is the same additive pattern
the file already documents for `rowClassName` (`data-table.tsx:25-32`).

**Required states — all eleven.**

| State | Contract |

| Loading (initial) | Skeleton rows matching column count and density — `components/skeletons/data-table-skeleton.tsx` exists, keep it |

modal trap.

## 8. Copywriting Contract

**Voice:** plain, specific, second person, present tense. Say what happened and what to
do next. Never "Oops", never "Something went wrong", never an error code alone, never
blame the user.

| Element | Copy |
|---|---|
| **Primary CTA — POS** | `Charge` (never "Submit", "Proceed", "Continue") |
| **Primary CTA — POS secondary** | `Send to kitchen` |
| **Primary CTA — list screens** | `New purchase order` / `New journal entry` / `Add ingredient` — always verb + the specific noun, never "Create" or "Add" alone |
| **Primary CTA — wizard** | `Continue` (advance) / `Finish setup` (final step) |
| **Empty state heading** | `No purchase orders yet` — noun + "yet". Never "No data" |
| **Empty state body** | `Create your first purchase order to start tracking vendor spend.` — one sentence, states the value, names the next action |
| **Empty — no results** (distinct) | `No purchase orders match these filters.` + `Clear filters` button |
| **Empty — no permission** | `You don't have access to purchasing.` + `Ask your administrator to grant the "vendor.view" permission.` — names the actual permission code |
| **Empty — offline** | `You're offline. 3 orders are queued and will sync automatically.` |
| **Error state** | `Couldn't load purchase orders.` + `The purchasing service didn't respond. Check your connection, then try again.` + `Retry` button |
| **Error — validation** | `Enter a quantity greater than 0.` — states the rule, not "Invalid input" |
| **Error — conflict** | `This purchase order was changed by Ayesha 2 minutes ago. Reload to see the latest version.` + `Reload` |
| **Error — period closed** | `The accounting period for 2026-07 is closed. Reopen the period or post to 2026-08.` — offers both real paths |
| **Loading (>2s only)** | `Loading purchase orders…` — never a bare spinner without context on a full-page load |
| **Success toast** | `Purchase order PO-1043 approved.` — names the record. Auto-dismiss 4s |
| **Offline queued** | `Saved offline. This order will sync when you reconnect.` |

**Destructive actions — every one, with its confirmation approach.**

| Action | Approach | Confirmation copy |
|---|---|---|
| **Void order** | `AlertDialog` + **required reason** (select + optional note) | `Void order #1043?` / `This reverses the order and its kitchen tickets. The reason is recorded in the audit trail. This can't be undone.` → `Void order` (danger) |
| **Refund payment** | `AlertDialog` + reason + amount confirmation | `Refund PKR 1,995 to card ending 4412?` / `The refund posts to the general ledger immediately.` → `Refund PKR 1,995` — **the button restates the amount** |
| **Delete draft journal entry** | `AlertDialog` | `Delete draft journal entry JE-2201?` / `This draft hasn't been posted, so no ledger entries change.` → `Delete draft` |
| **Close accounting period** | `AlertDialog` + **type the period code** | `Close period 2026-07?` / `No further entries can be posted to 2026-07 unless you reopen it. Type 2026-07 to confirm.` → `Close period` |
| **Suspend tenant** (platform) | `AlertDialog` + **type the tenant name** + reason | `Suspend {tenant}?` / `All {n} users lose access immediately. Open orders are preserved. Type {tenant} to confirm.` → `Suspend tenant` |
| **Impersonate tenant** (platform) | `AlertDialog` + type tenant name + reason, then a persistent banner | `Impersonate {tenant}?` / `You'll act as an administrator of this tenant. Every action is recorded against your account in the audit trail.` → `Start impersonation` |
| **Bump ticket** (KDS) | **No dialog** — optimistic, with `R` to recall for 60s | Toast: `Ticket #1043 bumped. Press R to undo.` |
| **Remove a sent order line** (POS) | Inline confirm chip on the line, not a dialog | `Remove? The kitchen has already seen this item.` → `Remove` / `Keep` |
| **Remove an unsent line** (POS) | **No confirmation** — instant, undoable via toast | Toast: `Removed 1× Naan.` + `Undo` |
| **Clear cart** | `AlertDialog` | `Clear this order?` / `All 6 items will be removed. Nothing has been sent to the kitchen yet.` → `Clear order` |
| **Delete saved view** | `AlertDialog` | `Delete the "Overdue POs" view?` / `Only you use this view.` (or `4 teammates use this shared view.`) → `Delete view` |

Rule: **confirmation friction scales with reversibility.** Instant + undo for reversible
actions (removing an unsent line, bumping a ticket); a dialog for consequential ones; a
typed confirmation only where the action is irreversible or affects other people.
Confirming an unsent cart line would be friction theatre; not confirming a period close
would be negligence.

## 9. Accessibility & Interaction

Target: **WCAG 2.2 AA across the product, AAA for text a cashier reads under time
pressure** (D-UI-01 constraint 2). §3.8 records the measured ratio for every pairing.

### 9.1 Focus management

- `:focus-visible` uses **`outline`, not `ring`** (§3.9). `ring` is a `box-shadow` and is
  clipped by `overflow: hidden`; the DataGrid, POS grid and KDS board are all scroll
  containers. This is a real bug in `globals.css:157-159` today.
- Focus is **never** removed without replacement.
- Dialog/Sheet/Drawer: focus moves to the first interactive element (or the heading if
  none), is trapped, and returns to the trigger on close — Radix provides this; do not
  override it.
- Route change: focus moves to the `PageHeader` `<h1>` (`tabIndex={-1}`), and the page
  title is announced.
- Deleting a row moves focus to the next row, or to the empty state if it was the last.
- A skip link (`Skip to main content`) is the first focusable element in every shell.

### 9.2 Shortcut registry

One `lib/hooks/use-hotkeys.ts` (Layer 3, no new dependency) replaces bespoke
`document.addEventListener` calls — `command-palette.tsx` has one today, and adding six
more independently is how shortcut conflicts and leaked listeners happen.

Requirements: a single documented keymap; scoped registration (a shortcut lives while its
surface is mounted); **never** intercept a key while focus is in a text input except
`Esc` and `⌘K`; a `?` overlay listing every active shortcut for the current surface; and
per-station remapping for the KDS bump bar.

### 9.3 Screen-reader semantics — DataGrid

- `<table>` with `<caption class="sr-only">` naming the dataset and the active filters.
- `<th scope="col">` on every column header — **currently missing everywhere**;
  `data-table.tsx:76` renders bare `<th>`.
- Sortable headers: `<th aria-sort="ascending|descending|none">` wrapping a `<button>`;
  the button's accessible name includes the action ("Sort by vendor, ascending").
- Row selection: `aria-selected` on `<tr>`, and a real `<input type="checkbox">` with an
  `aria-label` naming the row ("Select purchase order PO-1043"), never an unlabelled box.
- Selection count is announced through a polite live region ("12 of 50 rows selected") —
  `components/ui/status-announcer.tsx` already exists for this; reuse it.
- Loading: `aria-busy="true"` on the table, not a swap to a spinner (which destroys the
  accessibility tree).
- Pagination announces "Showing 1 to 50 of 1,284" via the same live region.
- Inline edit: the cell's editing state is announced, and commit/cancel is confirmed.

### 9.4 Screen-reader semantics — POS grid

- `role="grid"` on the tile container, `role="row"` per row, `role="gridcell"` per tile.
- **Roving tabindex**: exactly one tile has `tabIndex={0}`, all others `-1`. Tab-per-tile
  is unusable at rush — a 60-item menu means 60 tab stops between the search box and the
  cart.
- Each tile's accessible name is `"{item} — {price}{, unavailable}"`. An 86'd tile is
  `aria-disabled="true"` and states why.
- Adding to cart announces politely: `"Added 1 Chicken Karahi. Order total 1,995 rupees."`
- The order ticket is `role="list"`; each line is `role="listitem"` with its full label.
- The running total is a polite live region — assertive would interrupt on every tap.
- Modifier sheet: `role="dialog"`, labelled by the item name; required groups use
  `aria-required` and `aria-describedby` pointing at the "Required" chip.

### 9.5 Keyboard-drivable POS — the standard

**A POS that needs a mouse is a slow POS.** The complete order flow — search item, add,
set quantity, apply a modifier, send to kitchen, charge, tender cash, print — must be
completable without a pointing device. §7.1 defines the key map. This is verified by an
end-to-end Playwright test that performs a full order **using keyboard events only**, and
that test is a merge gate for the POS plans.

### 9.6 Reduced motion

`@media (prefers-reduced-motion: reduce)` already neutralises animation
(`globals.css:228-237`) — keep it verbatim. Additionally, under reduced motion:

- The KDS bump collapse becomes an instant removal.
- Sheets and dialogs cross-fade at 0ms rather than sliding.
- Sparklines and charts render final state directly, with no draw-in.
- Skeleton shimmer (`globals.css:222-226`) becomes a static `--surface-2` fill.

Because there is no page-transition animation at all (§3.12), the largest motion offender
disappears for everyone, not just users who ask.

### 9.7 Other

- **Touch targets:** ≥ 44×44 CSS px on POS, KDS and every mobile surface (SC 2.5.5 AAA);
  ≥ 24×24 with adequate spacing in back-office dense tables (SC 2.5.8 AA). Currently
  `button.tsx` tops out at 36px and `input.tsx` at 32px.
- **Colour is never the only channel.** Enforced for: status (icon + label — already
  correct in `status-badge.tsx`), KDS ageing (border width + icon + text, §3.7), chart
  series (direct labels or dash patterns, §3.4), variance (sign glyph + parentheses,
  §3.6), and onboarding step state (icon + text, §7.6).
- **Zoom:** usable at 200% zoom and at a 320px logical width without horizontal scrolling
  (SC 1.4.10). DataGrid becomes a card list below 640px (§6).
- **Verification:** all a11y claims here are derived from source and specification. **No
  screen-reader or axe run has been performed.** An axe-core sweep plus one NVDA and one
  VoiceOver pass over POS, KDS and one DataGrid screen is required before this phase can
  be marked verified.

## 10. Migration Strategy

**The app must keep working at every commit.** The plan is additive at every layer:
Layers 1–3 (`lib/api-client/`, `lib/repositories/`, `lib/adapters/`, `lib/models/`,
`lib/hooks/`) are **not touched at all**. The revamp lives entirely in Layer 4. Three new
dependencies, all additive, none replacing anything: `@tanstack/react-virtual@3.14.9`,
`recharts@3.10.1`, and optionally `@hookform/resolvers@5.7.1`. No removals; no version
bumps to Next, React or Tailwind.

### 10.1 How old and new coexist

Four mechanisms, each chosen so the two systems can share a screen:

1. **Token aliasing.** New role tokens (`--surface-1`, `--foreground-secondary`, …) are
   *added*; the existing names (`--background`, `--primary`, `--card`, `--border`) are
   *repointed* at the new ramps. Every untouched component picks up the new palette
   automatically with no code change. This is what makes step 2 a one-file commit that
   visibly transforms the whole app.
2. **Additive props.** `DataGrid` grows optional props defaulting off, so the 4 existing
   `DataTable` call sites compile and behave identically.
3. **Additive CVA sizes.** `Button`/`Input` gain `touch`/`pos` sizes; `default` is
   unchanged, so back office is untouched.
4. **Route groups.** POS and KDS move to `app/(operator)/` and `app/(kitchen)/`. Old
   routes remain as thin redirects for one milestone so bookmarks, the mobile nav and any
   printed QR codes keep working.

### 10.2 Sequence — each step independently shippable

### 10.3 What proves no regression at each step

Five gates, applied per step:

1. **Visual regression.** A Playwright screenshot set covering all 53 route `page.tsx`
   files, captured **before step 2**. Every subsequent step diffs against the previous
   step, not against the original — so intentional change is reviewed once and then
   becomes the new baseline.
2. **Machine-checked contrast.** A unit test that walks the §3.8 table through the
   existing `wcagContrastCheck` (`lib/theme/wcag-validator.ts`) and fails the build if any
   pairing drops below its stated threshold. The numbers in this document become
   executable.
3. **Permission-matrix test** (step 5 and after). Six role fixtures × the full nav config;
   the visible set must be byte-identical to the pre-revamp sidebar. This is the gate that
   protects the genuinely good permission work already in the codebase.
4. **Preserved-logic unit tests.** `cart-reducer.ts`, `sortKdsTickets`,
   `use-kds-clock.ts`, `getAgingTreatment`, `zod-resolver.ts` — these files are **not
   modified**, so their existing tests must stay green unchanged. A change to any of them
   is a signal the revamp has overreached.
5. **Money invariants.** For every converted list screen, the sum of the money column
   before and after conversion must match exactly. Paisa `BIGINT` handling is not a design
   concern, but a rendering change is exactly how a formatting bug enters.

### 10.4 Rollback

Steps 1–10 are individually revertable commits. Steps 11 and 12 keep the old route as a
redirect for one milestone, so rollback is a redirect flip rather than a revert. Step 2
(the token layer) is a single-file change and therefore the cheapest possible rollback
despite having the widest visual reach — which is precisely why it is sequenced early.
