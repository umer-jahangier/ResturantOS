<objective>
Prove the phase, and write down exactly what is left for the printer.

26-CONTEXT states seven definition-of-done items and says each is verifiable by command or browser
journey, never by opinion. This plan produces the commands and the journey, and it does one thing
none of the earlier plans can: it asserts the printed document against a document the live server
produced, rather than against the checked-in fixture every unit suite uses. A fixture proves the
renderer; a live run proves the wiring.

It also produces the hardware sign-off list. D-26-02 requires that the items genuinely needing U3 be
listed explicitly in the summary rather than left implied, and that only the things no emulator can
settle appear on it. Each earlier plan wrote its own section; this plan consolidates them into one
document a person can take to a shop counter.

Purpose: definition-of-done items 1 through 7, and D-26-02's explicit-list requirement.
Output: a live end-to-end script, a browser journey, and `HARDWARE-SIGNOFF.md`.
</objective>

    agent's renderer over a document through the emulator.

    Create `phase26-printing-e2e.sh` with one section per definition-of-done item, each printing PASS
    or FAIL and the script exiting non-zero on any failure.

    Item one — a cashier settles an order and gets a correctly totalled bill with no thermal printer
    attached. Create an order through the gateway, settle it in full with cash, issue the print
    document, and assert the document's amounts against the order read back from the API.

    Item two — the ESC/POS stream is asserted against an emulator including cut and drawer. Take the
    document the live server just produced, render it through the agent's renderer with a known
    printer entry, decode it with the emulator, and assert the decoded render contains the same lines
    and amounts, exactly one cut, and exactly one drawer pulse after that cut. This is the assertion
    that ties the server's output to the byte layer rather than trusting a fixture.

    Item three — a reprint produces an identical document and is distinguishable as a reprint. Issue
    a second time, compare the two bodies field by field excluding the issue block, and assert the
    reprint flag and sequence.

    Item four — totals match the order and the ledger to the paisa. Read the order's total from the
    POS API, read the posted journal entry for that order from the finance API, and assert all three
    figures agree as integers. This is the item that would have caught the hundredfold defect, and
    it must compare three sources rather than two: a receipt agreeing with an order that disagrees
    with the ledger is still a wrong receipt.

    Item five — the FBR regions render when populated and collapse when not. Assert the live document
    carries a fiscal region with every field null, then inject a document with a populated invoice
    number through the agent's renderer and assert the decoded render contains it. Phase 27 is not
    implemented; this proves the region is wired, which is what D-26-03 asks for.

    Item six — a tenant with no printer configured still gets a bill. Clear a branch's printer
    configuration, settle an order, issue the document, and assert it is produced with no drawer
    instruction and that no unroutable job was written for the receipt.

    Item seven — enumerate the hardware items. Print the contents of `HARDWARE-SIGNOFF.md` at the end
    of the run so the list travels with the evidence.

    Every money assertion reads both sides in the same run. No literal amounts anywhere in the
    script.

    When no fake-printer sink can be started, or the agent cannot run, report the affected assertions
    as SKIPPED with the reason and exit with a distinct status so a pass-with-skips is never mistaken
    for a clean pass.
  </action>
