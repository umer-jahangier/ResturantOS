<objective>
Close definition-of-done item 3: a reprint of a past order produces an identical document and is
distinguishable as a reprint.

The server half is already built — 26-03 stores the rendered document on the issuance row and
re-serves it verbatim, and 26-05's receipt component already renders the reprint band because the
issue metadata was in the schema from the start. What is missing is the cashier's way in, and the
proof that "identical" means identical bytes rather than two runs of an assembler that happened to
agree on a Tuesday.

That distinction is the whole plan. A restaurant reprints a bill when a customer loses one, when a
card machine jams, or when an auditor asks. In every one of those situations the reprint has to be
the same document, and it has to be obvious that it is a second copy.

Purpose: definition-of-done item 3, and the operational reality that bills get lost.
Output: a reprint control on the order list, a server-side byte-identity test, and a browser proof.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a past order to a new piece of paper | A financial document is reissued after the sale completed |
| the stored document to the reprint | Bytes written at one moment are served at another, after the world has changed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-26-08-A | Tampering | A reprint that differs from the original | critical | mitigate | Stored bytes are re-served; the drift cases (rename, reprice, refund) are integration tests that fail loudly if the implementation ever re-assembles |
| T-26-08-B | Repudiation | An unmarked duplicate presented as a second bill | high | mitigate | Every issue after the first carries a reprint band with its sequence and the original issue time; a human checkpoint confirms it is unmistakable |
| T-26-08-C | Repudiation | Untracked reissues | high | mitigate | Every reprint writes an issuance row; the count is assertable by query and is asserted in the browser test |
| T-26-08-D | Tampering | Double allocation from a double press | medium | mitigate | The control is disabled while the request is in flight, and the server's unique index is the backstop |
| T-26-08-E | Information Disclosure | Reprinting another tenant's or another user's order | critical | mitigate | The control is gated on order-view permission and the server refuses cross-tenant reads; the negative case is an integration test |
| T-26-08-F | Tampering | A reprint counted as a sale | high | mitigate | The reprint path writes only an issuance row; no order, payment or event is emitted, asserted by the existing lifecycle suites staying green |
| T-26-08-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan adds no package to any manifest. If one becomes necessary, halt and require the package-legitimacy audit plus a blocking human checkpoint |
</threat_model>
