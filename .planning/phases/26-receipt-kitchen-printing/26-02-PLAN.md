<objective>
Give the printer registry a validated, typed home, and settle in writing where tenant printing
configuration lives while Phase 17's tenant-configuration spine is still unbuilt.

The answer is not a new mechanism. `BranchEntity` already declares
`@Column(name = "receipt_config", columnDefinition = "jsonb")` at line 59, `BranchDtos` already
carries it on create, update and response, and `BranchService` already persists it — this was
verified in the repository, and the printing research (§9.5) independently names it as the right
home. What is missing is that the column is an unvalidated `String`: anything at all can be written
into it and nothing tells the caller their configuration is unusable.

Purpose: D-26-05 requires configuration that reaches terminal granularity, and the constraint in
26-CONTEXT is to follow Phase 17 rather than invent a parallel settings mechanism. Using the column
that Phase 17 will absorb honours both. The migration path is stated explicitly in the summary so
Phase 17 inherits a decision rather than a surprise.

Output: a typed receipt-configuration contract, a validating read/write endpoint pair, and the
frontend data layer for the configuration UI that plan 26-10 builds on top of it.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tenant admin to user-service | A branch's printing destinations are chosen by a human over HTTP |
| user-service to user_db | Configuration is written into a jsonb column on a tenant-scoped row |
| the configuration to the print agent | Host and port values become outbound TCP connections on the branch LAN |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-26-02-A | Tampering | Unvalidated jsonb write | high | mitigate | The write endpoint validates against a typed record before serialising; the legacy bare-string field on the branch DTO is left untouched but is no longer the printing path |
| T-26-02-B | Information Disclosure | Cross-tenant configuration read | critical | mitigate | Branch ownership is checked against the caller's tenant using the existing branch controller's check, and an integration test asserts the negative case |
| T-26-02-C | Information Disclosure | Secrets in a UI-readable config blob | high | mitigate | Prohibited outright; the agent credential is a separate hashed row introduced in 26-11 and never enters this column |
| T-26-02-D | Server-Side Request Forgery | Operator-supplied printer host and port | medium | accept | The value is supplied by an authenticated branch administrator and is dialled by the on-premise agent, not by any cloud service. The cloud never connects to it. Revisit if server-side direct printing is ever added |
| T-26-02-E | Denial of Service | An unrouted kitchen station | high | mitigate | The write response enumerates unrouted station codes; a silently incomplete configuration is the failure mode that presents as a kitchen that simply never prints |
| T-26-02-F | Elevation of Privilege | A weaker authority for printing than for branch settings | medium | mitigate | Both endpoints reuse the existing branch-management permission expression verbatim |
| T-26-02-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan adds no package to any manifest. If one becomes necessary, halt and require the package-legitimacy audit plus a blocking human checkpoint |
