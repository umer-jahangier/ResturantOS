<objective>
Define the one document every printer in this product will ever render, and the one place an
integer paisa amount becomes a string a human reads.

This is the load-bearing plan of Phase 26. Both renderers built later — the HTML bill (26-05) and
the ESC/POS byte stream (26-04) — consume this record and do no arithmetic. The server-side
assembler (26-03), the kitchen ticket (26-07) and the print agent (26-06) all speak it.

Purpose: `.planning/research/erp-completion/pos-printing.md` §9.3 decision 1 — "the browser never
emits bytes, it POSTs a document" — only holds if the document is defined first and defined once.
And D-26-04 ("money converts at the print layer and nowhere else") is only enforceable if there is
a single named function to point at.

Output: a shared-lib print package, a golden JSON fixture that is the wire contract, and its
TypeScript mirror.
</objective>

    - shared-lib/src/main/java/io/restaurantos/shared/money/Money.java — note the `double pkr` component. That field must never reach a print document.
    - frontend/lib/adapters/shared.ts — the frontend's `toMoney`, which formats with two fraction digits. The two sides currently disagree about how many digits a PKR amount has; this plan settles it for print.
  </read_first>
  <behavior>
    - An amount whose paisa remainder is zero renders with an explicit two-digit minor unit, so a bill never looks like it was rounded.
    - An amount with a non-zero paisa remainder renders that remainder exactly; a value of 123456 paisa must render a string ending in the remainder 56, and a test asserts this against the literal string, not against a re-formatting.
    - A negative amount (a discount line) renders with a leading sign and never as a bracketed accounting figure — a customer reads a receipt, not a trial balance.
    - Zero renders as a zero amount, not as an empty string or a dash. A tender row of zero must be visibly zero.
    - The largest value the domain can hold (Long.MAX_VALUE paisa) formats without overflow or scientific notation.
    - Parsing the rendered string back to paisa returns the input for every case above — the test performs this round-trip explicitly, which is the assertion that makes a hundredfold error impossible to ship.
    - The currency prefix is fixed and configurable per call from the branch's currency setting, defaulting to the PKR symbol used everywhere else in the product; it is never inferred from a JVM default locale, because a till's locale is not a business decision.
  </behavior>
  <action>
    Create a `print` package under shared-lib.

    `ReceiptAmount` is a record of an integer paisa value and its rendered string. It is the only
    money shape a print document may contain. Give it a static factory that takes paisa and the
    formatter, so constructing one with a mismatched pair requires deliberate effort.

    `ReceiptMoneyFormatter` is the single conversion site named by D-26-04. It takes integer paisa
    and returns the rendered string. Implement it with BigDecimal and an explicit scale of two,
    never with floating point, and never by delegating to `MoneyUtils.formatPkr` — that method
    fixes maximum fraction digits at zero, so it would round a bill to the nearest rupee and put
    the printed paper permanently out of agreement with the ledger. Record that reasoning in the
    javadoc so a later reader does not "simplify" the duplication away.

    Give the formatter a companion parse method used only by tests, so the round-trip assertion
    above is expressible without a second implementation of the format rules.

    Write `ReceiptMoneyFormatterTest` covering all seven behaviours, with the remainder case
    asserted against a hard-coded expected string.
  </action>
