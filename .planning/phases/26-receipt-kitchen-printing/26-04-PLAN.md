<objective>
Build the only code in this system that emits ESC/POS bytes, and the emulator that proves it right
without a printer in the room.

D-26-02 says everything except real-paper behaviour is verifiable against an ESC/POS emulator and
byte-level assertions on the generated command stream. This plan makes "an emulator" concrete: a
decoder in the test suite that consumes the produced stream, reconstructs the printer's state
machine (alignment, emphasis, size, codepage, the text it would have printed, where it cut, when it
pulsed the drawer) and **throws on any byte it cannot account for**. A test that only asserts "the
stream contains 1D 56" would pass on a stream that is otherwise garbage; a decoder that must
consume every byte will not.

Research §4 rejects WebUSB (Windows binds printer-class devices to `usbprint.sys` and Chrome cannot
claim them), Web Serial (a USB thermal printer enumerates as printer class, not as a COM port; and
Firefox requires a per-site add-on), and direct TCP from a browser (no such API outside ChromeOS
Isolated Web Apps). It recommends a local agent that owns the renderer. This plan is that renderer;
plan 26-06 is the agent around it.

Purpose: the ESC/POS tier is D-26-01's optimisation, not its requirement — so it must be provable
in CI on a laptop, or it will never be trustworthy.
Output: a new `print-agent` TypeScript package containing a pure renderer and its emulator.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a print document to the byte stream | Untrusted-shaped JSON becomes commands a physical device executes |
| the encoder library to the emitted bytes | A third-party package decides what reaches the printer |
| the renderer to the cash drawer | A software instruction opens a box of money |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-26-04-A | Tampering | Encoder library changing cut or pulse bytes | high | mitigate | Hexadecimal-literal assertions pinned to the Star specification fail the build on any change |
| T-26-04-B | Tampering | A malformed or truncated stream reaching a printer | high | mitigate | The emulator must consume every byte and throws on anything unclassified; a self-test proves it throws |
| T-26-04-C | Elevation of Privilege | An unauthorised drawer open | high | mitigate | The drawer pulse is emitted only when the document carries a drawer instruction, and the assembler only sets one for a cash tender; a test asserts the card-only case emits none |
| T-26-04-D | Denial of Service | An out-of-range pulse duration stalling a printer | medium | mitigate | Parameters validated against the specification's defined ranges and rejected rather than coerced |
| T-26-04-E | Information Disclosure | Customer tender data on a kitchen printer | medium | mitigate | The kitchen-ticket render is asserted to contain no amounts; the document schema already forbids the fields |
| T-26-04-F | Tampering | A legally required FBR symbol silently omitted | high | mitigate | A populated QR payload raises a named not-yet-implemented error rather than skipping the region |
| T-26-04-SC | Tampering | npm install of `@point-of-sale/receipt-printer-encoder` | high | mitigate | Blocking, non-auto-approvable human checkpoint in task 1 verifying the package on npm and GitHub before it enters any manifest; exactly one runtime dependency permitted |
</threat_model>

<hardware_signoff>
**Requires U3 (a physical 80 mm printer):**

1. **Whether the model performs the requested cut at all, and whether it degrades a partial cut to a
   full cut or vice versa.** The Star specification states plainly that models without an auto-cutter
   do not cut, and that models substitute the cut type they support. No emulator can answer this.
2. **Whether the drawer actually opens at the configured pulse duration on the customer's solenoid,
   and whether cutting immediately before the pulse browns out the supply.** Research §7.3 records
   the cut-before-drawer ordering as widely-held field practice that it could not confirm against a
   vendor document.
3. **The real columns-per-line for the model at its configured print width, font and codepage.**
   Deliberately unresolved by research §7.5.
4. **Whether the configured codepage renders Urdu glyphs correctly on the specific model.**

Everything else in this plan runs in CI.
</hardware_signoff>
