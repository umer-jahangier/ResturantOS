<objective>
Wrap the renderer in the daemon that research §9 concludes is the answer: a per-branch print agent
that owns a durable queue and the only socket in the system that talks to a printer.

Research §8's decisive column is "works if the tab closed". Every browser-direct transport fails it,
and during a service tills get locked, tablets sleep and Chrome kills background tabs. The agent is
what makes a print job survive the browser that raised it.

This plan builds the agent as a local service: loopback HTTP in, ESC/POS bytes out over
`socket://host:9100` or the operating system's own printer queue. The cloud-pull channel that lets
a kitchen ticket print with no tab open at all is plan 26-11; this plan is the machine that channel
will feed.

Purpose: D-26-01's ESC/POS tier and the cash-drawer kick in the scope fence both require a
component that can write bytes to a device, and no browser can.
Output: a runnable daemon with a durable queue, two transports, a health surface and a test print.
</objective>

  <behavior>
    - Enqueuing a job appends a record to a journal file on disk and forces it to storage before returning; a process killed immediately after the call still has the job on restart.
    - Loading a queue from an existing journal reconstructs exactly the jobs that were pending, with their attempt counts.
    - A job that fails delivery has its attempt count incremented and its next attempt scheduled with exponential backoff plus jitter.
    - A job reaching the attempt limit moves to dead-lettered and is never attempted again, but remains readable so a human can see what was lost.
    - Draining is single-flight: two concurrent drain calls do not deliver the same job twice, asserted by counting deliveries against a fake transport.
    - Compaction rewrites the journal dropping completed and dead-lettered records older than a retention window, and a crash during compaction leaves either the old or the new journal intact — never a half-written one.
    - A journal file containing a truncated final record (the shape a power cut produces) loads every complete record and discards only the partial one, and says so on a counter the health surface exposes.
    - Queue depth by status is readable without loading document bodies into memory.
  </behavior>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser to agent over loopback | An HTTPS page reaches a plain-HTTP local service |
| branch LAN to agent | Any device on the restaurant network can reach a LAN-bound agent |
| agent to printer over port 9100 | An unauthenticated, unencrypted protocol with no acknowledgement |
| agent to disk | Customer order and tender data is written to a local file |

<hardware_signoff>
**Requires U3 (a physical 80 mm printer):**

1. **Whether the model accepts one connection per job or expects a persistent connection.** The fake
   printer proves the agent's side; the device's tolerance is a device fact.
2. **Whether the printer reports paper-out or cover-open in any way the agent could observe.** Port
   9100 is fire-and-forget; some models expose status over a second channel and some do not. Until
   this is known the agent deliberately does not claim to know whether paper moved.
3. **Behaviour when the printer is powered off mid-job** — whether the socket refuses, accepts and
   discards, or accepts and prints on power-up.

**Explicitly NOT requiring U3:** the queue, its durability, the transport's byte fidelity, the
retry and dead-letter behaviour, and every server response shape. All are asserted against the fake
printer in CI.
</hardware_signoff>
