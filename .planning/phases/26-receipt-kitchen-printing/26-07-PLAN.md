<objective>
Give the kitchen a printed ticket, produced by the server that already knows which station cooks
what.

Research §9.3 decision 4 calls this the single biggest reliability win available in this phase, and
the reason is blunt: a kitchen ticket must print whether or not anybody is looking at a browser.
`POST /orders/{id}/send-to-kds` already exists, already knows the revision semantics, and already
publishes the event the kitchen display consumes. This plan hangs a print job off that same seam.

The ticket is enqueued here. Delivery to a physical printer with no browser open at all is plan
26-11's pull channel; until that lands, tickets drain through the browser bridge in 26-09. Either
way the job exists as a durable row the moment the order is fired, which is what makes the later
channel a delivery change rather than a redesign.

Purpose: the scope fence in 26-CONTEXT puts the kitchen ticket in scope, and D-26-05 requires the
routing to reach the station.
Output: a kitchen-ticket assembler, a dispatch service on the fire seam, and its tests.
</objective>

    Run GitNexus impact analysis on `OrderServiceImpl.sendToKds` and `OrderServiceImpl.performClose`
    before editing either. Both are on the live order path, both are covered by several integration
    tests, and `performClose` is the single seam that publishes the event four downstream services

    Create `PrintDispatchService` with two operations: dispatch the kitchen tickets for a fire, and
    dispatch the customer receipt for a close. Each resolves the target printer from the branch
    configuration, assembles, and enqueues through the existing issuance service.

    **The propagation boundary is the load-bearing decision in this task, so make it explicitly.**
    An earlier draft ran the enqueue inside the fire's own transaction and relied on a try/catch to
    keep failures away from the order path. That is wrong, and wrong in a way that would have looked
    correct in review and in every test that only forced Java-level faults. An insert that breaches a
    database constraint inside the caller's transaction marks that transaction **rollback-only**;
    catching the resulting exception in Java does not clear the flag, so the surrounding order
    transaction still fails at commit. A duplicate sequence in the print subsystem would take down
    the fire — precisely the outcome this plan's first prohibition forbids.

    Adopt an **after-commit boundary**. Inside the fire seam, register a transaction synchronisation
    whose after-commit callback invokes dispatch; annotate the dispatch operations so they run in a
    **new transaction** of their own. Consider and reject the two alternatives in a comment on the
    service, because both are tempting:

    - Same transaction with a try/catch — rejected for the rollback-only reason above.
    - `REQUIRES_NEW` invoked inline, before the fire commits — rejected because the ticket would
      commit independently and then survive a fire that rolled back, printing a phantom order the
      kitchen would cook.

    After-commit gives both properties that matter: a rollback-only flag cannot reach the fire,
    because the fire has already committed; and nothing is enqueued for an order that did not
    happen, because the callback never runs.

    **State its one real cost rather than hiding it.** A process death in the window between the
    fire's commit and the dispatch transaction loses that ticket with no row to show for it. The
    kitchen display is unaffected — it is event-driven, independent, and remains the source of truth
    — so food still gets cooked; but the paper ticket is silently absent, and silence is the failure
    mode this phase exists to eliminate. Close that with detection rather than pretending it away:
    add a reconciliation query, following the precedent of `scripts/reconcile-unposted-events.sql`,
    that lists orders fired with a routed station and no corresponding print job. Reference it from
    the summary and the agent README so an operator investigating a missing ticket has a first move.

    Because dispatch now runs outside the fire's idempotency guard, give the enqueue its own
    idempotency: key it on order, document type, target printer and revision, and let the unique
    index from 26-03 refuse the duplicate. Note that 26-03's index must include the target for this
    to be correct — a multi-station fire writes several rows for one order and document type, so an
    index scoped only to (tenant, order, type, sequence) would make a two-station fire collide with
    itself. Confirm that 26-03 landed the index with the target in it before writing this; if it did
    not, stop and raise it rather than working around it here.

    For the close path, enqueue only when the branch has a receipt printer configured. Distinguish
    that from a failure in the data, so a query can tell "this tenant prints in the browser" from
    "this tenant's printer is broken".

    Write `PrintDispatchIT` covering all twelve behaviours. The forced-constraint-breach cases are
    the ones that matter most: drive a genuine duplicate insert, not a mocked exception, because a
    mock cannot reproduce the rollback-only flag that is the whole point.
