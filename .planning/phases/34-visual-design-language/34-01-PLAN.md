<objective>
Build the zoning spine from D-34-02 and the test that enforces it, before any glass exists.

D-34-02 is the decision that keeps this product fast, and it is the one an executor under
deadline will quietly violate — not by adding glass to the POS, but by adding glass to a shared
`Card` that the POS happens to import, or to a shell header that renders above it. So the
enforcement is not a code-review note. It is a gate with two halves: a static half that walks the
import closure of the operational routes (catching the shared-primitive route) and a runtime half
that reads computed style in a real browser (catching the portal and global-stylesheet routes).

The gate is red today. `top-bar.tsx`, `mobile-bottom-nav.tsx` and `order-table-detail-drawer.tsx`
all carry a compositing filter and all three render on the POS screen right now, because POS still
lives inside the back-office layout. So this plan gets its negative control for free: the test is
written against a reality that fails it, and goes green by fixing that reality.

Purpose: every later plan in this phase is checked against this gate. Nothing that follows is
safe to write until the boundary exists and is proven to bite.
Output: a zone provider, zone declarations on all three zone roots, five de-blurred surfaces, and
a two-part containment gate.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator device to renderer | A cheap Android tablet's GPU is the scarce resource; a compositing filter crossing into the operational zone spends it |
| shared primitive to consuming zone | A component authored for the dashboard is imported by the POS and carries its treatment across the zone boundary |
| React tree to portal root | A portalled overlay leaves the zone subtree and loses every ancestry-based guarantee |
