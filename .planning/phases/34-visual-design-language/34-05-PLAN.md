<objective>
Give the four data states character, and prove the restyling did not undo the one thing phase 14b
bought.

Phase 14b's finding was that eleven of fifteen list screens rendered the empty state when the
request failed — a forced HTTP 500 and a forced empty array produced byte-identical text. The fix
was a component whose API makes the confusion unrepresentable. Restyling those states is exactly
the activity most likely to reintroduce the *visual* half of that defect while the API stays
correct: a designer's instinct on an error screen is to calm it, and a calm error looks like an
empty result.

So the deliverable here is two-sided. The states get depth, entrance and a considered empty
illustration. And a test renders a forced failure beside a forced empty result and asserts a person
can tell them apart — the same defect, re-asked after the restyle rather than assumed to have
survived it.

The second thing this plan fixes is smaller and real: the loading shimmer is an infinite animation,
and it reaches the operational zone through the shell's suspense boundaries. A perpetual animation
is a perpetual paint, on the device with the least to spare.

Purpose: these four states appear on every screen in the product, so they are the highest-leverage
place in the phase to add character — and the highest-leverage place to lose honesty.
Output: four restyled states, a zone-aware placeholder, and a distinguishability gate.
</objective>
