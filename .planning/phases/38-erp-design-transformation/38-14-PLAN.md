# 38-14 — Responsive

## Goal

One coherent breakpoint strategy, and content that is never clipped inside its container.

## Why

The shell is sound and the content is not. Measured at 390 / 768 / 1024 / 1440:

**What is already right — keep it.** **Zero routes produce horizontal page scroll at any width.**
The shell adapts: `MobileBottomNav` appears below `md`, the sidebar collapses, the top bar reduces
to icons. That is real work already done, and this plan does not disturb it.

**What is wrong is inside the containers.** `document.documentElement.scrollWidth` is fine while
individual elements are clipped or overlapping:

| Route | width | elements past the viewport |
|---|---|---|
| `/app/inventory/stock` | **390px** | **100** |
| `/app/inventory/stock` | 1024px | **42** |
| `/app/purchasing/purchase-orders` | 390px | 4 |

Visible in `evidence/shots/inventory-stock-mobile-light.png`: the desktop table dropped in
unchanged, "On hand" sliced mid-value — `90 EACI`, `213.5 K`, `-2987 K`. Brief §57: *"do not force
desktop tables onto mobile."*

And the POS, which is worse because it is silent — the probe reported **0 overflow** because the
cart panel does not overflow, it **overlays**. `evidence/shots/pos-mobile-light.png`: category
chips render as `Sta…`, `Ma…`, `Dri…`; menu tiles are sliced vertically; the till bar wraps
mid-value (`Float: Rs` / `5,000.00`). **An overflow probe cannot see an overlay defect. Only
looking can.**

Touch targets at small widths: `purchasing-po` **86** below 44px at 390px, `inventory-stock` **14**.

## Tasks

1. **Declare the breakpoint set and use only it**: 390 · 768 · 1024 · 1440 · 1920+. Brief §60: a
   coherent strategy, not dozens of breakpoints.

2. **Per-family adaptation, not scaling:**
   - **Lists** → `DataGrid` card fallback below `md` (built in 38-02; this plan verifies it
     everywhere).
   - **POS** → order panel becomes a bottom sheet with a persistent total bar; grid full-width
     (built in 38-04; verified here).
   - **KDS** → column count adapts; a ticket never truncates an item name.
   - **Forms** → single column below `md`; sections stack; actions become a sticky footer bar.
   - **Dashboard** → portlet grid reflows 4 → 2 → 1.
   - **Detail pages** → tabs become an accordion below `md`.

3. **Bottom sheets and drawers instead of large modals on mobile** (§29, §57). The 768px PO dialog
   becomes a full-height sheet below `md`.

4. **Touch targets ≥ 44px at every width**, not just on the POS.

5. **A viewport-integrity probe as a gate**, measuring what the audit measured: elements whose
   bounding box exceeds the viewport, **and** interactive elements whose bounding box is fully
   covered by a higher-stacked sibling — the overlay case that overflow counting misses.

## Verification

| Check | Kind | Passes when |
|---|---|---|
| Horizontal page scroll | e2e | 0 routes at 390 / 768 / 1024 / 1440. **Currently 0 — a regression gate** |
| **Element overflow** | e2e | 0 elements past the viewport on every audited route. Baselines: stock 100 → 0 @390, 42 → 0 @1024; PO 4 → 0 @390 |
| **Occlusion** | e2e | 0 interactive elements fully covered by a higher-stacked sibling. **This is the check that catches the POS cart overlay** |
| No `<table>` below `md` | e2e | card fallback on every list route |
| Target size | e2e | 0 controls < 44×44 at 390 and 768. Baselines: PO 86 → 0, stock 14 → 0 |
| Value truncation | e2e | no numeric cell renders with `text-overflow: ellipsis` active on a money or quantity value |
| Sheet not modal | e2e | below `md`, dialogs render as full-height sheets |
| Screenshots | automated_ui | every audited route × 4 widths × 2 themes, before/after |

### Negative controls — observe each failing

1. Render the desktop table at 390px → element-overflow red. It should reproduce the 100-element
   baseline exactly; if it does not, the probe is measuring something else.
2. Restore the two-column POS layout at 390px → **occlusion red**. Run this first: the defect
   exists today, so watch the check fail against current code before fixing.
3. Shrink a control to 40px → target-size red.
4. Force a money cell to ellipsis → truncation red.

> The occlusion check exists because the first audit pass reported `overflow=0` for the POS at
> 390px and the screenshot showed a broken screen. **A probe that measures the wrong property
> returns a confident, useless green.**
