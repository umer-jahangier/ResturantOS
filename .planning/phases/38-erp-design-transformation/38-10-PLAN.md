# 38-10 — Settings and authentication

## Goal

A settings architecture that is not one enormous page — scoped, honestly, after an audit that this
session could not perform.

## Why, and the limitation stated first

**Settings could not be audited.** `/app/settings` renders **"Access denied"** for a branch
manager, and the sidebar offers no Settings entry for that role, so the page is unreachable by
clicking. The roles that can reach it — `admin`, `owner` — both require TOTP, which this session
cannot satisfy (`scripts/CREDENTIALS.md`: *"Owner holds `rbac.manage` and both money codes"*;
tenant admin is challenged for `finance.period.close` and `hr.payroll.approve`).

`evidence/shots/settings-desktop-light.png` shows the access-denied state, which is itself
correct — it is a real, well-formed permission surface with a `[Back to dashboard]` action.

**So this plan's scope is provisional and task 1 is the audit.** Anything else would be planning
against a screen nobody in this phase has seen.

**Login is done.** 34-07 delivered it: a `GlassPanel depth={3}` with a brand band and `.vdl-enter`,
over `bg-surface-2` — an enumerated substrate, so the pairing is **measured**: 18.01:1 with the
compositing filter unavailable, 17.73:1 composited. Field names, submit path, error wording,
step-up prompt and redirect targets are untouched; 25 auth tests green. **Do not redo it.**
34-07 also fixed the evidence harness that had been producing byte-identical light and dark
screenshots.

**Not done by 34-07, and recorded as such:** `platform-shell.tsx`, `/platform/dashboard`,
`/platform/tenants` and `/app/settings` are **unchanged**. The SuperAdmin console is named in
phase 34's definition of done and was not delivered.

## Tasks

1. **Audit settings and the platform console under a TOTP-capable persona.** Enrol the owner or
   tenant-admin TOTP, walk every settings surface at four widths in both themes, and record what
   exists against brief §55's fourteen groups. **Write the findings into this plan before
   executing tasks 2–5.** If a group does not exist, say so; do not build an empty tab.

2. **Settings architecture (§55)** — grouped navigation across General · Restaurant · Branches ·
   Users · Roles · Permissions · Taxes · Payments · Printers · Kitchen · Notifications ·
   Integrations · Security · Appearance. **Never one enormous page.** Groups with no backing
   surface are not rendered as empty shells.

3. **The SuperAdmin console** — `platform-shell.tsx`, `/platform/dashboard`, `/platform/tenants` —
   onto `PageHeader`/`PageBody`, `DataGrid` and the shared `StatusBadge`
   (`components/platform/tenant-badges.tsx` is one of the six being collapsed).
   `components/platform/feature-matrix.tsx` is a hand-rolled table.

4. **Appearance screen and the brand-hue guard.** `/settings/appearance` can move the tenant brand
   colour at runtime. Two measured facts constrain it:
   - Phase 34's hue sweep proved glass contrast holds across the whole circle (worst 5.34:1 at
     125°) — but **only because `app/api/theme/route.ts` emits exactly thirteen declarations**
     (`--primary-50…950`, `--primary`, `--primary-foreground`) and no neutral, surface or
     foreground token. Three assertions keep that true. **If this plan changes what the route
     emits, the appearance screen needs its own contrast guard.**
   - Phase 20 measured that `--chart-1` follows the brand hue while `--chart-2..5` are pinned, so a
     tenant hue near **262°** walks series 1 into series 3 (ΔE2000 **15.8** at 262 against 35.5 at
     195). **The theme route must reject or nudge any `--brand-h` within ~35° of 262.** Phase 20
     carried this forward and it is still open.

5. `PageHeader` throughout; `h1Count === 1`; `ConfirmDialog` for destructive settings actions.

## Zone: `expressive`

Glass section cards, depth-1, entrance. Settings is low-frequency and reads as the product's
front-of-house. It may spend.

### Negative controls — observe each failing

1. Make the theme route emit `--surface-1` → the three phase-34 assertions must fail. Restore.
2. Set `--brand-h: 262` → the guard must reject or nudge; if the app renders it, red.
3. Change a login field name → the auth suite must fail (proves it still covers the form).
4. Add an empty settings group → empty-group check red.

If task 1 finds that most of §55's fourteen groups have no backing service, this plan delivers the
groups that exist and **reports §55 as partially delivered, with the list**. Fourteen tabs, ten of
them empty, is a worse product than four tabs that work.
