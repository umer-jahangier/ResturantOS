# 38-06 — Orders and tables

## Goal

An order list that can be scanned and filtered, an honest account of what the floor plan can
actually be built from, and a diagnosis of the defect that blocks it.

## Why

**Orders.** The order list shares the purchase-order screen's defects — no sticky header, no
pagination discipline, filters reduced to a status control, row heights of 65–81px against a
contract of 32/44. `h1Count = 0` on the POS order-management tab.

**Tables — and this is the important part.** The audit found two surfaces that disagree about
whether the restaurant has any tables:

| Surface | Reports |
|---|---|
| `/app/tables` | five tables — G1, T3 (Garden), T1, T2 (Rooftop), H1 (Other) |
| Manager dashboard | `TABLES OCCUPIED 0 / 5 · 5 free right now` |
| **POS → Floor View** | **"No tables configured"** |

Same tenant, same branch (`34cd6f62-…`), same session.
`evidence/shots/pos-floor-view-desktop-light.png`.

**This is a functional defect, not a design gap, and it blocks brief §17 entirely.** No floor plan
can be designed on top of a surface that reports zero tables. Diagnosis comes first.

## Tasks

1. **Diagnose the Floor View discrepancy** and record the finding. Likely candidates: a branch-id
   mismatch between the floor-view hook and the tables hook, an `active`/`area` filter, or a
   response-shape mismatch. **Fix only if the fix is presentational or a wrong query parameter in
   Layer 3.** If it is a service-side defect, record it, file it, and stop — do not design around
   it.

2. **Order list onto `DataGrid`** — sticky header, 44px comfortable rows, pagination, row
   selection, expandable detail, contextual row actions, shared `StatusBadge` for order status and
   payment status.

3. **Order number, never a UUID.** Enforced by `DataGrid`'s identifier-column rule (38-02).

4. **`FilterBar`** with the facets that exist today: status · payment status · order type · date
   range. **Server, customer and branch facets are blocked** on query parameters the orders
   endpoint does not accept (audit §12) — the chips are not built as dead controls.

5. **`/app/tables` stays the admin CRUD surface**, migrated to `DataGrid`, keeping its area
   grouping, with the shared `StatusBadge` and `ConfirmDialog` for retire.

6. **Declare the floor-plan visual vocabulary in the spec, build only what real data supports.**
   Brief §17's eight states (AVAILABLE · OCCUPIED · RESERVED · ORDERING · FOOD SERVED · PAYMENT ·
   CLEANING · OUT OF SERVICE), elapsed time, server and current order require occupancy,
   seat-time and server-assignment data that `pos-service` does not expose. Today's data supports
   `AVAILABLE` / `OCCUPIED` and seat count. **Build those two states honestly**; render the rest
   as unavailable with a stated reason rather than as an empty legend.

7. `PageHeader` on both surfaces so `h1Count === 1`.

## Verification

| Check | Kind | Passes when |
|---|---|---|
| **Floor View vs Tables agreement** | e2e | for a branch with N active tables, the floor view renders N. **Asserted against real seeded data, not a fixture** |
| Sticky header, row height, pagination | e2e | as 38-02 |
| Identifier column | unit | no UUID-shaped order identifier renders |
| Filter chips are live | e2e | every chip changes the result set; a chip that cannot filter is not rendered |
| Table status channels | unit | each state renders icon + text + colour |
| Unsupported states | unit | states without backing data render an explicit unavailable reason, **never a blank badge or a zero** |
| `h1` | e2e | exactly 1 on both routes |

### Negative controls — observe each failing

1. Point the floor-view hook at a different branch id → agreement check red. **Run this first,
   against the current code, and confirm the check reproduces the live defect.** If it does not,
   the check is measuring the wrong thing.
2. Render a status chip with colour only → channel check red.
3. Add a `Server` filter chip with no backing parameter → live-chip check red.
4. Substitute a UUID for the order number → identifier check red.

## Out of scope

Transfer / merge / split-bill workflows — behaviour, and blocked on the same missing data.
Reservation management. The activity timeline (§53), which needs an entity-scoped event feed from
`audit-service` that no surface consumes today.

## Honesty note

If the Floor View defect turns out to be service-side, this plan delivers the order list and the
tables CRUD and **reports §17 as not delivered, with the reason**. It does not ship a floor plan
that renders five decorative rectangles disconnected from the till.
