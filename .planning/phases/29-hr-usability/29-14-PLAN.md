<objective>
Prove the two claims this phase makes, end to end, and say plainly what it did not do.

Claim one is the definition of done's fifth item: payroll runs for the current fiscal year with no SQL.
That is the claim the audit's finding put in doubt, and it can only be proven by starting from a tenant
that has nothing — no departments, no components, no tax configuration — and reaching a calculated run
through the same surface a restaurant owner uses.

Claim two is the app-wide half: validation is live and errors name their field. Component tests prove the
kit; they do not prove the shipped screens use it. A browser test against the real stack does.

Purpose: this is where the phase either demonstrates itself or discovers it did not.
Output: one gateway script, two browser specs, a human verification checkpoint, and an honest closing
entry in the convention document.
</objective>

  <behavior>
    - On the employee form, blurring an empty required field shows its error with no submit having occurred.
    - Typing a valid value into that field clears the error on the keystroke, not on the next submit.
    - Submitting a duplicate employee number puts the server's message in that field's own error region, and the field receives focus.
    - The department control is a select whose options come from the tenant's list, and typing free text into it is not possible.
    - On the payroll screen with no tax configuration for the current fiscal year, calculating shows a notice naming that fiscal year and offering a link, and following the link reaches the tax configuration screen.
    - Configuring the year through the UI and returning allows the calculation to succeed.
    - On the leave request dialog, an end date before the start date is refused before submit with the message on the end date.
    - The assertions target each field's own error region rather than a page-wide text search, so a message rendered somewhere else cannot produce a false pass.
  </behavior>
  <action>
    Write hr-form-standard.spec.ts in the journeys project covering the field-level behaviours, and
    hr-payroll-cold-start.spec.ts covering the tax-configuration journey from refusal to success.

    Scope every assertion to the field. A page-wide text match is the failure mode that makes a browser test
    reassuring and worthless: the phase's whole point is that a message reaches the input it concerns, and a
    test that would pass with the message in a toast is not testing that.

    The cold-start journey is the one a reviewer should be able to watch: a user presses Calculate, is told
    which fiscal year is missing, clicks through, fills the table, comes back, and succeeds. If any step of
    that requires knowledge the screen does not give, this spec is where it shows.

    Where a behaviour cannot be asserted for an environmental reason, record it in the known-defects fixture
    with the reason, rather than deleting the assertion. An absent assertion is invisible; a recorded one is
    a decision someone can revisit.
  </action>
