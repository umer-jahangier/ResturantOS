<objective>
Build the form standard the whole app adopts, out of the parts that already exist.

The stack is not missing. `react-hook-form` 7.80, `zod` 4.4.3, a hand-rolled `createZodResolver`, and a
full shadcn-style `Form`/`FormField`/`FormMessage` set are all present and used by twenty-odd dialogs.
What is missing is behaviour, and the gap is the same one three times:

Not one `useForm` call in the codebase sets `mode`, so every form in the product uses react-hook-form's
default and validates only on submit. `ApiError` parses `fieldErrors` out of the response envelope and
nothing anywhere reads them — every `onError` collapses to a toast. And there is no shared select at all:
`components/ui/` has no `select.tsx`, so each screen writes its own `<select>` with a copy of the same
class string, and `MenuItemFormDialog` keeps a module-level `selectClass` constant for the purpose.

That is the shape this project's failure mode takes — structurally present, behaviourally absent. This
plan supplies the behaviour.

Purpose: every HR screen in wave 4, and the non-HR proof in wave 2, are written against this kit. It
must exist and be documented before any of them start.
Output: two form hooks, two select primitives, three form-component additions, a test suite that proves
the behaviours rather than the exports, and the convention document D-29-06 requires.
</objective>

  <files>frontend/lib/forms/standard-form.ts, frontend/lib/forms/server-field-errors.ts, frontend/lib/forms/index.ts, frontend/__tests__/lib/forms/server-field-errors.test.ts</files>
  <read_first>
    - frontend/lib/forms/zod-resolver.ts — the existing resolver, including setNestedError, which already walks a full dotted/indexed path; the server binder must produce paths of the same shape or nested errors will not resolve
    - frontend/lib/errors/api-error.ts — ApiError, its fieldErrors array, and the code predicates
    - frontend/lib/errors/user-facing.ts — formatUserFacingError and its code map; this stays as the fallback for errors with no field path and must not be deleted
    - frontend/lib/hooks/use-debounce.ts and use-debounced-value.ts — the debounce primitives already in the codebase; do not add a third
    - frontend/components/users/user-form-dialog.tsx — a representative current form, to confirm the new hook is a drop-in for `useForm({ resolver: createZodResolver(schema), defaultValues })`
  </read_first>
  <behavior>
    - A form created by useStandardForm reports a field's error after the user leaves that field, with no submit having occurred.
    - Once a field has been touched, each subsequent keystroke revalidates it, so an error clears the moment the input becomes valid rather than at the next submit.
    - A field the user has not yet touched shows no error, so opening a blank form does not greet the user with a wall of red.
    - applyServerFieldErrors takes an ApiError and sets one react-hook-form error per entry in fieldErrors, at the path each entry names.
    - A server field path that does not correspond to any field in the form is not silently dropped: it is surfaced as a form-level error so a contract mismatch is visible instead of invisible.
    - A server path is translatable: the caller may supply a mapping from server field name to form field name, because a form may collect rupees where the API takes paisa, and binding to a field that does not exist would lose the message.
    - An ApiError with no fieldErrors returns a form-level message produced by the existing formatUserFacingError, so nothing regresses for errors that genuinely have no field.
    - Applying server errors focuses the first offending field, so the user is taken to the problem rather than asked to find it.
  </behavior>
  <action>
    Create lib/forms/standard-form.ts exporting useStandardForm: a thin wrapper over useForm that takes a
    zod schema and the usual options, applies the existing createZodResolver, and sets `mode: "onTouched"`
    with `reValidateMode: "onChange"`.

    Those two settings are the entire disagreement with today's behaviour, so write the reasoning down
    where it is set. Pure `onChange` would fire while the user is typing the first character of a required
    field and tell them it is required — a form that argues with someone who is complying with it.
    `onTouched` waits for the first blur, and `reValidateMode: "onChange"` then makes every subsequent
    keystroke live, which is what D-29-02 asks for: validation as the user works, not at the end. The
    rule itself is shown before it can be broken by a persistent hint rather than by an error, which
    task 2 supplies as FormHint.

    Also expose from the hook the two things a submit control needs and no current form computes: whether
    the form is currently submittable, and if it is not, a sentence saying why — the count and the names
    of the fields still invalid, or the fact that a submission is in flight. Derive this from
    react-hook-form's own formState so it cannot drift from what the resolver believes.

    Create lib/forms/server-field-errors.ts exporting applyServerFieldErrors, taking the form, the thrown
    error, and an optional server-to-form field-name map. Walk ApiError.fieldErrors, translate each path
    through the map when one is supplied, and set the error at that path. Collect any path with no
    matching field and set them as a single form-level error naming them, rather than discarding them —
    a message the server took the trouble to produce and the client silently drops is worse than no
    message, because nobody ever learns it exists.

    Focus the first offending field after applying.

    For an error carrying no field path at all, fall back to formatUserFacingError so behaviour for
    those cases is unchanged. Do not modify user-facing.ts in this plan; its code map is consumed by
    screens outside this phase's scope.

    Debouncing: sync zod rules are cheap and run per keystroke without one. Reserve the existing
    use-debounced-value hook for rules that hit the network, such as a uniqueness check, and say so in
    the module comment so nobody adds a debounce to a string-length rule and makes the form feel laggy
    for no reason.

    Create lib/forms/index.ts as the barrel, re-exporting the resolver alongside the new hooks so a
    consumer has one import path.

    Write server-field-errors.test.ts covering the five binder behaviours as pure unit tests over a real
    useForm instance rendered in a test hook.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server error payload to rendered DOM | An error message crosses from an untrusted-in-principle response into the page |
| user input to request body | Client validation is a usability affordance, never an authorisation control |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
