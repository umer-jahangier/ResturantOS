<objective>
Prove the standard generalises, on a screen that has nothing to do with HR.

D-29-06 is blunt about why: a standard nobody else uses is not a standard. Two non-HR forms are good
candidates and both are converted here. `MenuItemFormDialog` keeps a module-level `selectClass` constant
— literally the duplication the shared Select exists to remove — and validates a price only on submit.
`CreateUserDialog` is the better-written of the two and still validates only on submit, still renders its
branch select inline with its own copy of the class string, and still collapses every server error into a
toast, including the pairing rule it deliberately enforces client-side.

Converting these before any HR screen is deliberate. If the kit only fits the module it was designed
alongside, this is where that shows, and it shows while there is still a whole wave in which to fix it.

Purpose: definition-of-done item 6, and an early failure signal on the wave-1 kit.
Output: two converted forms, a test that drives them as a user would, and a lint or test rule that makes
the next form use the standard by default.
</objective>
