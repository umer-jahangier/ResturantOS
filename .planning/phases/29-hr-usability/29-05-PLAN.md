<objective>
Turn the two worst free-text fields in the product into tenant-managed lists.

`employees.department` and `employees.designation` are TEXT. The Employees screen therefore offers two
text boxes, and the user's complaint follows: "Waiter", "waiter" and "Wtr" become three departments and
no report can group them. Plan 29-02 created the tables. This plan gives them an API, moves the
employee columns onto them, and — the part that cannot be skipped — carries the existing values across
rather than discarding a tenant's real data because it was entered badly.

`ddl-auto: validate` is deliberate in this project and caught a real boot failure once already. The
migration and the entity change therefore ship in this one plan; splitting them would leave hr-service
unable to start between two commits.

Purpose: every dropdown in wave 4's employee form, and the grouping in every HR report after it, needs
these to be rows rather than strings.
Output: two entities, one service, one controller, one migration with a backfill, and a test that proves
the backfill did not lose anyone.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tenant user to HR configuration API | Lists that every employee record references are written here |
| employee write to lookup reference | A client-supplied id could name a row in another tenant |
| Liquibase backfill to FORCE-RLS tables | The migration writes tenant rows with no session tenant context |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-29-05-A | Elevation of Privilege | Cross-tenant lookup id accepted on employee write | critical | mitigate | Every id is resolved against the caller's tenant before save and refused with a field path; RLS forces the same outcome at the database as defence in depth |
| T-29-05-B | Information Disclosure | List endpoints leaking another tenant's lists | critical | mitigate | Reads go through the tenant-scoped repository under FORCE RLS and are authorised by the OPA config action, which asserts same_tenant |
| T-29-05-C | Tampering | Backfill losing or misassigning employee data | critical | mitigate | `EmployeeLookupMigrationIT` seeds deliberately inconsistent values and asserts every employee's resulting reference; the TEXT columns are dropped only in the changeset after the backfill |
| T-29-05-D | Tampering | Backfill blocked or silently skipped by FORCE RLS | high | mitigate | The tenant GUC is set per tenant inside the changeset, following the idiom already proven by 900-seed-tax-config |
| T-29-05-E | Denial of Service | Deleting an in-use list entry orphaning employees | medium | mitigate | No delete endpoint exists; deactivation preserves referential integrity and history |
| T-29-05-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages. If one becomes necessary, halt and require the package-legitimacy audit plus a blocking human checkpoint |
</threat_model>
