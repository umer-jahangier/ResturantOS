<objective>
Unblock payroll.

The financial wiring audit's finding is exact and this plan is the response to it: `hr_db.tax_config`
holds one row, for the placeholder tenant `00000000-0000-0000-0000-000000000001`, for fiscal year 2026,
while `PayrollRunService.calculate` derives the fiscal year as `periodMonth >= 7 ? year + 1 : year` —
so a run for August 2026 asks for fiscal year 2027 and there is no row for it, for any tenant. There is
no controller, no screen and no write path: `TaxConfigEntity` has a protected constructor and not one
setter. Payroll cannot run.

The failure mode is as bad as the failure. `TaxConfigService` throws `IllegalStateException`, the shared
catch-all turns it into a 500, and the Payroll screen renders every mutation failure as a two-word
toast. So the most foreseeable condition in the subsystem — nobody has configured this year's tax
table — reaches the user as an unexplained server fault on a screen that offers no way to fix it.

While opening this file: `TaxSlab.ratePct` is a Java `double` and `SlabTaxCalculator` computes
`Math.round(excess * ratePct / 100.0)`. That is binary floating point in the income-tax computation,
against the phase's explicit constraint, and it is about to matter far more than it did — until now the
only slab table in existence was one a developer wrote; after this plan an accountant types the rates in.

Purpose: definition-of-done item 5 — payroll runs end to end for the current fiscal year with no SQL —
is unreachable without this plan, and items 3 and 4 are demonstrated by it.
Output: a writable tax configuration API, a named refusal for the absent case, one fiscal-year function,
and a decimal-clean tax path.
</objective>

## Trust Boundaries

| Boundary | Description |
