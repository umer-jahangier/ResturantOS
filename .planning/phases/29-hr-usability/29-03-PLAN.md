<objective>
Give HR configuration an authority before anything is built on top of it.

Everything this phase adds to the backend — departments, designations, salary components, tax
configuration — is tenant-level. `hr.rego`'s nine existing rules all end in `same_tenant_and_branch`,
which is correct for an employee record and wrong for a department list: the owner's token carries one
branch, and a branch-scoped predicate would let them manage the tenant's departments only while
switched to that one branch. The permission catalog has no `hr.config.*` code at all.

Three plans in wave 2 add controllers that must call this. If each invents its own answer, the phase
ends with three different ideas about who may edit the tax table.

Purpose: D-29-05 makes tax configuration a tenant-managed screen. A screen with no authority is either
unreachable or unguarded.
Output: two permission codes granted to the right existing roles including on existing tenants, two
rego rules with their own tests, and the hr-service enforcement point the wave-2 controllers call.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tenant user to hr-service configuration | A tenant-wide setting that determines every payslip is written here |
| JWT permission claim to OPA input | The permission set is asserted by the token and evaluated by the policy |
| tenant A to tenant B configuration | Dropping the branch predicate must not accidentally drop the tenant predicate |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-29-03-A | Elevation of Privilege | Tenant-scoped rules losing the tenant predicate | critical | mitigate | Both new rules call `common.same_tenant`; a cross-tenant denial test is part of the rego suite and of the integration suite |
| T-29-03-B | Elevation of Privilege | Branch operational roles reaching the tax table | critical | mitigate | The manage code is granted only to tenant-level owner/admin roles; the grant list is asserted in the changeset review |
| T-29-03-C | Tampering | Weakening the nine existing branch-isolated rules while editing the file | high | mitigate | A count assertion in the verify gate holds the number of branch-scoped rules at nine; per-action cross-branch denial tests are added |
| T-29-03-D | Denial of Service | Owners locked out because the grant reached only new tenants | high | mitigate | The changeset backfills existing tenants' roles, mirroring 045 |
| T-29-03-E | Spoofing | Permission claim trusted without a policy decision | high | mitigate | hr-service calls OPA rather than checking the claim locally; `DefaultOpaClient` converts any transport failure into a denial |
| T-29-03-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages. If one becomes necessary, halt and require the package-legitimacy audit plus a blocking human checkpoint |
